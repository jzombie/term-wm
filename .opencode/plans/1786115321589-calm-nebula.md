# Top panel: live drag + contained overflow indicators + submodule decomposition

## Problems (user-reported)
1. **Drag isn't obvious** — v1 only shows a drop bar; the entry stays put. The user
   wants it to *actually drag* (the item follows the cursor / reorders live).
2. **Chevrons obliterated** — the right `▶` and the entry strip are overwritten by
   the right-aligned tiling indicator (`render_tiling_indicator` runs AFTER
   `render_inner` and the strip's width math never reserves the tiling label's
   columns). The `◀`/`▶` aren't contained in their own region.
3. User wants the monolithic `WmTopPanelComponent` decomposed into applets/submodules
   so each region owns its rect and logic.

## Root causes (verified)
- `render` runs `render_inner` (strip + chevrons) then `render_tiling_indicator`
  (right-aligned at `max_x - tiling_width`) — wm_top_panel.rs:576-599. The strip's
  `max_entries_width` subtracts only menu+gap, NOT the tiling label, so the strip
  and `▶` extend under the tiling label.
- Drag v1 commits on Release only; a drop bar is the only affordance.

## Scope (confirmed with user)
**Full submodule decomposition** of the top panel, plus live drag and chevron
containment. No external callers of the panel's internals exist
(`menu_icon_*`, `hit_test_window`, `render_inner` are internal-only), and the crate
export is `pub use wm_top_panel::WmTopPanelComponent` + `pub mod wm_top_panel` — so
converting to a directory module `wm_top_panel/` keeps all public paths identical
(no lib.rs change).

## Structure — `crates/term-wm-sys-ui-components/src/wm_top_panel/`
- `mod.rs` — `WmTopPanelComponent` (public API unchanged: `Component` + `WmComponent`
  impls, `begin_frame`, `split_area`, `visible/height/area`, `menu_icon_rect`,
  `menu_icon_contains_point`, `hit_test_window`). Runs a small **layout pass** that
  assigns each applet a rect, then delegates render + events:
  `[menu][gap][window_strip .........][gap][tiling (right-aligned)]`.
- `menu.rs` — `MenuButton` applet: rect, `render`, `contains(col,row)`.
- `window_strip.rs` — `WindowStrip` applet: owns `h_scroll`, `drag_source`,
  `drag_cursor_col`, `drop_index`, `drag_moved`, `entries_start_x`,
  `scroll_viewport_width`, `max_scroll`, `entry_geometry`, `left/right_indicator_rect`,
  entry hit rects. Contains the two-phase render, chevrons, drag/reorder, edge-pan,
  scroll input — all strictly within ITS rect.
- `status.rs` — `StatusLine` applet: `render(rect, text, theme)`.
- `tiling.rs` — `TilingIndicator` applet: `render(rect, theme)` → rect + `contains`.

Layout pass (parent, single row):
- `menu_width` = menu label width; `tiling_width` = tiling label width (if present).
- `strip_rect` = `[ area.x + menu_width + MENU_GAP , area.x + area.width - tiling_width ]`
  (reserve the tiling slot on the right; `saturating` math).
- **StatusLine vs WindowStrip are MUTUALLY EXCLUSIVE, exactly like today:** when a
  status message is active (`status_line.is_some()`), assign `strip_rect` to the
  `StatusLine` applet (which truncates to fit); otherwise assign it to the
  `WindowStrip`. Only ONE of the two ever renders into `strip_rect` — the layout
  pass explicitly arbitrates, so they can never overlap or double-draw.
- The strip computes its own `max_entries_width = strip_rect.width`,
  `scroll_viewport_width`, `entries_start_x` (strip-local), chevrons INSIDE
  `strip_rect`. The right `▶` now sits strictly left of the tiling label → contained.

## Behavior fixes
### Live drag (obvious dragging)
- `WindowStrip::on_drag`:
  1. Edge-pan (cursor at strip edges nudges `h_scroll`, clamped).
  2. Compute the target index in the list EXCLUDING the dragged key (reduced-space):
     `idx = first reduced index whose entry logical_end > virtual_col`, default = len-1.
  3. If `idx != drag_source`'s current index → return
     `EventResult::Action(TermWmAction::ReorderWindow { key, index: idx })` so the WM
     live-moves the entry; next frame it renders in the new slot (item visibly follows
     the cursor).
  4. Else `Consumed` (no redundant dispatch).
- `WindowStrip::render`: while `drag_source == Some(key)` **AND `drag_moved` is true**,
  draw that entry with a distinct "dragging" style (e.g. `REVERSED` over the focused
  style). Gating the style on `drag_moved` (set by the first `Drag` event) prevents a
  plain click-to-focus from flickering into the drag style. Remove the redundant drop
  bar (the moving item is now the indicator).
- `WindowStrip::on_release`: clear drag state, return `Consumed` (the last Drag already
  committed). Plain click (no Drag event) never dispatches and never shows the drag style.
- Captured events still return `Consumed`/`Action`, never `Ignored` (unchanged contract).

### Edge-panning note (discrete events)
Terminal loops emit `Drag` only on physical cursor movement, so a user pans by holding
the cursor at a strip edge and "wiggling" (each wiggle fires a `Drag` → edge-pan step +
recompute). This is the standard limitation of the event model; the tests must simulate
multiple discrete `Drag` events (not a single one) to exercise multi-step panning.

### Chevron containment
- Menu, strip, and tiling each own a disjoint rect (layout pass). The strip's chevrons
  are drawn inside `strip_rect` only; guards skip a chevron if its column falls outside
  the strip rect. Tiling label is reserved in the layout pass so the strip never
  under-draws it.
