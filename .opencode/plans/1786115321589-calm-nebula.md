# Fix: monocle top-panel background presses must not fall through to windows

## Task (user, verbatim intent)
> Usability improvement when in monocle mode: clicking the chevron really fast
> the chevron can disappear, the panel will close, and you may accidentally
> click the window close button.

No demo app. This is the entire scope: a one-location fix + regression test in
the top panel component.

## Current state
The working tree was reset after an earlier attempt; the fix is NOT present.
`git status` shows no source changes. `wm_top_panel/mod.rs` `handle_events`
Press arm still ends with `EventResult::Ignored` at line 295.

## Root cause (verified)
`WmTopPanelComponent::handle_events` (crates/term-wm-sys-ui-components/src/wm_top_panel/mod.rs:280-295),
Press arm: menu → tab bar → tiling applet → fallthrough `EventResult::Ignored`.

In monocle-cramped mode the panel is an overlay `Layer`. Fast-clicks scroll the
tab bar to the end so the `▶` chevron disappears; the next click at that spot
hits the panel background → `Ignored`.

`handle_outside_click_precise` (crates/term-wm-core/src/window/window_manager/mod.rs:2434)
iterates hitboxes; a `Layer` returning `Ignored` (line 2463) falls through to the
next hitbox — the floating window overlapping the top row — returning `Focused`
(and the click lands on the window's close button). The runner's palette barrier
(runner.rs:580) closes the palette for anything that isn't
`OutsideClickResult::LayerConsumed`, which also hides the monocle panel overlay
(panel overlay is gated on the command menu being open).

## Fix — one guard
`crates/term-wm-sys-ui-components/src/wm_top_panel/mod.rs`, Press fallthrough
(replace the bare `EventResult::Ignored` at line 295):

```rust
// A press on the panel's background (no applet handled it) must be consumed
// so it never falls through to a window behind the panel (e.g. a floating
// window overlapping the top row in monocle), which would close the Command
// Palette and could hit the window's close button. Only consume when the panel
// is actually rendered (its area is set); an unrendered panel keeps Ignored.
if !self.area.is_empty() && rect_contains(self.area, mouse.column, mouse.row) {
    return EventResult::Consumed;
}
EventResult::Ignored
```

- Mirrors the exact idiom already used by `hit_test` at wm_top_panel/mod.rs:373
  (`!self.area.is_empty() && rect_contains(self.area, x, y)`).
- `LayerConsumed` ⇒ palette stays open, monocle panel overlay stays visible, the
  click never reaches the window behind it.
- Unrendered panel (`self.area` empty) keeps `Ignored`, so the existing
  `press_on_empty_panel_returns_ignored` test stays green.
- Non-monocle unaffected (windows sit below the panel row).

## Test
Add next to `press_on_empty_panel_returns_ignored` (~line 836) in
`crates/term-wm-sys-ui-components/src/wm_top_panel/mod.rs`:

```rust
#[test]
fn press_on_panel_background_is_consumed() {
    let keys = make_keys(1);
    let area = LayoutRect { x: 0, y: 0, width: 80, height: 1 };
    let mut p = WmTopPanelComponent::new("test-app");
    push_windows(&mut p, &keys, area); // sets p.area = area, active, display_order
    render_panel(&mut p);

    // Background press (past the single tab, not on menu/tab/chevron/tiling)
    // must be CONSUMED so it can't fall through to a window behind the panel.
    let res = p.handle_events(&mouse(MouseEventKind::Press(MouseButton::Left), 60, 0), &ctx());
    assert!(matches!(res, EventResult::Consumed), "background press must be consumed");
}
```
