# Top panel strip: gap before tiling indicator + auto-scroll only on focus change

Two related fixes to `window_strip.rs` / `wm_top_panel/mod.rs`.

## Issue 1 — right `▶` chevron butts against the tiling indicator
In `WmTopPanelComponent::render_contents` (`mod.rs:191-204`),
`strip_end = max_x - tiling_width`, so the strip's right edge (and its `▶` chevron
at `rect.x + width - 1`) is immediately left of the right-aligned `⊞ Float` label —
no gap.

**Fix (`mod.rs`):**
- Add `const TILING_GAP: u16 = 1;`.
- `let strip_end = if tiling_width > 0 { max_x.saturating_sub(i32::from(tiling_width + TILING_GAP)) } else { max_x };`
  (unchanged when no tiling indicator). Note: `max_x` is `i32`
  (`area.x.saturating_add(i32::from(area.width))`, mod.rs:177), so all the math is
  `i32` — no `u16` cast/type-mismatch.
- Strengthen `chevrons_do_not_overlap_tiling_indicator`: assert
  `strip_end <= tiling.x - i32::from(TILING_GAP)`.

## Issue 2 — chevron clicks are undone by per-frame auto-scroll
The strip auto-scrolls the focused entry into view EVERY frame when no drag is
active (`window_strip.rs:185-198`). So clicking `◀`/`▶` changes `h_scroll`, but the
very next frame's auto-scroll snaps it back to keep the focused window visible —
the click appears to do nothing.

**Fix (`window_strip.rs`) — auto-scroll only when the focused window, its logical
bounds, or the viewport size changed** (same guard pattern as
`ScrollHandle::ensure_selection_visible`):
- Add fields `last_auto_focus: Option<WindowKey>`, `last_auto_viewport: i32`, and
  `last_focused_logical_bounds: Option<(i32, i32)>` (init `None` / `0` / `None`).
  The logical bounds are `focused_range`'s `(logical_x, logical_width)` — derived
  purely from list order + label widths, independent of `h_scroll`, so they detect
  structural list mutations (spawn/close window, completed drag reorder) WITHOUT
  firing during manual panning.
- In render Phase 1, replace the unconditional auto-scroll block with:
  ```rust
  self.h_scroll = self.h_scroll.min(max_scroll);
  let focused_bounds = focused_range.map(|(x, w)| (x as i32, i32::from(w)));
  let auto_scroll = self.last_auto_focus != Some(focus_current)
      || self.last_auto_viewport != scroll_viewport_width
      || self.last_focused_logical_bounds != focused_bounds;
  if self.drag_source.is_none() && auto_scroll && let Some((flx, fw)) = focused_range {
      // existing auto-scroll logic (bring focused entry into view)
  }
  // Always update the trackers so a manual scroll (chevron/wheel/edge-pan) with
  // an unchanged focus/logical-bounds/viewport is preserved, while structural
  // changes (new/closed window, reorder) still re-follow the focused window.
  self.last_auto_focus = Some(focus_current);
  self.last_auto_viewport = scroll_viewport_width;
  self.last_focused_logical_bounds = focused_bounds;
  ```
- Behavior: auto-scroll engages on the first frame, on focus change, on a viewport
  resize, AND when the focused window's logical position shifts due to a list
  mutation (so a dragged-then-dropped active window snaps back into view). Manual
  scrolls persist until one of those changes.

## Tests (`wm_top_panel/mod.rs`)
- **`manual_scroll_persists_until_focus_changes`** (regression for issue 2):
  - Overflow setup, focus a middle window, render (auto-scroll once).
  - Simulate a chevron click / set `h_scroll` to a different value, render with
    the SAME focus → assert `h_scroll` is preserved (NOT snapped back).
  - Change focus to another window, render → assert `h_scroll` auto-adjusts to
    bring the new focused window into view.
- **`reorder_committed_off_screen_re_follows_focused`**: after a drag-drop that
  moves the focused window's logical position (structural mutation), the next
  render auto-scrolls it back into view even though focus is unchanged.
- Update `chevrons_do_not_overlap_tiling_indicator` for the `TILING_GAP` (issue 1).
- Existing scroll/overflow/drag tests remain valid (their first render always
  auto-scrolls since `last_auto_focus` starts `None`).
