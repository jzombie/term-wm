# Synchronize panel hit-test Z-order with visual Z-order

## Problem (user, recurring)
With a panel (or overlay) open OVER a floating window, hovering the floating
window's drag/resize handle still lights it up (draws the resize outline), even
though the handle is covered by the panel.

## Root cause (verified)
- Panels are hit-tested BELOW windows while being drawn ON TOP of them — a
  Z-order inversion between the hitbox registry and the render loop.
- `src/lib.rs:78` calls `wm.register_panel_hitboxes(...)` BEFORE the window loop
  (line 91), so panel hitboxes are registered FIRST = lowest hit-test priority
  (the registry's `hit_test` is LIFO — last-registered wins).
- Windows are composited in the window loop (91-250), so their chrome hitboxes
  (incl. `Chrome(Resize(...))`) are registered AFTER = HIGHER priority.
- `hovered_resize_handle` (window_manager/mod.rs:1222) uses `hit_test(pos)`; at an
  overlapping cell it returns the window's resize handle over the panel → the
  resize outline `render_resize_outline` lights up, AND clicking the panel row can
  accidentally grab the window's resize edge (invisible click-through).
- Visual order is correct (panels drawn on top via `render_panels` at line 253,
  overlays last via `render_overlays` at 473); only the hit-test order is wrong.

## Fix — register panel hitboxes AFTER windows (match visual Z)
- `src/lib.rs`: move `wm.register_panel_hitboxes(top_panel_owner, bottom_panel_owner)`
  from line 78 to AFTER the window loop (after line 250, before `render_panels` at
  253). Keep the owner computation (lines 68-77) where it is; only the registration
  call moves. Resulting hit-test order: windows → panels → overlays, matching
  visual Z.
- `hovered_resize_handle` stays UNCHANGED: with the panel on top, `hit_test(pos)`
  natively returns the `ComponentOwner::Layer` (not `Chrome(Resize)`), so the match
  fails and it returns `None` → the outline is suppressed. This also fixes the
  click-through: clicking the panel row now hits the panel, not the window.

## Why NOT the `hit_test_all`-occlusion hack (rejected)
The earlier idea of `hit_test_all(pos).any(Layer|Overlay)` in `hovered_resize_handle`
flattens Z (any background layer behind a window would wrongly suppress outlines)
and leaves the invisible resize hitbox on top of the panel (click-through). Fixing
the registration order is the correct, minimal fix that resolves both symptoms.

## Tests (`window_manager/mod.rs`)
- **`hovered_resize_handle_none_when_panel_layer_on_top`**: register a
  `Chrome(Resize(key, edge))` hitbox, then a `ComponentOwner::Layer` hitbox at the
  SAME rect (Layer registered last = topmost, as the lib.rs reorder produces), set
  hover inside → `None`.
- **`hovered_resize_handle_some_when_not_occluded`**: only the resize hitbox → `Some`.
- **`hit_test_prefers_panel_layer_over_window_resize`**: with both hitboxes at the
  same rect, `hit_test` at the point returns the `Layer` owner (not
  `Chrome(Resize)`) — the panel receives the click, not the window (click-through
  guard).
- Existing hover/resize/registry tests must still pass.
