# Fix: non-closable window headers showing the Close button

## Bug (user-reported)
With a mix of closable and non-closable windows, clicking a closable window
(focusing it) makes **non-closable** headers display the ✕ close button.

## Root cause
- `WindowManager::window_management_buttons()` (mod.rs:2636-2667) computes ONE
  button list from the **focused** window: it adds Close only
  `if self.window(focused).is_some_and(|w| w.closable())` (2643).
- `src/lib.rs:143` passes that single focused-derived list as `wm_buttons` into
  **every** window's `ChromeCtx` inside the per-window render loop.
- `render_window` (draw_plan_renderer.rs:1218-1234) draws `wm_buttons` on every
  header regardless of `focused`. So the focused window's ✕ appears on all
  headers, including non-closable ones.
- Header-button hitboxes already target the rendered window's own key
  (`ChromeTarget::CloseButton(*key)` etc., draw_plan_renderer.rs:148-151), so
  per-window buttons will match click behavior too.

## Fix: compute window-management buttons per window
### `crates/term-wm-core/src/window/window_manager/mod.rs`
- Add `pub fn window_management_buttons_for(&self, key: WindowKey) -> Vec<WmButton>`
  that computes buttons from `key` itself:
  - Guard: `if !self.windows.contains_key(key) { return Vec::new(); }`
    (handles a stale/invalid key).
  - Close button only `if self.window(key).is_some_and(|w| w.closable())`,
    action `CloseWindow(key)`.
  - Maximize/Restore (non-monocle) targeting `key`, label/symbol from that
    window's own `is_maximized()`.
  - Minimize (non-monocle) targeting `key`.
- Replace `window_management_buttons()` body with an explicit delegation
  (keeps the existing test + API). NOTE: `focused_window()` returns `WindowKey`
  (focus.rs:17 — `*self.focus.current()`, NOT `Option<WindowKey>`), so this is
  a direct call, not an `Option` match:
  ```rust
  pub fn window_management_buttons(&self) -> Vec<WmButton> {
      let focused = self.focused_window();
      if !self.windows.contains_key(focused) {
          return Vec::new();
      }
      self.window_management_buttons_for(focused)
  }
  ```
  (The review's SEV-1 assumed `focused_window() -> Option<WindowKey>`; it returns
  `WindowKey`, so no `if let Some(...)` is needed — the guard above covers the
  no-window case.)

### `src/lib.rs` (render loop, ~line 143)
- Change `wm_buttons: wm.window_management_buttons()` →
  `wm.window_management_buttons_for(*key)` so each header shows buttons for the
  window it belongs to.

Behavior after fix:
- Non-closable windows never show ✕ (reported bug fixed), regardless of focus.
- Each header's maximize/restore glyph reflects that window's own maximize state
  (fixes a latent visual inconsistency where focused state leaked to all headers).
- Clicking a header's control acts on that window (matches existing hitbox target).

## Tests
- Keep `window_management_buttons_hides_close_for_non_closable` (mod.rs:6013) —
  still passes (focused non-closable → `_for(focused)` has no Close).
- Add a regression test in mod.rs: two windows, one closable one not; assert
  `window_management_buttons_for(closable)` contains `CloseWindow(closable)` and
  `window_management_buttons_for(non_closable)` does NOT contain a Close for it —
  directly guarding the reported scenario (independent of which window is focused).
- Existing header-button/render tests use `test_wm_buttons()` directly and are
  unaffected.
