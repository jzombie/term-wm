# Fix: floating resize outline lights up under a panel/overlay (reuse existing occlusion)

## Acknowledge the mistake
I failed to find the existing occlusion mechanism used for the **tiling drag handle**
and instead invented hitbox-Z-order changes. Those changes are reverted (the working
tree is clean except this plan). This plan fixes the issue by REUSING the existing
`is_obscured` occlusion pattern — no new hit-test/priority/hack approaches.

## The existing pattern (already in the codebase)
- **Tiling drag handle:** `render_handles_masked(...)` (draw_plan_renderer.rs:1300)
  takes an `is_obscured` predicate (src/lib.rs:282-296) built from window regions
  above; the hover highlight is masked where a window covers the handle.
- **Floating resize outline:** `render_resize_outline(...)` (draw_plan_renderer.rs:1520)
  already has its own `is_obscured` (lines 1585-1594) that checks windows ABOVE in
  `draw_order`. It masks the outline where a window covers the hovered edge.

The gap: that `is_obscured` only considers **windows**, not **panels** or **overlays**.
So a floating edge under the top/bottom panel, or behind an open help/palette overlay,
is not masked and "lights up."

## Fix — fold panels/overlays into the EXISTING `is_obscured`
1. `crates/term-wm-console/src/draw_plan_renderer.rs`, `render_resize_outline`:
   add a parameter `extra_obscuring: &[LayoutRect]`. Build `is_obscured` by CHAINING
   the two sources — NO merged `Vec` (avoids heap allocation in the per-frame hot
   path; the pre-existing window `obscuring` `Vec` is kept as-is):
   ```rust
   let is_obscured = |x: u16, y: u16| -> bool {
       extra_obscuring.iter().any(|r| rect_contains(*r, x, y))
           || obscuring.iter().any(|r| rect_contains(*r, x, y))
   };
   ```
2. `src/lib.rs` (the `render_resize_outline` call at ~line 350): collect the extra
   occluders into a stack-allocated fixed buffer (no heap churn) and pass the used
   slice:
   ```rust
   // Modal invariant: every overlay (help, command palette, exit confirm) dims the
   // full managed area, so mask the whole area when any is open. Panels mask only
   // their claimed rows.
   let mut extra: [LayoutRect; 3] = [LayoutRect::default(); 3];
   let mut n = 0;
   let top = wm.top_claimed_area();
   if !top.is_empty() { extra[n] = top; n += 1; }
   let bottom = wm.bottom_claimed_area();
   if !bottom.is_empty() { extra[n] = bottom; n += 1; }
   if !wm.overlay_keys().is_empty() { extra[n] = area; n += 1; }
   let extra_obscuring = &extra[..n];
   render_resize_outline(buf, hovered_resize, None, wm.regions(), area, &floating_panes, draw_order, extra_obscuring, &wm.config().theme);
   ```
3. **Modal-overlay invariant (documented):** `overlay_keys()` denotes modal,
   full-area-dimming overlays; when any is open, the full managed `area` is masked.
   If a partial/floating overlay is ever introduced, iterate `overlay_bounds(key)`
   instead — noted in a code comment.

Effect (identical mechanism to the tiling drag handle):
- A floating window's edge under the top/bottom panel is masked where the panel covers it.
- While any modal overlay (help/palette/exit-confirm) is open, the whole resize outline
  is masked — the floating window no longer "lights up" underneath.
- No `hovered_resize_handle` changes, no hitbox-priority changes, no new suppression
  hacks.
