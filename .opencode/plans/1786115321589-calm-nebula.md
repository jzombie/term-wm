# Top panel: drag-to-reorder window list + horizontal scroll/overflow handling

## Decisions (confirmed)
- **Reorder scope:** list order ONLY (taskbar-style). It changes the top panel + Command
  Palette ordering via `build_display_order`; it does NOT touch the tiling tree,
  `z_order`, or `managed_draw_order` (on-screen arrangement unchanged).
- **Overflow:** BOTH — a horizontally scrollable entry strip AND an overflow
  indicator (edge chevrons) when entries remain off-screen.

## Background (verified)
- Panel order comes from `WindowManager::build_display_order()` (layout.rs:539-555),
  which sorts by `creation_order()` each frame. No reorder API exists;
  `creation_order` is read-only.
- `WmTopPanelComponent` renders `display_order` left-to-right (render_inner,
  wm_top_panel.rs:146-257); overflow = `break` at :233 (entries silently dropped);
  long labels truncated via `truncate_with_ellipsis`.
- Mouse: `handle_events` handles only `Press` (wm_top_panel.rs:350-368);
  `Drag`/`Release`/`Scroll*` return `Ignored`. Framework `ComponentInteraction`
  capture (window_manager/mod.rs:1919-1925) already routes Drag/Release back to the
  panel after a non-Ignored Press — so drag plumbing is ready.
- `ScrollLeft`/`ScrollRight` MouseEventKind exist (term-wm-events/src/lib.rs:185-186).
- `slice_by_columns` (helpers.rs:11) + `ScrollHandle` exist, but the panel doesn't
  use them; it's a self-contained leaf that owns `self.area`. We'll keep scroll
  state INSIDE the panel (no ScrollHandle threading).

## Feature 1 — Drag-to-reorder (list order only)

### `crates/term-wm-core/src/window/window_manager/mod.rs`
- Add field `user_display_order: Vec<WindowKey>` (init `Vec::new()` in `with_config`).
- Add `pub fn reorder_window(&mut self, key: WindowKey, index: usize)`:
  - Rebuild the list from the current effective `build_display_order()`, remove
    `key`, then **clamp** the insertion index against the list's current length
    (`let safe_index = index.min(list.len()); list.insert(safe_index, key);`) —
    the window set may have changed between the drag's index projection and the
    release dispatch (e.g. an async window close), so the index must never exceed
    the live list. Store as `user_display_order`.
  - No-op if `key` unknown. `mark_layout_dirty()`.
- Prune closed windows from `user_display_order` lazily (filter against `windows`).

### `crates/term-wm-core/src/window/window_manager/layout.rs`
- `build_display_order()`: when `user_display_order` is non-empty, start from it
  (filtered to live windows); otherwise creation order. Then append any mapped
  windows not yet listed (existing membership rule: `managed_draw_order` contains
  or `WindowState::Iconic`), in creation order. Keeps behavior identical when the
  user never reorders.

### `crates/term-wm-core/src/actions.rs`
- Add `TermWmAction::ReorderWindow { key: WindowKey, index: usize }` + category +
  Display label ("Reorder window").

### `crates/term-wm-core/src/runner.rs`
- Dispatch: `TermWmAction::ReorderWindow { key, index } => app.wm().reorder_window(key, index)`.

### `crates/term-wm-sys-ui-components/src/wm_top_panel.rs`
- Drag state fields: `drag_source: Option<WindowKey>`, `drag_cursor_col: Option<i32>`,
  `drop_index: Option<usize>`. These are an ONGOING multi-frame state machine: they
  must NOT be cleared in `begin_frame()` (which runs every frame during rendering —
  `Drag` events only fire on cursor movement, so clearing per-frame would make the
  drop indicator vanish whenever the user pauses mid-drag). They persist across
  frames and are cleared ONLY on `Release` (or a global drag cancellation, e.g. a
  press elsewhere / `Release` with no `drag_source`). `begin_frame()` continues to
  clear only the per-frame render data it already does (`list.window_hits`,
  `menu_rect`).
- `handle_events` (extend the existing override, keep global-coord style):
  - `Press` on an entry → focus it (existing `FocusWindow(key)`) AND set `drag_source = key`.
  - `Drag` → update `drag_cursor_col`; compute `drop_index` in **virtual (logical)
    space** projected from the entries' ACTUAL start column (menu + gap + LEFT
    indicator width only — NOT the total reservation):
    ```rust
    let entries_start_x = self.area.x as i32 + menu_width as i32 + MENU_GAP
        + left_indicator_width as i32;
    let virtual_col = drag_cursor_col - entries_start_x + self.h_scroll as i32;
    ```
    then find the insertion gap by comparing `virtual_col` against each entry's
    **logical** bounds; clamp cursor to the physical entries viewport and
    `drop_index` to `[0, display_order.len()]`. `entries_start_x` /
    `left_indicator_width` are computed in Phase 1 (below) and stored on the panel
    so the drag handler reuses the same geometry as painting.
  - **Edge-panning during drag (no deadlock):** edge indicators CANNOT be clicked
    while the button is held, so the `Drag` handler auto-scrolls: if
    `drag_cursor_col <= entries_start_x` →
    `h_scroll = h_scroll.saturating_sub(SCROLL_STEP)`; if
    `drag_cursor_col >= entries_start_x + scroll_viewport_width` →
    `h_scroll = h_scroll.saturating_add(SCROLL_STEP)` (clamped to the max scroll
    from Phase 1). This lets users reach off-screen drop targets while dragging,
    regardless of wheel support.
  - **Event consumption contract:** every captured panel mouse event returns
    `EventResult::Consumed` (or `Action(...)`), NEVER `EventResult::Ignored` —
    `Ignored` would let the drag coordinates bleed through to the terminal/PTY
    below the panel (text selection, etc.).
  - `Release` → if `drag_source` set and `drop_index` is valid, return
    `EventResult::Action(TermWmAction::ReorderWindow { key: drag_source, index: drop_index })`;
    otherwise return `EventResult::Consumed`. Clear drag state in both cases.

### `crates/term-wm-sys-ui-components/src/wm_top_panel.rs`
- Add `h_scroll: u16` field (panel-owned scroll offset).

#### Two-phase `render_inner` (avoids torn frames)
- **Phase 1 — Measure & auto-scroll (NO drawing):** walk `display_order`, compute
  each entry's logical width and the total `content_width`; record the focused
  entry's logical bounds.
  - **Static viewport reservation (no jitter):** use DECOUPLED indicator widths
    (`left_indicator_width = 1`, `right_indicator_width = 1`). Compute
    `max_entries_width` with SATURATING arithmetic (protects against a terminal
    resized narrower than the menu + gap):
    ```rust
    let max_entries_width = self.area.width.saturating_sub(menu_width + MENU_GAP);
    ```
    If `content_width > max_entries_width`, reserve BOTH indicator columns
    unconditionally for the whole frame:
    ```rust
    let entries_start_x = self.area.x as i32 + menu_width as i32 + MENU_GAP
        + left_indicator_width as i32;                          // left offset only
    let scroll_viewport_width = max_entries_width
        .saturating_sub(left_indicator_width + right_indicator_width); // total subtract
    ```
    `left_indicator_width` / `right_indicator_width` become 0 when there is no
    overflow. Else `scroll_viewport_width = max_entries_width`. Store
    `entries_start_x`, `left_indicator_width`, `right_indicator_width` on the
    panel for the drag handler.
  - Clamp `h_scroll` to `[0, content_width.saturating_sub(scroll_viewport_width)]`.
  - **Auto-scroll-to-focus is CONDITIONALLY suppressed:** adjust `h_scroll` to
    keep the focused entry visible ONLY when no drag is active
    (`self.drag_source.is_none()`). While a drag is in progress the user may
    manually scroll (wheel / edge indicators) to reach an off-screen drop target —
    an unconditional auto-scroll would instantly snap the viewport back to the
    (statically positioned) focused entry and make scrolling during drag
    impossible. All of this happens BEFORE any draw call.
- **Phase 2 — Paint (immutable `h_scroll`):** all rendering uses ABSOLUTE buffer
  coordinates; the entries viewport is a 0-based virtual window of width
  `scroll_viewport_width` starting at absolute `entries_start_x`. For each entry:
  - `vp_x = logical_x as i32 - self.h_scroll as i32` (0-based within the viewport);
    `vp_end = vp_x + width`.
  - Skip if `vp_end <= 0` (fully off the left) or `vp_x >= scroll_viewport_width`
    (fully off the right).
  - Compute the visible column range and slice the label once:
    `slice_start = max(0, -vp_x)`;
    `visible_width = min(scroll_viewport_width as i32, vp_end) - max(0, vp_x) as i32`;
    `label_slice = slice_by_columns(&label, slice_start as usize, visible_width as usize)`.
    This uniformly handles BOTH edges (left slicing and right truncation) so text
    never bleeds over the reserved `◀`/`▶` indicator columns.
  - Draw `label_slice` at absolute `x = entries_start_x + max(0, vp_x) as u16`
    (never a negative or zero-based coordinate) via `safe_set_string` with the
    same clip-to-bounds it already performs.
- Draw the drop indicator (vertical bar at the insertion gap) during the entry
  loop; draw `◀`/`▶` overflow indicators in their reserved columns.

#### Scroll input
- `handle_events`: handle `MouseEventKind::ScrollLeft/ScrollRight` (adjust
  `h_scroll`) and `Press` on an indicator rect (scroll by a named `SCROLL_STEP`).

- Extract magic literals into named consts per AGENTS.md: `ENTRY_PADDING` (the
  `" {label} "` padding `2`), `MENU_GAP` (`1`), `SCROLL_STEP`,
  `OVERFLOW_INDICATOR` glyphs `◀`/`▶`, `DROP_INDICATOR` glyph.

## Tests
- **WM (mod.rs/layout.rs tests):** `reorder_window` changes `build_display_order`;
  reorder is list-only (tiling tree / `managed_draw_order` unchanged); new windows
  append; closed windows are pruned; unknown key is a no-op; empty override
  preserves creation order.
- **Action dispatch (runner tests):** `ReorderWindow { key, index }` calls
  `reorder_window`.
- **Panel (wm_top_panel.rs tests):**
  - Overflow: with entries exceeding width, ◀/▶ indicators appear, `h_scroll`
    clamps to `[0, content - available]`, and no `u16` underflow / panic when
    scrolled to the far right (assert rendering is stable across `h_scroll` values).
  - Two-phase: `h_scroll` computed from Phase-1 measurement is stable and all
    painted entry coords are non-negative (no negative/`65535` cells in the buffer).
  - `ScrollLeft/ScrollRight` adjust `h_scroll`.
  - Focused-entry auto-scroll brings the focused entry into view.
  - Synthetic Press→Drag→Release: `drop_index` computed from **virtual** columns
    (drag far off the right edge clamps to `len`; far left clamps to `0`) and the
    release dispatches `ReorderWindow { key, index }`; drop indicator shown during
    drag.
- **Changelog:** add an entry to `CHANGELOG.md` under `0.9.15-alpha`.

## Out of scope
- Persisting order across sessions (no session-persistence infra exists).
- Live-reorder-while-dragging (v1 uses a drop indicator + commit on release).
- Reordering the tiling geometry (per user decision).

cargo test -p term-wm-core reorder
cargo test -p term-wm-sys-ui-components wm_top_panel
cargo clippy --workspace --all-targets --all-features -- -D warnings

(palette + panel reflect new order; on-screen layout unchanged); narrow the terminal
→ strip scrolls (wheel) and ◀/▶ indicators appear for off-screen entries.
