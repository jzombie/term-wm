# Plan: Fix long-line paste "types over" in editors — DECAWM in `term-wm-vt100`

## Task
Bug (user-verified): paste a line WIDER than the terminal into pico/nano; editing it "types over"
stale cells. Only long lines (horizontal scroll). Preexisting in the base vt100 emulator.

## Root cause (verified)
`term-wm-vt100` does not implement **DECAWM (`ESC[?7h/l`)** — `decset`/`decrst`
(screen.rs:1145-1219) have no param-7 arm, so autowrap is always ON. Editors horizontally
scrolling a long line disable wrap and manage their own columns; with wrap forced on, a char at
the right margin wraps the virtual cursor down a row, desyncing it from the editor → text appears
"typed over."

## DECAWM implementation spec (crate-side; user publishes)

### 1. State tracking (`Screen`)
- Add `decuwm: bool` (default `true`). `DECSET 7` → true; `DECRST 7` → false.

### 2. Clamp cursor on `DECRST 7` (review)
Pending wrap is encoded as `cursor.col == size.cols`. On `DECRST 7`, clamp it so the cursor is
never out of bounds while wrap is disabled:
```rust
7 => {
    self.decuwm = false;
    if self.cursor.col >= self.size.cols {
        self.cursor.col = self.size.cols.saturating_sub(1);
    }
}
```

### 3. Character placement (`text()`) — rigid margin when wrap off
- `decuwm == true` (default): preserve existing xterm deferred-wrap behavior unchanged.
- `decuwm == false`:
  - If `cursor.col >= size.cols`, clamp `cursor.col = size.cols - 1`.
  - Write the cell at `cursor.col`.
  - Increment `cursor.col` by 1 only if `cursor.col < size.cols - 1`.
  - If `cursor.col == size.cols - 1`, leave it there. Do NOT set `cursor.col = size.cols`.
  - Skip the `col_wrap` row-advance entirely. Subsequent chars overwrite column W-1 until an
    explicit move (`CUP`, `CUF`, `CR`, `LF`).

### 4. `EL 0` (`ESC[0K`) at pending wrap (review)
When `cursor.col == size.cols` (pending wrap), the current erase range `size.cols..size.cols` is
empty and leaves column W-1 stale. In the `EL` handler, if `cursor.col >= size.cols`, first clamp
`cursor.col = size.cols - 1`, THEN compute the erase bounds, so column W-1 is cleared. Also clear
any pending-wrap state.

  `make_parser_test_args()` helper + `parser_read_loop`, feeding `\x1b[?7l` + 85 chars on the

  ```rust
  #[test]
  fn parser_read_loop_decawn_off_does_not_wrap() {
      let mut args = make_parser_test_args();
      let mut payload = Vec::new();
      payload.extend_from_slice(b"\x1b[?7l");
      payload.extend_from_slice(&[b'x'; 85]);
      args.reader = Box::new(std::io::Cursor::new(payload));
      let shared = Arc::clone(&args.shared_parser);
      parser_read_loop(args);

          screen.cursor_position(),
  ```

## Fast-typing "blows right past" — flaky, types over chars on a WRAPPED line

### Updated understanding (from user)
- Symptom: typing fast in pico at the right margin "types right over existing characters on a
  wrapped line." Slow/paste case is INCONSISTENT (sometimes works).
- A WRAPPED line runs with **autowrap ON** (deferred wrap) — the DECAWM fix only changed the
  wrap-OFF path, so it does not cover this case.
- FLAKY ⇒ timing/interleaving-sensitive ⇒ a race or a margin-state interaction, not a
  deterministic DECAWM gap.

### Race-theory verification (evidence-based; refutes persistent-render-race)
- **Mid-burst render**: real but TRANSIENT (≤1 frame). Render is sequence-atomic (same
  `shared_parser` mutex as `process()`, terminal.rs:593-596) and self-correcting (edge-triggered
  dirty + Wakeup re-arms on the completing chunk, pty.rs:906). Cannot persist.
- **CPR/DSR**: written synchronously in `Pty::screen()` (pty.rs:658-665) via the same mutexed
  `PtyWriter` as keystrokes — no interleaving. Real weakness = STALENESS (reports the parser
  cursor at render time, up to 16ms late). Secondary suspect.
- **Per-read redraw**: refuted — wakeup is edge-triggered/coalesced; no torn chunk can be sampled.
- **Key fact**: pico never sees the rendered frame (only PTY input + CPR). A transient bad frame
  cannot feed back into pico's state. Persistent desync ⇒ emulator STATE divergence from pico's
  expectation ⇒ deferred-wrap / pending-margin interaction (timing-dependent ⇒ flaky), NOT a
  render race.

### Primary fix — emulator pending-wrap/margin hardening (the evidence-backed direction)
ROOT DIVERGENCE (review-confirmed): xterm's pending-wrap cursor sits at the LAST column
(`cols-1`) with a separate wrap-pending flag; this emulator encodes it as `cursor.col == size.cols`
(one PAST the last column). Consequences that are timing-dependent (hence flaky):
- `BS`/`CUB` from pending: xterm goes `cols-1 → cols-2`; this emulator goes `cols → cols-1`
  (one column off) → retyped chars overwrite the wrong cell → "types over."
- `CPR` (`ESC[6n`) from pending: this emulator reports `cols` (0-based) instead of xterm's
  `cols-1` → ncurses computes wrong relative deltas.

Implement in `term-wm-vt100` (`grid.rs` / `screen.rs`):
- `resolve_pending_wrap()` helper: `if pos.col >= size.cols { pos.col = size.cols.saturating_sub(1) }`.
  Called at the START of every relative-move / line-modify handler so pending state is
  canonicalized to the right margin BEFORE the operation:
  - `bs()` → resolve, then `col_dec(1)` ⇒ lands on `cols-2` (matches xterm).
  - `cub()` → resolve, then `col_dec(offset)`.
  - `cuf()` → resolve, then `col_inc_clamp(offset)` (stays at margin).
  - `ed()` modes 0/1 → resolve before `erase_all_forward/backward` (they use `pos.col`).
  - `el()` mode 0 → already clamps at the pending position (kept).
  - `cursor_position()` → resolve before returning, so `ESC[6n` replies report `cols-1`, not `cols`.
- The wrap-on-next-printable behavior is preserved: `text()` still sees `col == size.cols` and
  wraps; only control-sequence handlers resolve it.

Fork regression tests (in `src/screen.rs`):
- `bs_from_pending_wrap_lands_on_second_to_last`: 80 'a' (wrap on, pending), `\x08` → cursor
  `(0,78)`; `\x08` again → `(0,77)`.
- `cub_from_pending_wrap_lands_on_second_to_last`: 80 'a', `\x1b[D` → `(0,78)`.
- `cpr_from_pending_wrap_reports_margin`: 80 'a', then `cursor_position()` → `(0,79)` (not 80).

Workspace integration test (`crates/term-wm-pty-engine/src/pty.rs`):
- `parser_read_loop_wrapped_line_backspace_clears_pending_wrap`: feed 80 'a' with autowrap ON
  (cursor pending at col 80), then `\x08` + `'Z'`. Assert `cursor_position() == (0,79)`,
  `cell(0,78) == "Z"`, and `cell(0,79) == "a"` (unchanged — BS moves the cursor, it does NOT
  erase; the retyped char lands at 78, not overwriting 79).

CPR timing (review #2): the `cursor_position()` resolve removes the off-by-one. The
render-time-vs-parse-time staleness (≤16ms) is noted but LOW priority — ncurses rarely issues
`ESC[6n` mid-typing; only pursue reader-time capture if the trace shows pico CPRing during the
repro.
