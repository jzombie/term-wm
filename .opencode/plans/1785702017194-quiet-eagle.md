# Plan: Prevent narrow side-by-side columns from balanced tiling inserts

## Goal
`insert_window_balanced` currently splits a tile horizontally whenever
`visual_w >= visual_h` (`CELL_ASPECT_RATIO = 2`). On a half-screen column
(60 cols × 24 rows in a 120×24 terminal) `visual_w`=60, `visual_h`=48 → it
splits `Right`, producing two 30-wide full-height strips — the "narrow
column" symptom. Fix by biasing horizontal splits: require the region to be
clearly wider (≥1.5× visual height) before splitting side-by-side.

## Root cause recap
- `reweight_by_leaf_count` (layout-engine `tiling.rs:627`) equalizes **area only**
  (1/N per leaf); it never changes split directions or topology.
- Split **direction** is fixed at insert time in `insert_window_balanced`
  (core `tiling.rs:124-184`), from the aspect of the single largest leaf.
- The `_` tie-break arm (`tiling.rs:169-175`) uses an unbiased
  `visual_w >= visual_h`; a 60×24 half-column satisfies it → `Right` →
  narrow child strips. The 1.25× option ties exactly at 60×24 (240 == 240),
  so 1.5× is required.

## Changes

### 1. `crates/term-wm-core/src/constants.rs` (after line 74, `CELL_ASPECT_RATIO`)
Add named integer-multiplier constants (lossless, no float):
```rust
/// Horizontal-split bias for `insert_window_balanced`: visual width must be at
/// least 1.5x (3/2) visual height before a tile splits side-by-side, so a
/// horizontal split never produces tall, narrow vertical child strips.
pub const TILING_HORIZONTAL_BIAS_NUMERATOR: u32 = 3;
pub const TILING_HORIZONTAL_BIAS_DENOMINATOR: u32 = 2;
```

### 2. `crates/term-wm-core/src/layout/tiling.rs` — `insert_window_balanced`
Replace only the `_` tie-break comparison (lines ~169-175). Keep the
`(true, false) → Right` and `(false, true) → Bottom` arms unchanged.
```rust
_ => {
    let visual_h = (largest_rect.height as u32) * crate::constants::CELL_ASPECT_RATIO;
    let visual_w = largest_rect.width as u32;
    if visual_w * crate::constants::TILING_HORIZONTAL_BIAS_DENOMINATOR
        >= visual_h * crate::constants::TILING_HORIZONTAL_BIAS_NUMERATOR
    {
        InsertPosition::Right
    } else {
        InsertPosition::Bottom
    }
}
```
Effect: 60×24 → 120 < 144 → `Bottom` (stacked). 96×24 → 192 ≥ 144 → `Right`
(square 48×24 panes). 80×24 → 160 ≥ 144 → `Right` (2-up preserved).

### 3. Unit tests — `crates/term-wm-core/src/layout/tiling.rs` (tests module)
Add alongside the existing `insert_window_balanced_*` tests:
- `insert_window_balanced_avoids_narrow_vertical_strips`: single leaf, area
  60×24, insert id 2 → assert both regions have `width == 60`, `x == 0`, and
  `r1.y < r2.y` (stacked, not side-by-side).
- `insert_window_balanced_splits_square_panes_horizontally`: area 96×24 →
  assert `r1.x < r2.x` and both `width == 48` (side-by-side preserved for
  genuinely wide regions).
- `insert_window_balanced_two_up_landscape_stays_side_by_side`: area 80×24 →
  assert `r1.x < r2.x` (regression guard: 80×24 2-window layout unchanged).

### 4. WM-level test — `crates/term-wm-core/src/window/window_manager/layout.rs` (tests module)
`three_windows_on_wide_area_do_not_form_narrow_columns`:
- Seeded `make_wm` at 80×24 is too narrow; construct a WM, disable chrome,
  `register_managed_layout(Rect { 0, 0, 120, 24 })`.
- Open 3 windows (create + Mapped + tile, or `open_window`).
- Assert: no region has `width < 38`, and at least two regions share the same
  `x` (i.e. windows stack in a column rather than forming three full-height
  strips). Without the bias this fails (three ~40-wide full-height columns).

### 5. `CHANGELOG.md` — `[0.9.7-alpha]` balanced-tiling entry
Extend the Added bullet: horizontal splits now require the region to be ≥1.5×
as wide as tall (visual), so inserting windows into a half-screen column stacks
them instead of creating narrow side-by-side strips.

## Explicitly out of scope
- Drag-snap paths (`resolve_target` / `detect_quadrant` in `drag.rs`, used at
  `drag.rs:461` and `layout.rs:888`) — user-positioned, left unchanged.
- `(true,false)` / `(false,true)` minimum-size arms — left unchanged.
- No post-insert re-orientation / topology mutation (rejected: invalidates
  user-dragged split ratios, adds oscillation risk).
