# Plan: Fix terminal "garbage" on horizontal resize (reflow of the cursor's active line)

## Status
Investigation complete; root cause confirmed and reproduced. Part of the fix (preserve the
cursor's logical line in reflow) is already implemented in the vendored vt100 with test
updates; one essential piece remains (see Fix, step 2). Do NOT commit further — this plan
must be approved first.

## Symptoms (user-reported, reproduced)

Resizing a terminal horizontally — worst in tiled side-by-side terminals running `ls -lsa`
— leaves garbage rows on screen:

```
g  5 13:35 tests
  0 drwxr-xr-x@  3 administrator  staff      96 Au
g  6 11:03 vendor
administrator
administrator@d17-4 term-w
administ
administrator@d17-4 term-wm %
```

- Partial/duplicated shell prompt rows ("administrator", "administrator@d17-4 term-w",
  "administ") interleaved with `ls` output.
- Corrupted `ls` lines ("Aug  5" split as "Au" | "g  5"), i.e. wrong wrap boundaries.
- **Accumulates**: a shell reproduction cycling widths `20→40→20→30→20→46` shows **one
  new stale "administrator@d17-4" row per cycle** (cycle 0: 1 junk row; cycle 5: 6 junk
  rows).

## Root cause

1. **Reflow re-wraps the cursor's active line.** `Grid::reflow` flattens and re-chunks
   *every* logical line, including the line the cursor is on (the shell prompt). When the
   width shrinks, a 1-row prompt re-wraps into 2 rows.
2. **The shell's redraw only erases downward.** After SIGWINCH, zsh redraws its prompt with
   `\r \r ESC[0m ESC[27m ESC[24m ESC[J administrator@d17-4 ~ % `. `ESC[J` (ED) erases from
   the cursor **downward only**. Because the reflowed prompt's first row is *above* the
   cursor row, it survives the erase; the shell then draws a fresh prompt below it → the
   prompt appears duplicated/partial (the "administrator@d17-4 term-wm %" repeated rows).
3. **Accumulation.** Once the prompt is multi-row, the next resize preserves a multi-row
   cursor line whose first row(s) sit above the cursor, so the next `ESC[J` can't clear
   them either → one more stale row per resize cycle.

The byte stream itself is correct (the shell emits the prompt once); the emulator's reflow
leaves stale rows the shell's erase-from-cursor protocol cannot reach. This cannot be
"fixed" in the shell; it must be fixed in the reflow.

## Evidence / reproduction

- **Pure vt100 (minimal):** `Parser::new(24, 80, 2000)`; write `"some output\r\n
  administrator@d17-4 ~ % "`; `set_size(24, 20)`; then process the captured shell redraw
  bytes `\r\r\x1b[0m\x1b[27m\x1b[24m\x1b[Jadministrator@d17-4 ~ % ` → rows now contain the
  prompt twice (stale row + fresh rows).
- **Real shell (accumulation):** spawn `zsh`, `ls -lsa` in a directory with many files at
  46 cols; cycle widths 10×; screen gains one stale `administrator@d17-4` row per cycle.

## Fix (vendored `vt100/src/grid.rs`, `Grid::reflow`)

The application owns its active line and redraws it on SIGWINCH, so the reflow must leave
the cursor's line in a state the shell's `\r ESC[J` redraw can fully clear.

1. **Preserve the cursor's logical line** (already implemented, `is_cursor_line` branch):
   do not flatten/re-wrap the line containing `cursor_g`; keep its original rows resized
   (truncate/pad) to the new width.
2. **Position the cursor at the START of that preserved line** (`(line_start_in_all, 0)`
   rather than clamping it to the cursor's old column). Then the shell's `\r` + `ESC[J`
   erase covers the entire preserved line, the redraw is clean, and no stale row survives
   into the next cycle — eliminating both the duplication and the accumulation.

   (This is the missing piece. The cursor is transiently at the start of the line; the
   shell immediately redraws and repositions it. The current code sets
   `cursor_res = (line_start_in_all + (cursor_g - start), cursor_col.min(new_cols))`; change
   it to `(line_start_in_all, 0)`.)

## Tests to add/update

- **Vendored crate regression test** (`tests/reflow.rs`): a test reproducing the exact

  asserting the prompt appears exactly once.
- **Accumulation test** (in the shell harness or a pure-vt100 loop): N resize cycles must
  not grow the count of stale prompt rows.
