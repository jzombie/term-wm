# Plan: Fix pico background-color loss in the PTY engine (terminfo/`bce` + reader-thread hardening)

## Problem

pico (and other ncurses apps) lose background colors when run under term-wm on macOS.

### Root cause (confirmed)
term-wm unconditionally forces `TERM=screen-256color` for every spawned child
(`CHILD_TERM`, pty.rs:135). On macOS, Apple's shipped `screen-256color` terminfo **lacks the
`bce` (Background Color Erase) capability** — verified locally:

```
$ infocmp -1 screen-256color | grep bce    → (nothing)
$ infocmp -1 xterm-256color | grep bce     → bce,
```

Without `bce`, ncurses cannot assume `\x1b[K` (EL) erases to the current background, so it
compensates by resetting attributes before line erasures. vt100 processes those reset bytes
literally, erasing the background. This cannot be fixed in the VTE layer — the byte stream
is wrong at the source, so the fix is to advertise a terminfo entry that has `bce`.

The original reason `screen-256color` was chosen (comment at pty.rs:138-151) was that
`xterm-256color`'s advanced layout / `bce` shortcuts "break inside multiplexer grid math".
That concern is neutralized by the already-landed `LC_CTYPE=UTF-8` stripping (pty.rs:162-164):
the grid-math crashes were caused by `setlocale` failing on the invalid locale, not by the
terminfo entry. vt100 itself honors `bce` semantics (its `EL`/`ED` clear with the current
attributes), so a `bce`-capable terminfo yields correct backgrounds.

### Secondary issues (from review)
- Reader thread (`parser_read_loop`) uses `.unwrap()` on poisoned-mutex locks
  (`shared_parser` :808, `dirty_cond` :854, `cvar.wait` :856, plus test-only `osc52_text`
  :750/:823) — a panicking consumer crashes the reader thread and deadlocks the I/O pipe.
- `generate_snapshot` (:612-616) and `screen_lines` (:472-482) hold the `shared_parser`
  lock across the full O(rows×cols) formatting work, starving the reader thread during
  high-throughput I/O.

## Files to change

- `crates/term-wm-pty-engine/src/pty.rs` — all three fixes + test updates
- (no vt100 changes needed)

## Steps

### 1. Platform-specific `CHILD_TERM` (the actual pico fix)
- Replace the single `CHILD_TERM` (pty.rs:135) with cfg-guarded constants:
  ```rust
  /// macOS ships a defective `screen-256color` terminfo lacking `bce`, which
  /// makes ncurses apps (pico, nano) reset attributes before line erases and
  /// drop backgrounds. `xterm-256color` has `bce` and is safe now that the
  /// invalid `LC_CTYPE=UTF-8` is stripped. Other platforms keep
  /// `screen-256color` (their terminfo has `bce`).
  #[cfg(target_os = "macos")]
  const CHILD_TERM: &str = "xterm-256color";
  #[cfg(not(target_os = "macos"))]
  const CHILD_TERM: &str = "screen-256color";
  ```
- Update the `sanitize_child_environment` doc comment (pty.rs:138-151) to reflect the new
  rationale (bce/terminfo, macOS-specific).
- Keep `CHILD_COLORTERM = "truecolor"` unchanged.
- Add a test helper (e.g. `fn expected_child_term() -> &'static str`) mirroring the cfg so
  tests don't duplicate the branches.

### 2. Standardize mutex poison handling in `parser_read_loop`
The reader thread must survive a poisoned mutex (caused by a consumer panicking while
holding a lock) instead of panicking and deadlocking the I/O pipeline — or, with `if let
Ok`, silently dropping signal traffic. **Every** lock acquisition in `parser_read_loop`
becomes `unwrap_or_else(|err| err.into_inner())` so the recovered state is still used:

- :808 `shared_parser.lock()` — recover and parse the chunk
- :854/:856 `dirty_cond` — apply recovery to **both** the initial acquisition and the
  condvar wake cycle (condvar re-acquires the mutex before returning and can surface a
  `PoisonError` after the sleep):
  ```rust
  let mut guard = lock.lock().unwrap_or_else(|err| err.into_inner());
  while dirty.load(Ordering::Acquire) {
      guard = cvar.wait(guard).unwrap_or_else(|err| err.into_inner());
  }
  ```
- :750/:823 `osc52_text.lock()` — test hook; standardize for consistency
- :776 `pending.lock()` / :772 `last_bytes.lock()` — recover, don't drop buffered bytes
- :754/:797/:839/:867 `status_cb.lock()` — **critical**: this dispatches `Wakeup`/`Exited`
  and is the sole reader→UI signaling path. Skipping it on poison would silently swallow
  wakeups, park the reader at `IO_BURST_BUDGET` on `dirty_cond`, and deadlock the render
  loop. Recover so the callback still fires:
  ```rust
  let mut guard = status_cb.lock().unwrap_or_else(|err| err.into_inner());
  if let Some(ref cb) = *guard {
      cb(crate::PtyStatus::Wakeup);
  }
  ```
- :813 `pending_title.lock()` — recover and keep title updates

No behavior change in the non-poisoned path; on a poisoned mutex the reader thread keeps
running, keeps signaling, and keeps buffering instead of crashing or going silent.

### 3. Reduce `shared_parser` lock hold time in snapshot generation
`Screen` is `Clone` (vendor/vt100/src/screen.rs:54), so clone out of the lock, drop the
guard, then format on the local clone:
- `generate_snapshot` (:612-616):
  ```rust
  pub fn generate_snapshot(&mut self) -> Vec<u8> {
      self.screen();
      let screen = self.shared_parser.lock().unwrap_or_else(|err| err.into_inner())
          .screen().clone();
      screen.state_formatted()
  }
  ```
- `screen_lines` (:472-482): same pattern — clone `Screen`, drop the lock, then run
  `contents()` / line splitting on the clone.

The clone is a cheap grid memcpy; the O(rows×cols) string/escape formatting no longer
blocks the reader thread's `shared_parser` acquisition. The `MutexGuard` must be dropped
immediately after the `clone()` (end of the `let` statement), before any string/escape
formatting runs against the local clone.

**Out of scope:** the UI render path in `term-wm-ui-components/src/terminal.rs` also holds
`shared_parser` while reading cells each frame (the review's SEV-2 mentions it), but this
task is scoped to the PTY engine. The snapshot fix above addresses the engine-side holder;
the render-side lock is a separate follow-up.

### 4. Update tests (pty.rs)
- `sanitize_sets_multiplexer_safe_term` (:2164): assert `TERM` equals the cfg-expected
  value (via the helper from step 1) instead of hardcoding `screen-256color`.
- `spawned_child_receives_sanitized_environment` (:2253): assert `TERM={expected}`.
- `sanitize_sets_truecolor`, LC_CTYPE tests: unchanged.
