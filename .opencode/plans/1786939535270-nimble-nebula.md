# Plan: Add Support for Multiple Workspaces (Issue #110)

## Issue Summary

`term-wm` incorporates the `term-session` library and becomes its own client and server. A workspace = a channel namespace. The top panel gets a Herdr-style tabbed workspace bar. Workspaces are always available — you can create, switch, and manage them at runtime regardless of launch flags. Session persistence is a default-on compile flag that can be disabled.

## Current Architecture

- `term-wm` binary spawns **local PTYs** directly — no daemon
- `term-session` binary connects to a separate daemon process, uses `RemotePane`
- `term-session-server` exposes `run_gateway(gateway: ChannelName)` — the full IPC server
- `term-session-client` exposes `RemotePane` (implements `Pane` trait over IPC)
- `TerminalComponent` stores `Box<dyn Pane>` — agnostic to local vs remote
- `ChannelName` has `namespace/name` format — namespace IS the workspace

## Target Architecture

`term-wm` starts its own gateway daemon **in-process** on a background thread, then connects to it via IPC as a client. All terminals are managed as channels. Workspace = channel namespace. The entire WM view is whatever the active workspace presents — whether local or remote, the full WM experience is available.

Each binary has its own gateway (`term-wm/<user>/gateway` vs `term-session/<user>/gateway`), so `term-wm` and `term-session` don't directly communicate. That's fine — the `term-session` binary is the reference implementation and remains compatible, but workspaces are per-binary. Cross-device works by remote users connecting to the gateway (via SSH tunneling or TCP transport) and joining the same namespace — they see the full WM with workspace tabs.

```
┌─ term-wm process ─────────────────────────────────────┐
│                                                        │
│  ┌─ Gateway Thread ──────┐  ┌─ Main Thread ─────────┐ │
│  │ RpcIpcServer          │  │ WindowManager          │ │
│  │ ChannelStateHashMap   │←─│ RemotePane per window  │ │
│  │ Session per channel   │  │ TopPanel (window tabs  │ │
│  │ PTY I/O routing       │  │  or workspace view)    │ │
│  └───────────────────────┘  └────────────────────────┘ │
│                    ↑ IPC (local socket) ↓              │
└────────────────────────────────────────────────────────┘
```

## Shared Workspace Design

Multiple clients can join the same workspace. The UI is shared — every client renders the same view. The session server handles identity, lifecycle, and input routing.

### Identity

Each client identifies itself on `Attach` (`{ user, hostname, pid, ssh_ip }`). The daemon maps `conn_id → ClientInfo`. The connection itself carries the identity — no user tags needed in events or actions.

### Client Lifecycle (Event-Driven)

The daemon broadcasts client lifecycle events to all subscribers via a dedicated stream (same pattern as `OnPtyResized`):

- `ClientJoined { user, hostname }` — broadcast when a new client attaches to the channel
- `ClientLeft { user, hostname }` — broadcast when a client disconnects

Each client's WM renders these as notifications. No polling — muxio streaming handles delivery.

### Shared Input

Everyone has focus. Everyone can type. Input from all clients goes to the same shared PTY. The daemon routes input from each client's `StreamInput` channel to the shared session. Keystrokes interleave naturally — same model as tmux shared sessions.

### Action Attribution

The UI doesn't need to know which user clicked a button. Each client has its own IPC connection. When user B clicks "exit workspace":

1. Click event is local to user B's client
2. Client sends `DisconnectSelf` over its own connection (conn_id=4)
3. Daemon looks up conn_id=4 → user "B" → disconnects B
4. Daemon broadcasts `ClientLeft { user: "B" }` to remaining subscribers
5. User A's WM renders the notification

The connection carries the identity. Actions are scoped to the connection that sent them. No user field needed in action types.

### Per-User Actions

- `DisconnectSelf` — client closes its own connection (always allowed)
- `DisconnectClient { conn_id }` — admin-only, disconnect another user (new RPC, requires permission check)
- All other actions (workspace switch, window management) affect the shared state and are broadcast to all clients

### Notification Flow

```
Client A                    Daemon                    Client B
   |                          |                          |
   |--- Attach (user: "A") -->|                          |
   |                          |<-- Attach (user: "B") ---|
   |                          |                          |
   |<-- ClientJoined { B } ---|--- ClientJoined { B } -->| (to self too)
   |                          |                          |
   |                          |<-- DisconnectSelf -------| (B clicks exit)
   |<-- ClientLeft { B } -----|--- disconnect B ---------|
   |                          |                          |
```

## Compile Flags

Session persistence is compiled in by default via Cargo features. Users who want a minimal build can disable them.

```toml
[features]
default = ["session-persistence"]
session-persistence = ["dep:term-session-server", "dep:term-session-client"]
```

With `session-persistence` enabled (default):
- In-process gateway daemon starts automatically
- Workspaces are available at runtime
- Sessions persist across client disconnects
- Cross-device: remote users can join workspaces by connecting to the gateway (via SSH tunneling or TCP transport)

With `session-persistence` disabled (`--no-default-features`):
- No gateway, no IPC
- Workspaces still work as a logical grouping (local PTYs only)
- No session persistence, no cross-device

## Launch Modes

`term-wm` supports multiple launch configurations. Workspaces are always available — the flags control initial state and whether the session daemon runs.

### Default (no flags)

```
term-wm
term-wm -n 4
term-wm --run vim --run htop
```

Full window manager with workspaces. Starts in-process gateway daemon. All windows in workspace `"default"` initially. Create and switch workspaces at runtime via command palette or keyboard shortcuts. The entire WM view is whatever the active workspace presents.

- Workspaces always available
- In-process gateway daemon
- Full WM chrome: top panel (window tabs default, workspace view toggleable), bottom panel, FAB, command palette
- Backward compatible with existing usage
- Cross-device: remote users can join by connecting to the gateway

### Initial Workspace

```
term-wm --workspace dev
term-wm -w dev -n 3
term-wm --workspace prod --run "ssh server"
```

Same as default, but starts in the specified workspace. Creates the workspace if it doesn't exist. The full WM is available — toggle the top panel to workspace view to switch. Remote users connecting to the gateway see the same full WM experience for that workspace.

### Headless Session Client

```
term-wm --no-wm
term-wm --no-wm --workspace dev
term-wm --no-wm --channel dev/main
```

Runs without the window manager — just a session client. Connects to an existing gateway (local or remote) and runs a single terminal in a TUI. Useful for quick one-off sessions or scripting.

- No window manager, no TUI chrome
- Single terminal, full-screen
- Connects to an existing gateway (doesn't start one)

### Gateway Daemon

```
term-wm --daemon
```

Runs as a standalone session daemon (gateway). No window manager, no terminal UI. Accepts IPC connections from `term-wm` processes or clients. Manages channels, sessions, and PTY I/O routing.

- Headless daemon process
- IPC-accessible by multiple clients
- Sessions survive client disconnects
- Cross-device workspace sharing hub

### Mode Summary

| Configuration | Flags | Gateway | WM | Workspaces |
|---------------|-------|---------|-----|------------|
| Default | (none) | Yes (in-process) | Yes | Yes |
| Initial workspace | `--workspace <name>` | Yes (in-process) | Yes | Yes |
| Headless client | `--no-wm` | Connect to existing | No | N/A |
| Gateway daemon | `--daemon` | Yes (standalone) | No | N/A |

## Implementation Steps

### Step 1: Add compile flag for session persistence

**File:** `Cargo.toml` (root)

```toml
[features]
default = ["session-persistence"]
session-persistence = ["dep:term-session-server", "dep:term-session-client"]

[dependencies]
term-session-server = { path = "crates/term-session-server", optional = true }
term-session-client = { path = "crates/term-session-client", optional = true }
```

Remove `term-session-client` from `[dev-dependencies]` (it's now a regular optional dep).

In code, gate session-specific paths with `#[cfg(feature = "session-persistence")]`.

### Step 2: Add CLI flags

**File:** `src/main.rs` (line 30, `Cli` struct)

```rust
/// Initial workspace name (default: "default")
#[arg(short = 'w', long = "workspace", default_value = "default")]
workspace: String,

/// Run without window manager (headless session client mode)
#[arg(long = "no-wm")]
no_wm: bool,

/// Run as a standalone session daemon (gateway)
#[arg(long = "daemon", hide = true)]
daemon: bool,
```

Route to mode:
- `--daemon` → start gateway daemon and exit (no WM)
- `--no-wm` → call `run_headless_session(workspace, channel, cmd)` and exit
- Otherwise → start WM with workspace tabs (gateway starts automatically when `session-persistence` feature is enabled)

**Without `session-persistence`:** Workspaces still work as a logical grouping of local PTYs. No daemon, no IPC. The `workspace` field tracks which workspace each window belongs to. Create/switch workspaces via command palette — windows are shown/hidden based on active workspace.

### Step 4: Spawn terminals via session daemon

## Shared Workspaces

Multiple users can join the same workspace. The UI is shared — every client renders the same view.

### How it works

- Each client identifies itself on connect (user, hostname, pid)
- The connection carries the identity — no user tags in events or actions
- Everyone has focus, everyone can type (shared PTY input)
- Client lifecycle events (joined/left) are broadcast to all subscribers
- Disconnecting is per-connection — one user leaving doesn't affect others

### Joining a workspace

```bash
# Machine A starts a workspace
term-wm --workspace dev

# Machine B joins the same workspace (via SSH tunnel or TCP)
term-wm --workspace dev
```

Both users see the same workspace view. Input from either user goes to the shared terminals.

### Notifications

When a user joins or leaves, all remaining clients see a notification:
- "User B joined workspace dev"
- "User B left workspace dev"
```
