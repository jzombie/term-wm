# Fix: Focus Ring Stale Key After Last Window Close

## Root Cause

When the last window is closed, `remove_from_focus_ring` produces an empty order. `FocusRing::set_order([])` self-heals only if the new order is non-empty — with an empty order, `current` still holds the removed key. `select_fallback_focus` then cannot find a first element, so `focused_window()` returns a dangling key. All subsequent `direct_mode` reads via this stale key silently fail `is_some_and`, returning `false` by default, making the system appear unresponsive.

## Changes

### 1. `window_manager/focus.rs` — Fix `select_fallback_focus()`

Reset to `WindowKey::default()` when ring is empty so stale-key callers hit safe defaults:

```rust
pub(super) fn select_fallback_focus(&mut self) {
    if let Some(fallback) = self.focus.order().first().copied() {
        self.focus.set_current(fallback);
    } else {
        self.focus.set_current(WindowKey::default());
    }
}
```

This is the only change. `focus_add` preserves its contract (no unconditional `set_current`). `direct_mode()` already safely handles missing keys via `is_some_and`. No redundant `has_window` guard in runner.rs.
