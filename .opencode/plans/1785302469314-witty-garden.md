# Plan: Fix Terminal Bottom-Row Loss on Vertical Shrink & Bouncy Scrollbar

## Issue 1 — Bottom n rows deleted from visual buffer on vertical shrink

### Root Cause
vt100 `grid.set_size()` (0.16.2) calls `self.rows.resize(new_rows, ...)` at `grid.rs:81`, which **truncates rows from the end** — bottom N rows of the viewport are dropped without pushing them into scrollback. After a shrink, only the top rows of the old viewport remain visible.

### Fix: Pre-scroll in `Pty::resize()` via SU + CUU

**File:** `crates/term-wm-pty-engine/src/pty.rs` — `Pty::resize()` line 249

When `new_rows < self.pty_size.rows`, send two escape sequences **before** `set_size()`:

```rust
if new_rows < self.pty_size.rows {
    let delta = self.pty_size.rows - new_rows;
    // SU (Scroll Up): push top delta rows into scrollback, add delta empty rows at bottom
    // CUU (Cursor Up): move cursor up by delta to keep it anchored to its text line
    let seq = format!("\x1b[{delta}S\x1b[{delta}A");
    guard.process(seq.as_bytes());
}
guard.screen_mut().set_size(new_rows, new_cols);
```

**Why both sequences:**
- `\x1b[<delta>S` (SU) scrolls viewport content up by `delta` rows → top `delta` rows enter scrollback, `delta` blank rows appear at bottom
- `\x1b[<delta>A` (CUU) moves cursor up by `delta` rows → cursor tracks its original content line (SU does NOT move the cursor)
- `set_size(new_rows, ...)` truncates the `delta` blank rows from the bottom → bottom content preserved

**Edge case:** `scroll_region_active()` prevents scrollback push — rare for full-screen terminals, acceptable degradation.

- Update `TestPane::resize` (currently a no-op at `terminal.rs:1201`) to call `set_parser_size` and support `process()` calls
- Add test: write N lines, shrink viewport by K, verify line N is still at the bottom and line 0 moved to scrollback

## Issue 2 — Bouncy Scrollbar (Layout Thrashing)

### Root Cause
ScrollView retry loop (`scroll_view.rs:418-482`) oscillates when scrollbar visibility toggles: scrollbar appears → width shrinks by 1 → child re-renders → content height may change → scrollbar may disappear → retry repeats.

### Fix: Hysteresis with persistent state

**File:** `crates/term-wm-core/src/component_context.rs` — Add `last_needs_vertical: bool` and `last_needs_horizontal: bool` fields to `ScrollState`

**File:** `crates/term-wm-ui-components/src/scroll_view.rs` — `ScrollState` struct + `ScrollViewComponent::render()`

Use **deadband hysteresis** so scrollbar is harder to turn off than on:

```rust
// In ScrollState (long-lived, persists across render calls):
pub last_needs_vertical: bool,
pub last_needs_horizontal: bool,

// In render, when computing needs_vertical:
const HYSTERESIS_SLACK: usize = 2;
let needs_vertical = if state.last_needs_vertical {
    // Harder to turn OFF: must fit with extra slack
    content_h + HYSTERESIS_SLACK > inner_area.height as usize
} else {
    // Standard trigger to turn ON
    content_h > inner_area.height as usize
};
state.last_needs_vertical = needs_vertical;
```

This prevents the feedback loop: the scrollbar won't disappear until content is well within bounds, and won't reappear until content clearly exceeds bounds.

### Testing
Add test to `scroll_view.rs`: set content_height = viewport_height + 1 (triggers scrollbar ON), then reduce to viewport_height (should stay ON due to hysteresis).
