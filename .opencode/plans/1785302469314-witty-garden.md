# Plan: Fix Terminal Bottom-Row Loss on Vertical Shrink & Bouncy Scrollbar

## Issue 1 — Bottom n rows deleted from visual buffer on vertical shrink

### Root Cause
vt100 `grid.set_size()` (0.16.2) calls `self.rows.resize(new_rows, ...)` at `grid.rs:81`, which **truncates rows from the end** — the bottom N rows of the viewport are dropped without being pushed into scrollback.

### Fix: Pre-scroll in `Pty::resize()` guarded by scroll region check

We need to scroll the viewport up by `delta = old_rows - new_rows` before `set_size()` so the `resize` truncates empty rows (added by scrolling) instead of content. This requires `SU` (Scroll Up), but `SU` only pushes rows to scrollback when no custom DECSTBM margin is active — TUI apps (`vim`, `tmux`) set margins and would get corrupted.

**Approach:** Add a public `scroll_region_active()` method to vt100 `Screen` (1-line forwarding to existing `Grid::scroll_region_active()`), use via `[patch.crates-io]`. Then guard SU injection on this check:

```rust
// crates/term-wm-pty-engine/src/pty.rs — Pty::resize() line 249
if new_rows < self.pty_size.rows {
    let delta = self.pty_size.rows - new_rows;
    // Only pre-scroll if no custom DECSTBM margins are active.
    // SU within a custom scroll region would corrupt TUI app layouts
    // (vim, tmux, less, htop).
    if !guard.screen().scroll_region_active() {
        let seq = format!("\x1b[{delta}S\x1b[{delta}A");
        guard.process(seq.as_bytes());
    }
}
guard.screen_mut().set_size(new_rows, new_cols);
```

**Why both sequences:** `\x1b[<delta>S` (SU) scrolls content up by `delta` rows → top rows enter scrollback, blank rows appear at bottom. `\x1b[<delta>A` (CUU) moves cursor up by `delta` (SU does NOT move cursor). Then `set_size()` truncates blank rows, preserving bottom content.

**When custom margins are active:** `set_size()` is called directly (as today). Bottom rows may be lost, but the TUI app will receive SIGWINCH and redraw correctly — this is the standard terminal emulator behavior.

**No live render probes, no DECSTBM reset, no scratch buffers.**

| File | Change |
|------|--------|
| `Cargo.toml` | Add `[patch.crates-io]` section for vt100 fork |
| `crates/term-wm-pty-engine/src/pty.rs` | Pre-scroll via SU + CUU before `set_size()` on shrink, guarded by `scroll_region_active()` |
| `patches/vt100-0.16.2/src/screen.rs` | Add `pub fn scroll_region_active() -> bool` forwarding to `Grid` |

## Issue 2 — Bouncy Scrollbar (Layout Thrashing)

### Root Cause
`ScrollViewComponent::render()` starts every frame assuming `needs_vertical = false`, forcing pass 1 at width W and (if content overflows) pass 2 at W-1. This triggers **two child renders per frame**, and for children that reflow (markdown viewer), the W-1 render inflates content_h via extra wraps, preventing the scrollbar from ever turning off.

### Fix: Seed from persistent state (no probe renders)

**File:** `crates/term-wm-core/src/component_context.rs` — Add `last_needs_vertical: bool` and `last_needs_horizontal: bool` to `ScrollBounds`

**File:** `crates/term-wm-ui-components/src/scroll_view.rs` — Modify render loop:

Instead of speculative render probes (which trigger SIGWINCH on terminal children), base `needs_vertical` transitions entirely on **passive bounds comparison** using the actual rendered state from the current pass:

```rust
// Seed pass 1 with persistent state — avoids dual-resize per frame
let mut needs_vertical = state.last_needs_vertical;
let mut needs_horizontal = state.last_needs_horizontal;

loop {
    let inner_area = self.compute_layout(area, needs_vertical, needs_horizontal);
    // ... render child at inner_area ...
    // ... read content_w, content_h from state ...

    if needs_vertical {
        // Transition OFF only when content at W-1 fits strictly within viewport.
        // No probe render at full width — speculative renders would resize
        // terminal PTYs and flood the child with SIGWINCH.
        if content_h <= inner_area.height as usize {
            needs_vertical = false;
            // Re-render at full width W (no scrollbar gutter)
            let inner_area = self.compute_layout(area, false, needs_horizontal);
            continue;
        }
        // else: content still overflows at W-1, keep scrollbar ON — stable state
    } else {
        // Transition ON normally
        if content_h > inner_area.height as usize {
            needs_vertical = true;
            // Re-render at W-1 (reserve scrollbar gutter)
            let inner_area = self.compute_layout(area, true, needs_horizontal);
            continue;
        }
    }

    // ... determine retry_vertical / retry_horizontal / offset_changed ...
    break;
}

state.last_needs_vertical = needs_vertical;
state.last_needs_horizontal = needs_horizontal;
```

**Key insight:** No speculative renders at unconstrained width. The OFF-transition uses `content_h <= inner_area.height` where `inner_area` is at W-1. For overflowing content, this is inherently conservative:
- If content genuinely fits (no overflow), `content_h <= inner_area.height` is true → scrollbar turns OFF
- If content overflows at W-1, scrollbar stays ON → no oscillation
- If content is at the boundary where W-1 overflows but W doesn't (reflowing children), the scrollbar stays ON until the user explicitly scrolls to make content fit — this is a deliberate trade-off to avoid SIGWINCH flooding

| `crates/term-wm-ui-components/src/scroll_view.rs` | Seed pass-1 from persistent state; OFF-transition only when content at W-1 fits strictly |
