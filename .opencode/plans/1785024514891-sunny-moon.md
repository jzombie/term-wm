# Fix: Remove CHROME_BUTTON_FLOAT_OFFSET from button_x_pos

## Problem

`button_x_pos` applies `CHROME_BUTTON_FLOAT_OFFSET = 1` internally — subtracting 1 for
tiled windows, adding 1 for floating. This shifts the Close button 1 column left of
the spec position, producing a **2-column inset** instead of the mandated **1-column
inset**.

Trace for 30-wide window:
- `outer_right = 29` (30 - EDGE_INDEX_ADJUST)
- `header_right = 28` (29 - RIGHT_BORDER_WIDTH)
- `bx = 28 - CHROME_BUTTON_INSET_RIGHT(1) - HEADER_BUTTON_GAP(2) * 0 = 27`
- non-floating: `27 - CHROME_BUTTON_FLOAT_OFFSET(1) = 26` ← **off by 1**
- Result: X at 26, border at 29 → 2 empty cols (27, 28) → **2-column inset**

The float offset was a historical visual tweak compensating for the old buggy formula
(where `HEADER_BUTTON_GAP` served double-duty as both inset and inter-button spacing).
With the correct formula, it breaks the spec geometry.

## Changes

### 1. `crates/term-wm-core/src/chrome/metrics.rs`
- Remove `floating` parameter from `button_x_pos`
- Remove `CHROME_BUTTON_FLOAT_OFFSET` branch
- Remove unused import of `CHROME_BUTTON_FLOAT_OFFSET`
- Base formula becomes: `header_right - CHROME_BUTTON_INSET_RIGHT - HEADER_BUTTON_GAP * i`
- Result: X at 27, ▢ at 25, _ at 23 for 30-wide window ✓

### 2. `crates/term-wm-console/src/draw_plan_renderer.rs`
- Update both callsites (render + hitbox register) to drop the `floating` arg
- Remove the `floating` variable from the loop body (no longer needed)

### 3. `crates/term-wm-core/src/window/window_manager/mod.rs`
- Update both D-button test callsites to drop the `floating` arg
- Update the comment
