# De-flake `stop_gateway_daemon_e2e_from_app_actions`

## Root cause (confirmed by code trace)

The test binary has two INDEPENDENT lock systems:

1. `#[serial(runtime_config)]` (serial_test) guarding tests that mutate the
   process-global `term_wm_config::runtime` CONFIG (`Mutex<RuntimeConfig>`).
2. An ad-hoc `env_lock()` std Mutex guarding env-var mutations.

`stop_gateway_daemon_e2e_from_app_actions` (src/main.rs:1418) holds ONLY
`env_lock()`. It is NOT in the `runtime_config` serial group. Meanwhile these
tests install `session_persistence: false` into the process-global config for
their duration, serialized against each other but NOT against the e2e test:

- `handle_custom_action_returns_false_when_runtime_disabled` (:1601)
- `run_project_task_works_without_persistence` (:1670)

`App::handle_custom_action` (src/main.rs:885) starts with
`if !session_persistence_enabled() { return false; }`. When a disabled-config
window overlaps the e2e test, `OpenStopGatewayConfirm` / `StopGatewayDaemon`
return false instantly and the e2e asserts (`assert!(opened)`,
`assert!(app.handle_custom_action(&TermWmAction::StopGatewayDaemon))`) fail.
Matches all evidence: failure is FAST (CI summary shows the whole bin suite at
0.23s; every probe/timeout path would take seconds), intermittent (pure thread
interleaving), and passes in isolation.

## Fix

### 1. Consolidate process-global serialization into ONE serial_test key

Replace BOTH mechanisms with a single `#[serial(process_global_state)]` key for
every src/main.rs test that mutates or pins process-global state (env vars,
`runtime::init`, global panic hook). This removes the split-lock hazard entirely:
no test can observe another's half-applied global state.

Concretely, annotate with `#[serial(process_global_state)]` (replacing
`#[serial(runtime_config)]` and/or the `env_lock()` guard):

- `stop_gateway_daemon_e2e_from_app_actions` (async, multi_thread; drop the
  `env_lock()` guard and its `#[allow(clippy::await_holding_lock)]`; serial_test
  4.x supports async fns natively)
- `handle_custom_action_consumes_stop_gateway_actions` (sync variant)
- `runtime_config_enabled_without_flag_or_env`,
  `runtime_config_flag_disables_persistence`, and the other two
  `runtime_config_for` tests (drop `env_lock()`)
- `help_shows_resolved_gateway` (drops TERM_WM_GATEWAY/TERM_WM_ENV)
- `handle_custom_action_returns_false_when_runtime_disabled`,
  `run_project_task_works_without_persistence`
- `handle_custom_action_consumes_workspace_actions`, the switch_workspace pair,
  `toggle_workspace_follow_toggles_flag`, and any other `runtime::init` caller

Then delete `fn env_lock()` once it has no remaining users. Keep unique-socket
naming (`testgw-stop-{id}`, pid-suffixed variants) unchanged; sockets were never
the shared state being locked.

### 2. Chained, RAII-managed panic hook (src/main.rs)

Review findings adopted: (a) `/tmp/twm-panic.log` breaks Windows and leaks across
runs; (b) the custom hook suppressed default stderr panic output because it never
forwarded to the previous hook.

Toolchain fact (verified): rustc 1.98 `std::panic::take_hook()` returns a
NON-cloneable `Box<dyn Fn(&PanicHookInfo)>`, so the review snippet's
`prev_hook.clone()` does not compile. Adaptation: park the taken `Box` behind a
shared `Arc<Mutex<Option<_>>>`; both the replacement hook (to chain) and the
RAII guard (to restore) hold clones of that handle. Types stay compatible with
`set_hook`/`take_hook`.

```rust
/// A panic hook as accepted by `std::panic::set_hook`.
#[cfg(feature = "session-persistence")]
type PanicHook = Box<dyn Fn(&std::panic::PanicHookInfo<'_>) + Send + Sync + 'static>;

/// Shared slot holding the previously installed panic hook while a test's
/// diagnostic hook is active: the replacement hook chains into it, and the
/// RAII guard takes it back out to restore on scope exit (pass, fail, or
/// unwind).
#[cfg(feature = "session-persistence")]
type ChainedHookSlot = std::sync::Arc<std::sync::Mutex<Option<PanicHook>>>;

/// RAII guard: restores the chained panic hook in `Drop`, so mid-test
/// assertion panics can never leave the diagnostic hook installed for later
/// tests. `install_diagnostic_panic_hook` returns this; no trailing restore
/// call is needed.
#[cfg(feature = "session-persistence")]
struct PanicHookGuard(Option<ChainedHookSlot>);

#[cfg(feature = "session-persistence")]
impl Drop for PanicHookGuard {
    fn drop(&mut self) {
        if let Some(slot) = self.0.take() {
            // Poison tolerance: a panic inside the forwarded hook poisons
            // this mutex; restoration must still happen, so recover the
            // inner value regardless of the poison flag.
            let mut guard = slot.lock().unwrap_or_else(|poison| poison.into_inner());
            if let Some(prev) = guard.take() {
                std::panic::set_hook(prev);
            }
        }
    }
}

/// Install the diagnostic panic hook (logs to a per-process temp file, then
/// forwards to the previously registered hook) and return the RAII guard.
#[cfg(feature = "session-persistence")]
fn install_diagnostic_panic_hook() -> PanicHookGuard {
    let slot: ChainedHookSlot =
        std::sync::Arc::new(std::sync::Mutex::new(Some(std::panic::take_hook())));
    let chained = std::sync::Arc::clone(&slot);
    std::panic::set_hook(Box::new(move |info| {
        // Per-process filename: concurrent test binaries during
        // `cargo test --workspace` never contend on one file, and stale
        // cross-UID files cannot break opens of a fresh name.
        let log_path =
            std::env::temp_dir().join(format!("twm-panic-{}.log", std::process::id()));
        if let Ok(mut f) = std::fs::OpenOptions::new()
            .create(true)
            .append(true)
            .open(log_path)
        {
            let _ = writeln!(f, "PANIC: {info}");
            let _ = writeln!(f, "{:?}", std::backtrace::Backtrace::force_capture());
        }
        // Forward to the previously registered hook so default stderr panic
        // output is preserved while our hook is installed. The slot lock is
        // held across the call by necessity (PanicHook is not Clone): the
        // only other contenders are sibling hook invocations and Drop, which
        // tolerates poisoning above, and nothing re-enters this mutex, so no
        // deadlock is possible.
        let guard = chained.lock().unwrap_or_else(|poison| poison.into_inner());
        if let Some(prev) = guard.as_ref() {
            prev(info);
        }
    }));
    PanicHookGuard(Some(slot))
}
```

Note on syntax: let-chains are stable on this repository's toolchain
(rustc >= 1.88, edition 2024; already used elsewhere in the crate tree), but
the two new sites use plain nested `if let` anyway per review preference.

Call sites (`handle_custom_action_consumes_stop_gateway_actions`,
`switch_workspace_follow_enabled_uses_all_viewers_scope`) become:

```rust
let _panic_guard = install_diagnostic_panic_hook();
let mut app = test_app();
// ... body ... (no trailing restore call)
```

The guard binds for the whole lexical scope, so restoration happens in `Drop`
on pass, fail, or unwind.

to the failure messages of the two `handle_custom_action` asserts so any future
