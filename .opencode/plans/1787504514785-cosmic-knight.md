# Command Palette: consistent default selection + "Switch to Window:" relabel

## Problem

1. Typing "new" in the Command Palette sometimes defaults to "New Workspace" instead
   of "New Terminal". Root cause: `rerank` / `rerank_with_registry` CLAMP the previous
   selection index into the newly filtered list instead of resetting it. A stale index
   (from arrow-key browsing or a prior click) lands on the second match once "new"
   filters the list to 2 items ("New Terminal", "New Workspace").
2. Window switcher entries read "Switch to: <title>"; user wants "Switch to Window:".
   Per docs/UI-STYLE.md, the canonical `TermWmAction::Display` string must be updated
   in lockstep ("Focus Window" -> "Switch to Window").

Item stays named "New Terminal" (user confirmed; no rename).

## Changes

### 1. Reset selection when the query changes (crates/term-wm-ui-components/src/command_palette.rs)

Single choke point rather than per-handler resets, so EVERY mutation path is covered
(char input, Backspace, ClearCommandPaletteQuery, programmatic query sets):

- Add field `last_ranked_query: String` (init `String::new()` in `new()` at :128).
- In BOTH `rerank` (:250) and `rerank_with_registry` (:398), AFTER computing
  `filtered_items` and BEFORE the clamp block (:332/:486):

```rust
// A changed query must land on the best match, never carry a stale index
// from the previously ranked list.
if self.query != self.last_ranked_query {
    self.selected = 0;
}
self.last_ranked_query = self.query.clone();
```

- Existing behavior preserved otherwise: same-query data refreshes (palette tick,
  refresh_palette_items) keep the clamp-only path so live refresh does not yank
  keyboard navigation; disabled-skip still finds the first enabled row.
- Note: `rerank_with_registry` is the live path (wm_command_palette.rs:185); `rerank`
  is kept in sync because both exist publicly.

### 2. Relabel window switcher (crates/term-wm-core)

- src/window/window_manager/command_palette.rs:475:
  `format!("Switch to: {}", ...)` -> `format!("Switch to Window: {}", ...)`.
- actions.rs:377 Display: `TermWmAction::FocusWindow(_) => "Focus Window"` ->
  `"Switch to Window"` (payload is an opaque WindowKey, so Display carries no title;
  precedent: SwitchWorkspace interpolates only because its payload IS a name).
- Update the two test prefix matchers in window_manager/command_palette.rs (:858,
  :894): `starts_with("Switch to: ")` -> `starts_with("Switch to Window: ")`.
- Update the Display test expectation in actions.rs (~:517): "Focus Window" ->
  "Switch to Window".
- docs/UI-STYLE.md: add `` `Switch to Window: <title>` `` to the Chicago title-case
  examples list (next to the workspace example) per the user's note about keeping the
  doc aligned.

### 3. Tests for the selection reset (command_palette.rs tests module)

Add a test mirroring the existing rerank test setup style (see tests near :960-1103
that build `FuzzyMatch`/`MruRanker` and call `rerank_with_registry`):
- Seed items where two entries match "new" ("New Terminal" first, "New Workspace"
  second), set `selected = 1`, set `query = "new"`, `query_dirty = true`, call
  `rerank_with_registry`; assert `selected == 0` and the selected display name is
  "New Terminal".
- Same-query re-rank keeps a moved selection (set selected=1, re-rank with identical
  query) to pin the clamp-not-reset behavior for live refreshes.

## Code-review amendments

### SEV-1 (ReportWmStats type mismatch): REJECTED, no change

Verified against current HEAD and rebutted with evidence:
- The protocol defines `ReportWmStats::Input = (u32, u32)`
  (crates/term-session-muxio-service-definitions/src/methods.rs:685); the wire struct
  carries only `windows`/`tasks_running`. There is NO channel field.
- All three cited call sites (tests/integration_session.rs:1989 uses the fixture's
  `(u32, u32)` stats tuple; :2116 `(3u32, 2u32)`; :2134 `(9u32, 9u32)`) match that
  Input type exactly.
- `cargo test -p term-wm --test integration_session --no-run` compiles cleanly.

Applying the directive (3-tuples) would introduce the very E0308 it warns about.
No action.

### SEV-2 (undrained stderr pipe): ACCEPTED as hardening

tests/integration_session.rs `launcher_exits_immediately_on_nesting_fatal`
(:2170-2234) polls `try_wait()` without draining the piped stderr. Practically bounded
today (the child writes one short FATAL line before exit, far below the ~64KB pipe
buffer, and the 10s timeout kills + fails rather than hanging), but draining
concurrently is strictly more robust and costs nothing. Amend the test to:

```rust
let (tx, rx) = std::sync::mpsc::channel();
std::thread::spawn(move || {
    let out = child.wait_with_output();
    let _ = tx.send(out);
});
let out = rx
    .recv_timeout(Duration::from_secs(10))
    .expect("term-wm did not exit within 10s — likely retrying instead of exiting immediately");
let elapsed = start.elapsed();
let stderr = String::from_utf8_lossy(&out.stderr);
```

Keep the existing assertions (non-zero status, FATAL diagnostic mentions term-wm,
elapsed < 5s). The `kill()` path disappears because `recv_timeout` owns the timeout;
on timeout the child leaks by design of the harness (same as today's post-panic
state) — acceptable for an integration test.
