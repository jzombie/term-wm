# Plan: Single-click dismiss command palette + activate background window

## Goal

When the command palette is open and the user clicks **outside the palette bounds**, the palette should:
1. Dismiss immediately
2. The **same click** should activate the window under the cursor (focus + bring to front)

Clicking **inside the palette** (on items or background) must never propagate to windows below.

## Background

Currently, the command palette uses a **blind event barrier** in `runner.rs:438-508` — when the palette is visible, ALL events are consumed, and the runner returns early. Clicking outside the palette returns `CloseMenu` (palette dismissed), but the mouse event never reaches the window layer, so the user must click again to activate a window.

This is overly conservative — safe but wasteful. The existing `DialogOverlayComponent::handle_click_outside` already does correct spatial hit-testing (bounds check vs click position). We just need to let the event continue to the normal dispatch for outside-clicks.

## Spatial Hit-Testing Safety

The three click regions and their handling:

| Region | Detection | Current behavior | Desired behavior |
|--------|-----------|-----------------|-----------------|
| **Outside palette** | `handle_click_outside` returns true | → `CloseMenu`, barrier returns early | → Close palette, **continue event to window activation** |
| **Inside palette (item row)** | `MenuComponent` returns `MenuSelect` | → Action dispatched, barrier returns early | Same (safe) |
| **Inside palette (background)** | `MenuComponent` returns `Ignored` → `handle_command_palette_event` returns `None` | → Barrier stays, palette remains open | Same (safe) |

The key insight: outside-clicks are already spatially gated by `DialogOverlayComponent::handle_click_outside` (`dialog_overlay.rs:113-140`). We don't need to touch the overlay code — we just need to change how the runner handles the `CloseMenu` result for mouse events.

## Changes Required

### 1. `runner.rs` — Modify the command palette event barrier

File: `crates/term-wm-core/src/runner.rs`, lines 438-509.

Currently the barrier always returns early after `handle_command_palette_event`. We need it to **not return early** when:
- The action is `CloseMenu` (outside-click dismissal)
- AND the event is a `Mouse` event

In this case, after closing the palette, the event should continue to the normal mouse dispatch path (specifically `handle_mouse_focus_click` at line 551, which hit-tests and activates the window under the cursor, and then `handle_focused_app_event` via `dispatch_mouse` for the full dispatch).

**Specific change:**

```rust
// OLD (simplified):
if app.wm().command_palette_visible() {
    if let Some(action) = app.wm().handle_command_palette_event(&evt) {
        match action { TermWmAction::CloseMenu => {} /* ... */ }
    }
    update_selection_snapshot(app);
    return flush_state_changes(app, driver, ControlFlow::Continue, false, None);
}

// NEW:
if app.wm().command_palette_visible() {
    let mut close_menu_outside_click = false;
    if let Some(action) = app.wm().handle_command_palette_event(&evt) {
        match action {
            TermWmAction::CloseMenu => {
                close_menu_outside_click = matches!(&evt, Event::Mouse(_));
            }
            // ... all other actions handled as before, then return early ...
        }
        if !close_menu_outside_click {
            // Non-CloseMenu actions, or CloseMenu from keyboard → return early as before
            // ...focus routing for keys...
            update_selection_snapshot(app);
            return flush_state_changes(app, driver, ControlFlow::Continue, false, None);
        }
    } else {
        // No action → keep barrier
        // ...focus routing for keys...
        update_selection_snapshot(app);
        return flush_state_changes(app, driver, ControlFlow::Continue, false, None);
    }
    // close_menu_outside_click=true: fall through to normal mouse dispatch
    // handle_mouse_focus_click at line 551 will activate the window under cursor
    // handle_focused_app_event at line 577 routes the mouse through dispatch_mouse
}
```

The event already passes through `handle_mouse_focus_click` (line 551) and `handle_focused_app_event` (line 577) on the normal code path below the barrier. No changes needed there.

### 2. No changes to overlay components

- `WmCommandPaletteComponent` (`wm_command_palette.rs`) — already returns `Action(CloseMenu)` for outside-clicks
- `DialogOverlayComponent::handle_click_outside` (`dialog_overlay.rs`) — already does correct spatial bounds check
- `MenuComponent` (`menu.rs`) — already returns `Ignored` for background clicks inside palette (safe)
- `handle_command_palette_event` (`overlays.rs`) — already closes palette and returns `Some(CloseMenu)`
