# Plan: Visibility-Filtered Geometry (No Tree Mutation)

## Problem
Previous approach mutated the layout tree on minimize (`detach_from_tiling_layout` removed windows, `clear_leaf` replaced Leaf with Void) and then tried to restore using fragile path-memory (`TreePath`). This caused:
- Windows getting lost when tree collapsed then restored
- Layout drift on maximize/unmaximize
- Infinite nesting via path restoration in collapsing trees

## Solution: Visibility-Filtered Geometry
Windows NEVER leave the layout tree. Minimize just changes `WindowState::Iconic`. The geometry pass skips hidden (Iconic) windows, reallocating their space to visible siblings.

### Principle
- **Minimize**: sets `WindowState::Iconic` — no tree mutation
- **Maximize**: viewport overlay (`maximized_window`) + full-area `floating_rect` — no tree mutation
- **`detach_from_tiling_layout`**: NO-OP (was previously removing windows)
- **`reattach_to_tiling_layout`**: NO-OP (was previously re-inserting windows)
- **`register_managed_layout`**: uses topology keys (ALL non-floating non-unmapped windows) for `sync`, visible keys (only Mapped) for geometry

### Why This Works
The `TilingLayout::sync` function in the codebase already synchronizes the layout tree with a set of keys. By passing ALL windows (including Iconic) as topology keys, the tree stays intact. Only the geometry pass skips hidden windows.

## Step 3: Update `register_managed_layout` — Two Key Sets

**File:** `crates/term-wm-core/src/window/window_manager/layout.rs`

Current approach builds `active_keys` from tree regions + floating windows, then uses that for `z_order` and focus. Problem: the same set is used for both tree sync and rendering.

New approach: decouple topology keys from visibility keys.

After the existing code that builds `active_keys` from regions + floating windows (around line 486), add topology sync logic:

```rust
// ── Tree topology: ALL managed windows (including minimized) ──
// This keeps the layout tree stable — windows are never removed
// from the tree on minimize, only their region allocation changes.
let topology_keys: Vec<WindowKey> = self
    .windows
    .iter()
    .filter(|(_, w)| !w.is_floating() && w.state() != WindowState::Unmapped)
    .map(|(k, _)| k)
    .collect();

if let Some(ref mut layout) = self.managed_layout {
    layout.sync(&topology_keys);
}
```

Note: Check if `TilingLayout` has a `sync` method. If not, the existing `layout.regions()` call (which calls `layout_rects` on the root) already works without removing windows from the tree — it just computes geometry from whatever the tree contains. Since we no longer call `remove_window`, the tree stays intact and no sync is needed.

Actually, the key insight is: the tree is NEVER mutated by minimize anymore. So there's nothing to "sync" — the tree always has all windows. The `regions()` call just computes geometry. So we DON'T need a sync function.

The real change is: in the loop that processes layout tree regions, don't skip Iconic windows entirely — instead, set their region to zero (or skip them). But they MUST stay in the tree.

Let me re-examine the existing loop:

```rust
for (key, rect) in &regions {
    if self.window(*key).is_none() { continue; }
    if self.is_window_floating(*key) { continue; }
    if self.window_state(*key) == Some(WindowState::Iconic)
        || self.window_state(*key) == Some(WindowState::Unmapped)
    { continue; }
    self.regions.set(*key, *rect);
    active_keys.push(*key);
}
```

This already skips Iconic windows for regions and active_keys. The window IS in the layout tree (tree unchanged), but it gets no region and no active_key. This is correct for visibility.

BUT — the `active_keys` is used to rebuild `z_order`:
```rust
self.z_order.retain(|key| active_keys.contains(key));
```

If Iconic windows are not in `active_keys`, they get removed from `z_order`. This is fine — Iconic windows shouldn't be in z_order.

When the window is restored to Mapped, the geometry pass WILL include it because `window_state(*key) == Mapped` passes the filter. The window gets back into `active_keys`, z_order, etc.

So actually, the existing code ALREADY works correctly for visibility filtering! The only change needed is to NOT call `detach_from_tiling_layout` (which was removing windows from the tree). The rest of the pipeline handles it correctly.

## Step 4: Update `transition_window` — Minimize SKIP `detach_from_tiling_layout`

**File:** `crates/term-wm-core/src/window/window_manager/mod.rs`

The `Mapped → Iconic` transition calls `self.detach_from_tiling_layout(key)` at line ~509. Since `detach` is now a no-op, this doesn't need changing — the function will just do nothing.

BUT: the `Managed → Mapped` transition at line ~511 needs to NOT try to reattach (since the window is already in the tree). The current code checks `is_window_floating` and either assigns a cascading rect or calls `reattach_to_tiling_layout`. With visibility-filtered geometry, neither is needed — the window is already in the tree.

New code for Iconic→Mapped:
```rust
(WindowState::Iconic, WindowState::Mapped) => {
    if !self.z_order.contains(&key) { self.z_order.push(key); }
    if !self.managed_draw_order.contains(&key) { self.managed_draw_order.push(key); }
    // Window never left the tree — it's already in the layout tree.
    // The next register_managed_layout pass will compute its region
    // and add it to active_keys now that state is Mapped.
    self.focus_add(key);
    self.bring_to_front_key(key);
}
```
