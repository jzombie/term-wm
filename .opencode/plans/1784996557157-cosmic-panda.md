# Plan: Fix Direct Mode Repeat Key Suppression

## Bug
At `crates/term-wm-core/src/runner.rs:511`, the direct-mode key forwarding guard only allows `KeyKind::Press`:
```rust
&& key.kind == KeyKind::Press
```
This drops all `KeyKind::Repeat` events, so holding a key in direct mode (e.g., navigating in a TUI editor like vim) only registers a single keystroke.

## Root Cause
The guard was written when `KeyboardNormalizer` filtered repeats on Windows. After removing that filter (`72e1bba`), repeat events now reach the runner but are blocked by this stale `Press`-only check. There is no Windows-specific rationale for the runner-level filter — the platform issue was entirely in the normalizer.

## Fix

### 1. Update direct mode guard (`runner.rs:511`)
```rust
// Before:
&& key.kind == KeyKind::Press
// After:
&& matches!(key.kind, KeyKind::Press | KeyKind::Repeat)
```

The other two `key.kind == KeyKind::Press` guards at line 397 (command palette toggle) and line 550 (quit keybinding) are intentionally `Press`-only — these are UI actions where repeat would be incorrect.

### 2. Verify downstream safety (already confirmed)
- `to_pty_bytes()` at `events.rs:28-63` does NOT read `KeyKind` — it only uses `code` and `modifiers`. Repeat events produce identical byte sequences to Press events.
- `handle_focused_app_event()` does NOT filter on `KeyKind` — it dispatches all events as-is.
- No other filtering on `KeyKind::Repeat` exists in the runner or dispatch chain.

### 3. Add test for direct-mode Repeat forwarding
Add a test in `runner.rs` that sets direct_mode, sends a `KeyKind::Repeat` event, and asserts it routes through `handle_focused_app_event`.
