# Fix: Arrow Keys Blocked in Embedded Man Pages / git log

## Root Cause

Two independent problems:

1. **Keyboard arrow keys intercepted**: `ScrollViewComponent` in `ScrollKeyMode::Full` intercepts bare Up/Down (bound to `ScrollUp`/`ScrollDown`) for native scrollbar. Arrow keys must **always** be forwarded to the PTY child — standard terminal behavior.

2. **No passive state tracker for PTY byte stream**: Mouse scroll routing relies on ad-hoc `direct_mode` flag and `alternate_screen()` calls through vt100 parser. These lack a unified deterministic state machine to detect alternate screen, mouse tracking, or custom margins.

## Design

### Input Routing Table

| Input | Routing |
|-------|---------|
| Keyboard arrow keys (Up/Down/Left/Right) | Always → PTY child process (never intercepted) |
| Keyboard PageUp/PageDown/Home/End | ScrollViewComponent (native scrollbar) |
| Keyboard Shift+Up/Down | Native scrollback navigation (modifier-based) |
| Mouse scroll wheel | Query `Pane::requires_app_routing()` → PTY or native scrollbar |

### PtyStateTracker — Lock-Free Atomic State Machine

A `vte::Perform` implementor that runs on the **reader thread** (same thread that feeds bytes into vt100). State booleans are `AtomicBool` / `AtomicU8` so the main thread can read them without locks.

**Tracked states (atomic):**
- `is_alt_screen_active: AtomicBool` — set by `\e[?1049h` / `\e[?1047h` / `\e[?47h`
- `mouse_tracking_mode: AtomicU8` — decoded from DECSET 1000/1002/1003 (0=None, 1=X11Normal, 2=CellMotion, 3=AllMotion)
- `is_sgr_mouse_active: AtomicBool` — set by `\e[?1006h`
- `is_alt_scroll_mode_active: AtomicBool` — set by `\e[?1007h`
- `has_custom_margins: AtomicBool` — set by `DECSTBM (\e[r)` when margins ≠ full height
- `terminal_height: AtomicU16` — updated on resize from main thread

**Decision (read from main thread via `Ordering::Acquire`):**
`requires_app_routing() = is_alt_screen_active || mouse_tracking_mode != None || has_custom_margins`

### 3. New: `crates/term-wm-pty-engine/src/pty_state_tracker.rs`

```rust
pub struct PtyStateTracker {
    is_alt_screen_active: AtomicBool,
    mouse_tracking_mode: AtomicU8,  // 0=None, 1=X11Normal, 2=CellMotion, 3=AllMotion
    is_sgr_mouse_active: AtomicBool,
    is_alt_scroll_mode_active: AtomicBool,
    has_custom_margins: AtomicBool,
    terminal_height: AtomicU16,
    // Non-atomic: mutated only on reader thread via &mut self
    vte_parser: RefCell<vte::Parser>,
}

impl PtyStateTracker {
    pub fn new(terminal_height: u16) -> Self;
    pub fn requires_app_routing(&self) -> bool;  // reads atomics (Ordering::Acquire)
    pub fn resize(&self, height: u16);           // writes terminal_height atomically

    // Called on reader thread via vte::Perform:
    fn set_alt_screen(&self, active: bool);
    fn set_mouse_tracking(&self, mode: MouseTrackingMode);
    // ... etc

    /// Feed bytes through the vte parser. Called on reader thread.
    pub fn feed_bytes(&mut self, bytes: &[u8]) {
        self.vte_parser.borrow_mut().advance_bytes(self, bytes);
    }
}
```

`vte::Parser` stored in a `RefCell` because `vte::Perform` takes `&mut self` but `feed_bytes` is called from the reader thread where we have `&mut self`.

DECSTBM evaluation: `top > 1 || bottom < terminal_height` → `has_custom_margins = true`.

## Concurrency Model

```
Reader Thread                                Main Thread
─────────────                                ───────────
reader.read(&mut buf)                        event loop:
  → tracker.feed_bytes(&buf[..n])              → mouse scroll event
    (vte::Perform updates atomics)               → comp.handle_events()
  → shared_parser.lock().process()                → pane.requires_app_routing()
                                                     (reads atomics, no lock)
```

- **Tracker mutated only on reader thread** — same thread as bytes, synchronous with read
- **Main thread reads atomics** — `Ordering::Acquire`, no locks, no contention
- **No channel** — bytes are not copied across threads for state tracking
- **No heap allocation per read** — tracker processes the existing `buf[..n]` slice in-place
- **No batch dropping** — every byte is processed, no data loss
- Same pattern as `shared_parser` (vt100) — both live on reader thread
