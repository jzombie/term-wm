# Copy selections: wrap-aware line joining

Status: planned (not implemented, not built)

Owner: jeremy
Date: 2026-08-10

## Problem

Selecting a soft-wrapped line in a terminal pane (e.g. a long `git branch`
line that visually wraps across multiple rows) and copying it produces a
string with an inserted `\n` at each visual wrap point, corrupting the
original continuous text.

## Root cause

`TerminalComponent::selection_text_for_range` in
`crates/term-wm-ui-components/src/terminal.rs` (lines ~937-968) is the single
place terminal selections are converted to copied text. It iterates the
selected rows and unconditionally inserts `\n` between every pair of rows:

```rust
for absolute_row in vt100_start_row..=vt100_end_row {
    // ... pagination via guard.screen.set_scrollback(offset) ...
    result.push_str(&line);
    if absolute_row < vt100_end_row {
        result.push('\n');   // always inserts, ignores soft-wraps
    }
}
```

The emulator already tracks the distinction between a soft wrap and a real
newline:

- `term-wm-vt100` fork exposes `Screen::row_wrapped(row)` (fork
  `src/screen.rs:552`): returns true when the given *visible* row's text
  wraps onto the next row.
- The fork's own serialization (`write_contents` in fork `src/grid.rs:666-674`)
  suppresses the newline after a wrapped row — that is the behavior we mirror.

Note on semantics: `row.wrapped() == true` means "this row's text continues
onto the next row" (the wrap-source row), so `!row_wrapped(viewport_row)`
decides whether to push a `\n` after the current row.

## Decision: join with nothing

Soft-wrapped fragments are concatenated directly with no separator. This is
the choice made with the user; it matches every mainstream terminal (kitty,
WezTerm, Windows Terminal, iTerm2) and is correct for long identifiers (e.g.
a wrapped branch name rejoins byte-for-byte).

Explicitly NOT stripping all newlines: genuine multi-line output must keep its
real newlines. The wrap flag is what distinguishes the two cases.

## Change

### Core fix — `crates/term-wm-ui-components/src/terminal.rs`

In `selection_text_for_range`, only push `\n` when the current visible row is
not soft-wrapped:

```rust
if absolute_row < vt100_end_row && !guard.screen.row_wrapped(viewport_row) {
    result.push('\n');
}
```

`row_wrapped` is queried per-visible-row *after* the existing
`set_scrollback()` pagination for that row, so it stays correct for both
viewport and scrollback selections. No config flag is introduced (join with
nothing is unconditional).

### Tests — `crates/term-wm-ui-components/src/terminal.rs`

Reuse the existing `make_term_with_content` helper / `TestPane`:

1. `selection_text_wrapped_long_line_is_continuous` — width 20, a 50-char
   unbroken byte stream → selection returns one continuous string with no `\n`.
2. `selection_text_wrapped_line_then_real_newline_keeps_break` — wrapped
   50-char line followed by `\r\n` + `second` → joins inside the wrap,
   preserves `\n` at the real break (`a*50\nsecond`).
3. `selection_text_wrapped_rows_in_scrollback` — small `max_sb` so wrapped
   lines land in scrollback; verify paginated extraction joins correctly.
4. `selection_text_wrapped_partial_selection_mid_continuation` — selection
   that ends mid-wrap-row stays continuous up to the end column.

Existing tests (`selection_text_multi_line_crlf`, `selection_text_full_row`,
`selection_text_in_scrollback_with_small_max_sb`) use unwrapped short lines
and must pass unchanged.

## Open decision point: scope beyond the terminal

`TerminalComponent` is the only selection source with a true soft-wrap flag.
The text-rendering components (`text_renderer.rs` `selection_text`, used by
markdown_viewer / scroll_view system panels) wrap reflowed UI text at word
boundaries and carry no wrap flag; joining those would heuristically collapse
legitimate line breaks. This plan keeps them out of scope; can be revisited as
a follow-up if the behavior is wanted there.
