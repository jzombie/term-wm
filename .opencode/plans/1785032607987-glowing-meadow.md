# Plan: Fix drag geometry desync when borders re-appear on tiled-to-floating transition

## Root Cause

When dragging a tiled window (`show_borders: false`) from the titlebar, the first `Drag` event that breaches the deadzone calls `set_floating_rect` using the tiled frame rect directly (`mod.rs:1348-1362`). Floating mode has `show_borders: true`, so `content_rect` subtracts LEFT_BORDER_WIDTH (1) and TOP_BORDER_HEIGHT (1) from the frame origin, shifting the content area right+down by 1 cell. The cursor that was on the header now appears on the border edge — a resize-handle-like position.

## Fix

In `crates/term-wm-core/src/window/window_manager/mod.rs`, in the `if !self.is_window_floating(*key)` block (~line 1348), expand the floating rect to account for the borders that will render. Additionally, synchronize the active drag anchor so subsequent move ticks don't snap back to the old origin.

```rust
if !self.is_window_floating(*key) {
    let rect = self.visible_region_for_key(*key);

    let left_border = i32::from(crate::chrome::LEFT_BORDER_WIDTH);
    let top_border = i32::from(crate::chrome::TOP_BORDER_HEIGHT);
    let right_border = crate::chrome::RIGHT_BORDER_WIDTH;
    let bottom_border = crate::chrome::BOTTOM_BORDER_HEIGHT;

    // Expand the frame rect so the content area stays in the same
    // visual position as the tiled frame (content_rect will subtract
    // these same borders when rendering).
    let expanded = crate::window::FloatRect {
        x: rect.x - left_border,
        y: rect.y - top_border,
        width: rect.width.saturating_add(left_border as u16 + right_border),
        height: rect.height.saturating_add(top_border as u16 + bottom_border),
    };

    self.set_floating_rect(
        *key,
        Some(crate::window::FloatRectSpec::Absolute(expanded)),
    );

    // Synchronize the in-flight drag anchor so MouseMove doesn't
    // compute delta against the old unexpanded origin and snap the
    // frame back by (L, T) on the next tick.
    *initial_x = expanded.x;
    *initial_y = expanded.y;

    self.bring_to_front_key(*key);
}
```

Within the match arm, `initial_x` and `initial_y` are `&mut i32` references into the `MouseCaptureState::DraggingWindow` — updating them in place is safe and correct.

This keeps the **content area** at the same visual position as the tiled frame, and the cursor remains on the header row (not the border).

### Downward-drag restore path (maximized windows, ~line 1311)

That path already applies a `TOP_BORDER_HEIGHT` adjustment:
```rust
let new_y = row as i32 - i32::from(crate::chrome::TOP_BORDER_HEIGHT);
```
This is correct and needs no change.
