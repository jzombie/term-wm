# Standardize "Direct Mode" → "Direct Input Mode" terminology

## Problem

The feature is called "Direct Mode" in user-facing prose, but the codebase's
canonical symbols are `DirectInputMode` / `DirectInputChanged` / `DirectInputTracker`.
Standardizing on **Direct Input Mode** aligns documentation with the code's naming and
the feature's actual purpose (unbuffered, zero-delay input pass-through).

## Scope decisions (confirmed with user)

- **CHANGELOG**: historical entries are immutable — do NOT rewrite any existing
  `## [...]` section. Add a note only under a new `## [0.9.20-alpha] - TBD` header.
- **Toast string**: rename in code too so runtime message matches docs.
- **Log tag**: rename `[direct-mode]` → `[direct-input-mode]`.
- **Code identifiers** (`direct_mode`, `direct_input_mode`, `DirectInputMode`,
  `DirectInputTracker`, `DirectInputChanged`) stay unchanged — they already align.

## Canonical phrasing

- **Term**: "Direct Input Mode" (noun).
- **Mechanism**: "zero-delay, unbuffered pass-through" — never "zero latency".
- Recommended definitional prose (use in README architecture item 4):

  > **Direct Input Mode**
  > `PtyStateTracker` (`term-wm-pty-engine`) monitors the PTY byte stream for
  > alternate-screen or mouse-tracking requests. When active, `term-wm` enters
  > **Direct Input Mode**, bypassing window manager keybinding/focus evaluation and
  > eliminating ESC sequence buffering to hand raw input to applications like Vim or
  > Less via zero-delay pass-through.

- Toast examples quoted in docs become:
  `Direct Input Mode (keyboard and mouse) enabled for vim`,
  `Direct Input Mode (keyboard) enabled for nano`.
