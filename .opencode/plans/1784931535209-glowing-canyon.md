### 2. Add `clear_session()` to `ServerState`

Encapsulate session teardown in `ServerState` so `notify.notify_one()` is always
fired when the session is removed — regardless of which code path does it.
**Must drain pending PTY output before dropping the session** to avoid silently
truncating trailing output (shell exit messages, teardown logs).

```rust
impl ServerState {
    /// Terminate and clear the active session, flushing remaining PTY buffers
    /// and stream completion markers to all active subscribers.
    fn clear_session(&mut self) {
        if let Some(mut session) = self.session.take() {
            let _ = session.pty.kill_child();
            let raw = session.read_output();
            if !raw.is_empty() {
                for sub in &self.subscribers {
                    sub.respond.respond(raw.clone(), false);
                }
            }
        }
        for sub in &self.subscribers {
            sub.respond.respond(Vec::new(), true);
        }
        self.subscribers.clear();
        self.notify.notify_one();
    }
}
```

## Memory Analysis: No-Subscriber Path

When no clients are connected, the polling loop calls `sync_screen()` on each
wakeup. This clears the `dirty` flag without draining the `pending` buffer —
accumulated bytes are preserved for `early` delivery to future subscribers.

The `Pty` pending buffer is capped at **1 MB** (`PENDING_CAP` in `pty.rs:537`).
If the buffer exceeds this cap it is cleared entirely, bounding accumulation.

If observed RSS appears to grow:

1. **Allocator caching, not a leak.** Userspace allocators retain freed pages
   in thread caches. OS RSS continues reporting those pages until the
   allocator yields them back (`madvise(MADV_DONTNEED)` / `munmap`).
2. **Diagnose with heap profiling, not RSS.** Use `heaptrack`, `valgrind
   --tool=dhat`, or jemalloc profiling to distinguish allocator retention
   from true state accumulation.
3. **No known unbounded growth.** See below for bounded-channel enforcement.

## Bounded Channels

All crossbeam channels currently use `unbounded()`. Replace with `bounded()`
to cap head-of-line queuing under burst load.

| Channel | Location | Capacity | Rationale |
|---------|----------|----------|-----------|
| `push_rx` / `push_tx` | lib.rs:255 — PTY output bytes from server | 256 | Matches typical frame buffer depth. Over capacity → reader task backs pressure via muxio IPC flow control. |
| `clip_rx` / `clip_tx` | lib.rs:256 — OSC 52 clipboard text | 64 | Clipboard events are human-driven (~Hz), 64 is ample. |
| `input_rx` / `input_tx` | lib.rs:357 — crossterm input events | 64 | Keystrokes are human-driven. 64 covers paste bursts. |

Change in `lib.rs`:
```rust
// Before:
let (push_tx, push_rx) = crossbeam_channel::unbounded::<Vec<u8>>();
let (clip_tx, clip_rx) = crossbeam_channel::unbounded::<String>();
// ...
let (input_tx, input_rx) = crossbeam_channel::unbounded::<Event>();

// After:
let (push_tx, push_rx) = crossbeam_channel::bounded::<Vec<u8>>(256);
let (clip_tx, clip_rx) = crossbeam_channel::bounded::<String>(64);
// ...
let (input_tx, input_rx) = crossbeam_channel::bounded::<Event>(64);
```

**Critical:** `crossbeam_channel::Sender::send()` is a synchronous blocking
call. It must NOT be used inside the tokio async background task (would stall
the worker thread). Use `try_send()` instead, yielding the tokio task when the
channel is full:

```rust
// Inside rt.spawn(async move { ... }) — the tokio background reader:
while let Some(chunk) = reader.recv().await {
    match chunk {
        Ok(data) => {
            if let Some(text) = osc52.push(&data, &prev_tail) {
                let _ = clip_tx.try_send(text);
            }
            // ... prev_tail bookkeeping ...
            // Non-blocking push; if saturated, yield and retry
            while let Err(crossbeam_channel::TrySendError::Full(pending)) = push_tx.try_send(data) {
                data = pending;
                tokio::task::yield_now().await;
            }
        }
        Err(_) => break,
    }
}
```

The crossterm input thread (a `std::thread`, not an async task) uses the
blocking `send()` — blocking a std::thread while the main loop catches up is
acceptable since it runs outside the tokio runtime.
