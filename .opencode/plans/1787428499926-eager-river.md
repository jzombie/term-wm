## Step 2 — #290: run/list tasks from the CLI

**Files:** `src/main.rs` (Cli + run ladder), `crates/term-wm-core/src/project_tasks.rs`, `src/term_wm_app.rs` (extract shared prep)

### Shared execution-prep extraction
Move the resolution core of `TermWmApp::command_builder_for_task` (term_wm_app.rs:596-622) into project_tasks.rs as a reusable function so both UI and CLI paths share argv/cwd/env/substitution logic:
```rust
pub struct ResolvedTask { pub argv: Vec<String>, pub cwd: PathBuf, pub env: HashMap<String,String> }
pub fn resolve_task(task: &ProjectTaskConfig, root: &Path, launch_cwd: &Path, vars: &TaskVarContext) -> Option<ResolvedTask>
```
`command_builder_for_task` becomes a thin wrapper building `portable_pty::CommandBuilder` from `ResolvedTask` (behavior unchanged; existing builder tests :1645-1794 still pass).

### CLI surface (flat Cli struct, src/main.rs:22-85 — no subcommands)
```rust
/// List available project tasks for the current directory.
#[arg(long)] pub list_tasks: bool,
/// Run a project task by label (or 1-based index from --list-tasks). Repeatable.
#[arg(long)] pub task: Vec<String>,
```
- `--list-tasks`: load via `load_tasks_for_cwd(std::env::current_dir())`; print numbered list `[1] label — command…`; exit 0. Print notice when no tasks file found.
- Index selection: exact-label match first; if the argument parses as `usize`, fall back to 1-based index matching `--list-tasks` numbering (labels take precedence if ambiguous).
- Multiple `--task` flags run sequentially, **stop on first failure**, exit code = failed task's exit status.
- Execution: build `std::process::Command` from `ResolvedTask` (inherits stdio — `npm run` semantics; std Command inherits env/cwd cross-platform, matching CommandBuilder defaults used by `Pty::spawn`). Slot into the early-exit ladder in `run()` (:176-276) next to `--no-wm` (:215), BEFORE any TUI/gateway work.
- **Signal-safe exit codes** (SEV-2 fix): never `.unwrap()` `status.code()` — it returns `None` when the child dies to a signal (Ctrl+C). Extract via helper:
  ```rust
  #[cfg(unix)]
  use std::os::unix::process::ExitStatusExt;

  fn exit_code_of(status: std::process::ExitStatus) -> i32 {
      match status.code() {
          Some(code) => code,
          #[cfg(unix)]
          None => status.signal().map_or(1, |sig| 128 + sig),
          #[cfg(not(unix))]
          None => 1,
      }
  }
  ```
  Stop-on-first-failure compares against this value; the CLI exits with it.
- `{wm.pid}` here resolves to the CLI process PID (`std::process::id()`) — consistent with "PID of the term-wm process performing the spawn".

### Tests
- project_tasks.rs: `resolve_task_*` (root join, env overlay, None cases) — pure.
- src/main.rs: index-vs-label precedence helper unit test; sequential-stop-on-failure logic via extracted helper `run_cli_tasks(labels) -> io::Result<i32>` taking an injectable runner closure so tests avoid real spawns where practical.

## Step 3 — #297: CLI environment override (**research gate**)

### Phase A — Research deliverable (do first, present before implementing)
User explicitly asked to research the environment model before committing. Produce a short design note (post to issue #297 / present in chat) covering:
1. Enumerate ALL consumers of `active_environment()` / `Environment` across the workspace (grep `active_environment|Environment::`). Known today: gateway socket scoping (`gateway_channel_name`, channel.rs:98-125 — documented intent: "dev builds never attach to prod gateways"), task gating (`load_tasks_for_cwd`), `TERM_WM_ENV` doc'd as single override for both (UI-STYLE.md:62-64).
2. Analyze the coupling problem: overriding env to see dev tasks also repoints the IPC socket namespace → user silently attaches to a different daemon family.
3. Confusion source: heuristic treats `cargo run` AND `cargo run --release` as Dev (`CARGO_MANIFEST_DIR || debug_assertions`, env.rs:73-79).
4. Present options:
   - **A. Single `--env <dev|prod|test>` flag** setting `TERM_WM_ENV` early in `run()`. One source of truth; socket scoping follows deliberately. Simplest; matches existing docs.
   - **B. Task-gating-only override** (e.g. `--task-env <name>`) decoupled from socket scoping. Avoids surprise re-scoping but forks "environment" into two concepts.
   - **C. Generalize environments to arbitrary user strings** (tasks.json already stores strings; enum is the bottleneck) — enables custom names like `profiling`, but env strings flow into socket names (charset risk) and touches more surface.
5. Recommendation recorded; implementation proceeds on user-approved option.

### Phase B — Implementation (default recommendation: Option A)
- `crates/term-wm-config/src/env.rs`: add a process-level override — **no `std::env::set_var`** (SEV-2 fix: it is `unsafe` in Rust 1.80+/edition 2024 and mutates thread-unsafe global state):
  ```rust
  static ENV_OVERRIDE: OnceLock<Environment> = OnceLock::new();

  /// Explicit CLI-provided environment override. First call wins; later calls are ignored.
  pub fn set_override_environment(env: Environment) {
      let _ = ENV_OVERRIDE.set(env);
  }

  pub fn active_environment() -> Environment {
      if let Some(&env) = ENV_OVERRIDE.get() {
          return env;
      }
      // existing TERM_WM_ENV parse → default_environment() heuristic
  }
  ```
  Because `gateway_channel_name()` (channel.rs:119) also calls `active_environment()`, socket scoping follows the override automatically — one source of truth preserved, zero unsafe code.
- `src/main.rs`: add
  ```rust
  /// Override the environment used for task visibility and gateway scoping (dev/prod/test).
  #[arg(long, value_parser = ["dev","prod","test"])] pub env: Option<String>,
  ```
  Handle at the top of runtime-config init (:183): parse via `parse_environment` and call `term_wm_config::env::set_override_environment(env)` BEFORE any gateway/task code runs. Invalid values rejected by clap pre-run.
- Tests: env.rs tests for override precedence (`set_override_environment` beats `TERM_WM_ENV`, beats heuristic; first-set-wins semantics); task-filter wiring reuses patterns from `gating_filters_at_load_prod` (project_tasks.rs:333). Note env-var-mutating tests in that file already serialize on an env lock; new OnceLock tests need their own serialization strategy since the cell is process-global (run in one dedicated test binary or accept first-wins ordering).
