# Fix: voice-typed characters arrive out of order over SSH (term-session)

## Symptom
Google voice typing on termux-over-SSH commits a burst of characters that appear scrambled/reordered in the session.

## Root cause
`crates/term-session-server/src/session_server.rs`, the `StreamInput` handler (~lines 846–874).

The input path is: client keystrokes → `pane.write_bytes()` → `writer.send()` on `STREAM_INPUT` stream → server `StreamInput` handler → per-channel `input_tx` (bounded mpsc, cap 128) → single `input_rx` consumer task → `pty.writer_handle().write_bytes()`.

The muxio dispatcher invokes the sync `StreamInput` handler **in wire order** for a stream. But the handler currently does:

```rust
RpcStreamEvent::PayloadChunk { bytes, .. } => {
    tokio::spawn(async move {
        let channel = bound_channel(state.as_ref(), conn_id).await; // RwLock read
        let ch = resolve_channel(state.as_ref(), &channel).await;   // RwLock read
        let tx = { let guard = ch.lock().await; guard.input_tx.clone() }; // Mutex
        let _ = tx.try_send(bytes);
    });
}
```

Every chunk spawns an independent tokio task. Those tasks race to acquire the async `RwLock`/`Mutex` locks, so chunk N+1's task can `try_send` into `input_tx` **before** chunk N's task. Result: bytes reach the PTY out of order. Normal typing is slow enough that each task usually completes before the next chunk arrives; voice typing commits a whole phrase in a few ms, so many tasks are in flight at once and the race becomes visible.

Secondary issue: `try_send` on the bounded (128) `input_tx` silently drops chunks when full (warn-only).

## Fix (recommended)
Preserve per-connection ordering by replacing the per-chunk `tokio::spawn` with a per-connection ordered forwarder:

1. Add to `ServerState` a field:
   ```rust
   /// Per-connection ordered input forwarders. The sync `StreamInput` handler
   /// forwards each chunk into this queue in wire order; one consumer task per
   /// connection drains it FIFO into the channel's `input_tx`, so bursty input
   /// (e.g. IME voice typing) is never reordered.
   input_forwarders: std::sync::Mutex<HashMap<usize, mpsc::Sender<Vec<u8>>>>,
   ```
   (bounded `tokio::sync::mpsc` at capacity `INPUT_CHANNEL_CAPACITY` = 128, keeping the existing memory-safety intent). Initialize in `run_gateway` (`ServerState { .. }` literal, line ~568).

2. Rewrite the `StreamInput` handler (lines 846–874):
   - `Header`: no-op (forwarder created lazily on first chunk).
   - `PayloadChunk { bytes }`: look up (or lazily create) the per-connection forwarder; synchronously `try_send(bytes)` into it (preserves wire order since the handler runs in order on one thread); on `Full`, warn + drop (same semantics as today). When creating, spawn ONE consumer task per connection:
     ```rust
     tokio::spawn(async move {
         while let Some(bytes) = rx.recv().await {
             let Some(channel) = bound_channel(&state, conn_id).await else { continue };
             let Some(ch) = resolve_channel(&state, &channel).await else { continue };
             let tx = { ch.lock().await.input_tx.clone() };
             // Backpressure instead of try_send-drop; still bounded by input_tx (128).
             if tx.send(bytes).await.is_err() { break; }
         }
     });
     ```
   - `End` / `Error`: remove `conn_id` from `input_forwarders` (drops the sender → `rx.recv()` returns `None` → task exits after draining). The channel's own `input_tx`/`input_rx` persists, so the session survives client disconnect (unchanged behavior).

3. Keep the `WriteInput` prebuffered method as-is (client typing goes through `StreamInput`).

### Why this preserves ordering
- muxio invokes the sync handler for one stream in wire order (confirmed in `rust-muxio`: `rpc_respondable_session.rs::read_bytes` calls the per-request handler synchronously per decoded event; endpoint holds the dispatcher lock during `read_bytes`).
- Successful `try_send` calls into a single mpsc preserve call order.
- Exactly one consumer task per connection drains FIFO and forwards sequentially to `input_tx`, which itself has a single consumer that writes to the PTY.

## Regression test
`tests/integration_session.rs` (modeled on `session_input_output_roundtrip`, uses the `echo` mock which passes stdin→stdout verbatim):

Add `session_stream_input_preserves_order_under_burst`:
1. `spawn_session(&test_channel("test/input_order")).await`; `Spawn` the `echo` mock (cols/rows = `TEST_COLS/TEST_ROWS`).
2. `open_channel(SUBSCRIBE_OUTPUT_METHOD_ID, 0)` and `open_channel(STREAM_INPUT_METHOD_ID, 0)`.
3. Send a burst of many distinct one-byte chunks **without awaiting between sends** (e.g., bytes `b"0123456789...z"` chunked individually, ~100 chunks) to maximize concurrent in-flight chunks at the server.
4. Collect echoed output via `wait_for_output` (extend as needed) and assert it equals the exact expected byte sequence in order.
5. `guard.shutdown().await`.

On the fixed build this passes deterministically; on the buggy build a large back-to-back burst makes the per-chunk race very likely to reorder.
