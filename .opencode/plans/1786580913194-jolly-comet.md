## Part A — Issue #236: require `--force` when killing a channel with participants

Same semantics as daemon `stop`: refuse (RPC error) when the channel has attached participants, unless `--force` is passed. Participants = `ChannelState.clients` (what `list` renders as "clients: N connected"). Check happens **before** any mutation so a refused kill leaves the channel fully operational.

- `KillChannelRequest` (line 372): add `pub force: bool`.
- `KillChannel`: change `type Input = String` → `type Input = (String, bool)`; update `encode_request` (`KillChannelRequest { channel: input.0, force: input.1 }`) and `decode_request` (`Ok((r.channel, r.force))`).

### `crates/term-session-server/src/session_server.rs` — KillChannel handler (lines 1110-1151)
- Decode `let (channel_str, force) = KillChannel::decode_request(&payload)?;`
- Restructure the handler so the participant check and the kill run under a **single** channel-lock acquisition (no TOCTOU gap where a client attaches between check and teardown):
  ```rust
  // 1) Snapshot target conns (read-only, as today).
  let target_conns: Vec<usize> = { ... existing snapshot ... };
  // 2) Lock once: refuse if participants attached (without --force), else kill.
  if let Some(ch) = resolve_channel(state.as_ref(), &name).await {
      let mut guard = ch.lock().await;
      let n = guard.clients.len();
      if !force && n > 0 {
          return Err(rpc_err(&format!(
              "{RPC_ERROR_LIVE_PARTICIPANTS} ({n} participant(s) attached)"
          )));
      }
      guard.request_session_kill(SIGTERM);
      guard.finalize_subscribers();
      for conn_id in &target_conns {
          guard.clients.remove(conn_id);
          guard.subscribers.retain(|s| s.conn_id != *conn_id);
      }
      drop(guard);
      spawn_kill_escalation(&state, &name).await;
  }
  ```
  (The error return auto-drops the guard; holding the lock through check+kill serializes against concurrent `Spawn`/`Attach` so a participant can no longer slip in after the check. Mirrors the `ShutdownGateway` refusal at lines 1230-1248.)

- Pure shared primitives (both hosts use the same rules):

  ```rust
  /// End-exclusive word bounds around `index`; returns `(index, index)` when
  /// `index` is out of range or the cell is not a word char.
  pub fn find_word_bounds(cells: &[Option<char>], index: usize) -> (usize, usize)
  ```

- `SelectionViewport` trait: new defaulted method `fn word_range_at(&mut self, _pos: LogicalPosition) -> Option<SelectionRange> { None }` (contract: `Some` only when `pos` is on a word char; end-exclusive, single row).
- New `SelectionController` methods:
  - `note_click_at(pos, now: Instant) -> u8` (injectable time for tests) + `note_click(pos) -> u8`: returns consecutive click count; resets to 1 when window / position tolerance / not-button-up precondition fails. Records `last_click_at/pos`.
  - `begin_word_selection(range)`: anchor=start, cursor=end, `word_anchor_start=start`, `word_anchor_end=end`, `phase=Dragging`, `button_down=true`, `granularity=Word`.
  - `update_word_drag(pos, word: Option<SelectionRange>)`: **never mutates the origin bounds** and **never falls back to cell-level `update_drag`** (fixes both reverse-drag contraction AND word truncation when the pointer crosses whitespace/punctuation — the origin word stays fully enclosed):
    ```rust
    let Some(anchor_start) = self.state.word_anchor_start else { return };
    let Some(anchor_end) = self.state.word_anchor_end else { return };
    if pos < anchor_start {
        self.state.anchor = Some(word.map(|w| w.start).unwrap_or(pos));
        self.state.cursor = Some(anchor_end);
    } else {
        self.state.anchor = Some(anchor_start);
        self.state.cursor = Some(word.map(|w| w.end).unwrap_or(pos));
    }
    ```
    Over a word, its boundary is used; over whitespace, raw `pos` becomes a cell-granularity boundary so gaps are included — and `[anchor_start, anchor_end]` is always strictly enclosed in the range.
  - `granularity()`, `anchor()`.
- `prepare_drag`/`begin_drag`/`activate_drag` reset `granularity=Cell`. `finish_drag` resets granularity. **Do NOT clear `last_click_*` in `prepare_drag`** (would break detection). `clear()` inherits defaults.
- `handle_selection_mouse` Press arm (lines 307-317) — borrow-safe (note_click in a scoped block returning the count, then re-borrow host). **Double-click activates on exact `count == 2`** so triple-click (count 3, future `SelectionGranularity::Line`) or rapid 4+ clicks are not hijacked — they fall through to a fresh `prepare_drag`:
  ```rust
  let count = {
      let selection = host.selection_controller();
      selection.set_pointer(mouse.column, mouse.row);
      selection.note_click(pos)
  };
  if count == 2 && let Some(word) = host.word_range_at(pos) {
      host.selection_controller().begin_word_selection(word);
      return true;
  }
  host.selection_controller().prepare_drag(pos);
  return true;
  ```

### Text renderer host — `crates/term-wm-ui-components/src/text_renderer.rs`

**On-demand single-row extraction — NO persistent grid cache.** Word lookups touch a single `pos.row`, so caching a full-content `Vec<Vec<Option<char>>>` (nested per-row allocations, heap bloat on large docs, `grid_signature`/`text_generation` invalidation machinery) is a code smell. Instead, extract the characters of the target display row on demand and feed the shared `find_word_bounds`:

- **No-wrap mode (`wrap == false`):** `pos.row` indexes directly into `self.text.lines` — concatenate that line's span contents into the char stream. O(1) line access, zero rendering.
- **Wrap mode (`wrap == true`):** locate the source line containing `pos.row` by accumulating each line's `actual_wrapped_height` (the same visual-height pass `render()` already performs at lines 67-71 / `compute_display_lines`), then render **only that single source line** — `Paragraph::new(line.clone()).wrap(...).scroll((local_row, 0))` into a 1-row scratch `Buffer` — and read the row's per-cell symbols (empty continuation cell → repeat the lead char). No full-content re-render, no cache to invalidate.
- `word_range_at(pos)`: `let chars = row_chars(pos.row, self.content_width.get())?; let (start, end) = find_word_bounds(&chars, pos.column);` → `None` when `start == end` (non-word cell), else the single-row `SelectionRange`.
- Removes the previously-proposed `display_grid` / `grid_signature` / `text_generation` fields, the `maybe_rebuild_grid` hook in `render()`, and the generation bumps in `set_text`/`set_linkified_text` — **no `TextRendererComponent` struct changes at all**.
- Cost envelope matches existing precedent: `render()` already pays O(content) height computation per frame (`compute_display_lines`), and `link_at` (text_renderer.rs:535) already renders a full hit palette per mouse-move when links exist.

> **Implementation note:** an earlier build pass began wiring the now-discarded cache approach (`display_grid` / `grid_signature` / `text_generation` fields, `maybe_rebuild_grid`, generation bumps, and the `render()` hook) into `text_renderer.rs`. The build pass must first **revert that scaffolding**, then implement the on-demand `row_chars` + `word_range_at` override. No other source files are affected by this rework.

## Part C — Documentation: clipboard enablement vs Direct Input Mode

**Docs only.** Accurate wording: WM mouse-managed clipboard features (click-drag selection copy, right-click paste) are overridden by Direct Input Mode apps; OSC 52 copy emitted by the app continues to be relayed. Plus a code TODO to file a follow-up issue for gating OSC 52 at the core.

### `README.md`
Add a note after the "Clipboard split-brain" paragraph (line 83), the existing spot that already discusses Direct Input Mode apps and Paste:

> **Clipboard enablement in Direct Input Mode.** While a window is in Direct Input Mode, `term-wm`'s mouse-managed clipboard integration — click-and-drag selection copy and right-click paste — is overridden: mouse events are forwarded to the running application unfiltered, and clipboard handling within that application is the application's responsibility. Application-initiated copy continues to work, as OSC 52 copy sequences emitted by the running application are still intercepted and relayed to the system clipboard.

### `crates/term-wm-sys-ui-components/assets/help.md`
Extend the existing note in the **Selection & Clipboard** section (lines 115-116):

> * Selection and right-click paste are available only while **not** in Direct Input Mode. In Direct Input Mode, all mouse events pass through to the running application unfiltered, clipboard enablement is overridden, and clipboard handling is delegated to the application: it is responsible for its own selection and copy. OSC 52 copy sequences emitted by the application continue to be relayed to the system clipboard.
