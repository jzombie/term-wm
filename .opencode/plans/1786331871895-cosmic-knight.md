# Coalesce Direct Mode toasts + combined "keyboard and mouse" label

## Why "Mouse" never shows

`DirectInputMode::access_label()` (pty_state_tracker.rs) returns `"Mouse"` only for
`keyboard == false && mouse == true` — an app that requested mouse tracking but is **not** on the
alternate screen and has no margins. In practice every mouse-enabled TUI (vim/helix/micro/opencode)
also switches to the alternate screen (`?1049h`), so `keyboard == true` and the label is `"Full"`.
That's why the user only ever sees "Full"/"Keyboard".

## Why notifications double up

The reader fires `PtyStatus::DirectInputChanged` on **every** struct diff. A vim startup emits
`?1049h` (→ `keyboard`) then `?1002h` (→ `keyboard+mouse`) within milliseconds, producing two
events → two toasts ("Direct Mode (Keyboard) enabled", then "Direct Mode (Full) enabled"). The
runner (runner.rs:380-398) pushes one toast per transition unconditionally.

## Goal

One toast per transition burst showing the combined access, e.g.
`Direct Mode (keyboard and mouse) enabled for vim`. Bonus: reading the title at flush time
(~200 ms later) fixes the "wrong app name" staleness (the window title is applied on the next
render pass, which happens well within the debounce window).

## Design

Add a **debounced, leading-edge-with-cap** Direct Mode toast: the first transition for a window
arms a flush timer; subsequent transitions update the buffered mode but do **not** push the
deadline back. The toast fires once `DIRECT_MODE_TOAST_DEBOUNCE` (200 ms — enough to coalesce the
`?1049h`+`?1002h` startup pair while staying responsive) after the **first** transition in a
burst, so slow-trickling sequences can never starve it. Reuse the existing
`TaskScheduler<SystemTask>` (same pattern as `reset_drag_snap_timer`). Change `access_label()` to
a friendly combined phrase.

`run_with_defaults` (runner.rs:843) always installs the system task handle before the loop, so
there is **no** no-handle immediate-push fallback — test harnesses that assert the toast must call
`set_system_task_handle` (identical debounced semantics in test and production).

| Mode | Label today | Label new |
|---|---|---|
| keyboard + mouse | `Full` | `keyboard and mouse` |
| keyboard only | `Keyboard` | `keyboard` |
| mouse only | `Mouse` | `mouse` |
| none | `Off` | `off` |

Toast: `Direct Mode (keyboard and mouse) enabled for vim` / `Direct Mode disabled for vim`.

  ```rust

  ```
- Initialize in the constructor (near line 874, `system_task_handle: None`):
  `direct_mode_debounce: HashMap::new(),`.
- New constants near the top of the file (AGENTS.md magic-value rule):
  `DIRECT_MODE_TOAST_DEBOUNCE: Duration = Duration::from_millis(200)` and
  `DIRECT_MODE_TOAST_TTL: Duration = Duration::from_secs(3)`.
- New methods:
  ```rust
  /// Buffer a Direct Mode transition. Leading-edge debounce with a hard cap:
  /// the FIRST transition arms the flush timer; later transitions only update
  /// the buffered mode (deadline is never pushed back, so trickling sequences
  /// cannot starve the toast).
  pub fn direct_input_mode_changed(&mut self, key: WindowKey, mode: DirectInputMode)
  ```
  - If an entry for `key` already exists in `direct_mode_debounce`: update the buffered mode only,
    return (keep the armed `TaskId`/deadline).
  - Else: `schedule_once(DIRECT_MODE_TOAST_DEBOUNCE, SystemTask::FlushDirectModeToast(key))` and
    insert `(task_id, mode)`.
  - If `system_task_handle` is `None`: `tracing::warn!` + no-op (only reachable outside
    `run_with_defaults`, which always installs the handle; tests must set it — no divergent
    immediate-push path).
  ```rust
  /// Flush the buffered mode as a single toast (called by the runner on the task).
  pub fn flush_direct_mode_toast(&mut self, key: WindowKey)
  ```
  - `if let Some((_, mode)) = self.direct_mode_debounce.remove(&key)`; no-op if absent.
  - If the window no longer exists, return (avoid a toast for a just-closed window).
  - Push `Direct Mode ({mode.access_label()}) enabled for {title}` when
    `mode.requires_direct_input()`, else `Direct Mode disabled for {title}`; title via existing
    `window_title(key)`; TTL `DIRECT_MODE_TOAST_TTL` via `push_notification`.
- Cleanup in `close_window`: remove `direct_mode_debounce` entry for the key (the armed flush task
  then fires as a harmless no-op via the missing-entry guard).

## Tests

- `pty_state_tracker.rs`: update `access_label()` assertions to the new phrases.
- `window_manager/mod.rs` (new unit tests; every test calls
  `set_system_task_handle(TaskScheduler::<SystemTask>::new().handle())` so the debounced path is
  exercised exactly as in production):
  - `direct_mode_toast_debounce_coalesces` — two rapid `direct_input_mode_changed` calls
    (Keyboard then Full) leave one `direct_mode_debounce` entry holding the Full mode; a single
    `flush_direct_mode_toast` pushes exactly one notification whose message is
    `Direct Mode (keyboard and mouse) enabled for …`.
  - `direct_mode_toast_cap_does_not_reschedule` — after the first `direct_input_mode_changed`, a
    second transition updates the buffered mode but does NOT change the armed deadline
    (`time_until_next()` unchanged / `drain_expired_once()` after the window yields exactly one
    `FlushDirectModeToast`).
  - `direct_mode_toast_no_starvation` — simulate a trickling stream (first transition arms; later
    transitions only re-buffer); after the 200 ms window the flush fires once with the latest mode
    (the deadline is anchored to the first transition, never pushed back).
  - `direct_mode_toast_disabled` — a mode with `requires_direct_input()==false` flushes as
    `Direct Mode disabled for …`.
  - `direct_mode_toast_skips_closed_window` — flush for a removed window is a no-op (no toast).
- `runner.rs`: existing direct-mode routing tests still pass (the drain now calls
  `direct_input_mode_changed`; the runner test path that asserts routing goes through
  `run_with_defaults`/`run_event_loop`, which installs the task handle at runner.rs:843). No test
  asserts the toast directly, so removing the immediate-push fallback has no blast radius.
