# Split Direct Mode: keyboard vs mouse capture

## Problem

Direct Mode today is a single all-or-nothing bool (`ctx.direct_mode()`) driven by
`PtyStateTracker::requires_app_routing()` = `alt_screen || mouse_tracking || custom_margins`.

In `TerminalComponent::handle_events`, native text selection / right-click paste / link clicks are
gated behind `!ctx.direct_mode()` (terminal.rs:90-115). So an app on the **alternate screen without
mouse tracking** (pico/nano) disables native selection **and** gets no mouse events forwarded
(`mouse_event_allowed(None, …) == false`). The mouse is dead — text can't be selected or copied.

Desired model:
- **Default state (off):** app did NOT write mouse-enable sequences (`\x1b[?1000h/1002h/1003h` + `\x1b[?1006h`) → the terminal keeps mouse control → native selection + clipboard copy work, even on the alternate screen.
- **Captured state (on):** app enabled mouse tracking with a supported encoding → suppress native selection, forward mouse events to app stdin as SGR bytes.
- **Override:** holding Shift (universal) or Option (macOS only) while click-dragging forces native selection even in a captured app.

Represent Direct Mode as a structured, serializable snapshot with independent `keyboard` and
`mouse` dimensions; log it to the debug logger; show the access level in the toast; and carry the
snapshot through the transition event so **any** mode change (not just the aggregate flip) is
notified and logged.

## Design

New `DirectInputMode` struct (pty-engine), built by the tracker, carried on `ComponentContext`,
carried through the `DirectInputChanged` event, and used for logging + toast.

| Signal | Definition | Gates |
|---|---|---|
| `keyboard` | `alt_screen \|\| custom_margins` | runner key-forward, ScrollView key-scroll & scrollbar render, Terminal Shift+PgUp, Terminal render scroll-suppression |
| `mouse` | mouse tracking requested **with a supported encoding** (see §1) | Terminal mouse branch (native vs forward), ScrollView wheel→scrollback (suppress when captured) |
| `requires_direct_input()` | `keyboard \|\| mouse` (aggregate) | kept for `direct_mode()` back-compat and the toast "enabled" check |

Single source of truth for "is the mouse captured": the `mouse` field computed by
`PtyStateTracker::direct_input_mode()` and surfaced as `ctx.mouse_captured()`. `terminal.rs` gates
on `ctx.mouse_captured()` (tracker-derived) — it does **not** independently recompute capture from
the vt100 screen. The screen is read only to produce the encoded byte sequence in the forward path.

## Changes

### 1. `crates/term-wm-pty-engine/src/pty_state_tracker.rs`
- New struct (derive `Debug, Clone, Copy, PartialEq, Eq, Default`; no serde — the debug log is
  plain `String` lines, so `Debug`/`tracing` are sufficient):
  ```rust
  pub struct DirectInputMode {
      pub keyboard: bool,   // alt screen || custom margins
      pub mouse: bool,      // mouse tracking + supported encoding
      // informational (logged, not gating):
      pub alt_screen: bool,
      pub application_cursor_keys: bool,
      pub custom_margins: bool,
      pub mouse_tracking: MouseTrackingMode,
      pub sgr_mouse: bool,
      pub utf8_mouse: bool,   // DECSET 1005
      pub alt_scroll: bool,
  }
  ```
- Methods: `requires_direct_input() -> bool` (`keyboard || mouse`), `access_label() -> &'static str`
  (`"Full"`/`"Keyboard"`/`"Mouse"`/`"Off"`), `is_active()`.
- `DirectInputTracker` trait: replace `fn requires_direct_input(&self) -> bool` with
  `fn direct_input_mode(&self) -> DirectInputMode`.
- `PtyStateTracker`:
  - Add `is_utf8_mouse_active: AtomicBool`; set from DECSET/DECRST param `1005` in
    `PtyPerformAdapter::csi_dispatch`.
  - **Include `is_utf8_mouse_active` in `reset_all()`** (alongside the existing
    `is_sgr_mouse_active`, `mouse_tracking_mode`, `is_alt_screen_active`, etc.). The existing
    hooks already route here: `PtyPerformAdapter::esc_dispatch` calls `reset_all()` on RIS
    (`ESC c`) and `csi_dispatch` on DECSTR (`CSI ! p`). Without this, a crashed/`reset`-spawning
    TUI that never emits explicit `?1005l`/`?1006l` would leave `DirectInputMode.mouse` stale.
  - Track DEC private mode `9` (X10 mouse) as `update_mouse_tracking(1)` for parity with the
    vt100 screen's `?9 → Press`.
  - `direct_input_mode()` reads all atomics. **`mouse` uses the same structural check as the
    forward path**:
    ```rust
    let encoding_supported = !self.is_utf8_mouse_active.load(Acquire)
        || self.is_sgr_mouse_active.load(Acquire);
    let mouse = self.mouse_tracking_mode.load(Acquire) != 0 && encoding_supported;
    ```
  - `requires_app_routing()` redefined as `self.direct_input_mode().requires_direct_input()`
    (same aggregate semantics — existing tests at lines 277-533 still pass, plus new ones).
- `crates/term-wm-pty-engine/src/lib.rs`: re-export `DirectInputMode`; change
  `PtyStatus::DirectInputChanged(bool)` → `PtyStatus::DirectInputChanged(DirectInputMode)`.

### 2. `crates/term-wm-pty-engine/src/pty.rs`

  `prev_mode != new_mode` (full struct compare) — so Keyboard→Full and Full→Keyboard transitions
  notify even though the aggregate bool is unchanged.

  - `direct_mode()` getter → `mode.requires_direct_input()` (aggregate, back-compat).
  - New getters: `keyboard_direct()` → `mode.keyboard`, `mouse_captured()` → `mode.mouse`.
  - Keep `with_direct_mode(bool)` (maps to `{ keyboard: b, mouse: b, ..Default::default() }`, so existing tests keep passing); add `with_direct_input_mode(DirectInputMode)`.
- `io/event_source.rs` (~59, 128): `take_direct_input_changed() -> Vec<(WindowKey, DirectInputMode)>`.
- `runner.rs`:
  - Line 241-245: build ctx with `.with_direct_input_mode(app.wm().direct_input_mode(focus_id))`.
  - Line 649: key-forward gate → `app.wm().direct_input_mode(focus_id).keyboard` (a mouse-only app

  - `DirectInputChanged` drain (~377-388): `for (key, mode) in transitions`, toast with access

    `term_wm_core::debug_log::global_debug_log()`. Because the event carries the mode, sub-mode
    shifts (e.g. Keyboard→Full) now produce a toast + log entry.

### 5. `crates/term-wm-ui-components/src/terminal.rs` — the behavioral fix
Rework the `Event::Mouse` branch (89-147) so the native-vs-forward decision no longer consults `ctx.direct_mode()`:
- `app_captures_mouse = ctx.mouse_captured()` (tracker-derived single source; no parser lock on the
  native path).
- `override_active = force_native_selection(mouse.modifiers)` — new helper:
  ```rust
  fn force_native_selection(modifiers: KeyModifiers) -> bool {
      modifiers.shift || (cfg!(target_os = "macos") && modifiers.alt)
  }
  ```
  (Shift is the universal override. Option/Alt is only hijacked on macOS, matching the design doc;
  on Linux/Windows `Alt` continues to pass through as an SGR modifier bit so Emacs/Helix-style
  Alt+mouse keep working.)
- **Comment/document the override as best-effort within term-wm's input stream:** it only applies
  to SGR mouse streams that actually reach `term-wm`. When `term-wm` runs nested inside a host
  terminal (Terminal.app/iTerm2/Alacritty), the host intercepts `Shift+mouse` at its OS windowing
  layer and sends no bytes to term-wm's stdin — host-level selection takes precedence there. This
  is documented in the terminal.rs comment, README, and help.md (see §7), not treated as a
  guarantee.
- `gesture_active = selection.button_down() || selection.is_dragging()` (keeps a native drag alive
  even if the override is released mid-gesture).
- If `!app_captures_mouse || override_active || gesture_active` → native handling (right-click
  paste, `handle_selection_mouse`, `try_handle_link_click`); return `Consumed` if handled, else
  `Ignored` (never forward while overriding / mid-gesture).
- Else (captured, no override) → existing forward path: read screen `(mode, encoding)`,
  `mouse_event_allowed(mode, kind)`, `localize_coordinate`, `mouse_event_to_bytes` →
  `TermWmAction::MouseToBytes`. Keep the existing `Default | Sgr` encoding guard as a paranoia
  net (should already be satisfied by the tracker's `mouse` definition).
- Change scroll-suppression gates from `ctx.direct_mode()` to `ctx.keyboard_direct()`:
  line 73 (Shift+PgUp), line 513 (`suppress_scroll`), line 577 (scroll-sync push). Leave wheel &
  selection rendering semantics otherwise untouched.
- Keep `right_click`/`selection` code comments updated (AGENTS.md: update, don't delete).

### 6. `crates/term-wm-ui-components/src/scroll_view.rs`
- Line 384 (key scroll bindings) and line 539 (scrollbar render): `!ctx.direct_mode()` → `!ctx.keyboard_direct()`.
- **Line 359 (wheel→scrollback): `!ctx.direct_mode()` → `!ctx.mouse_captured()`.** Wheel is a mouse
  input, so it follows the mouse-capture decision: when the app has NOT captured the mouse, the WM
  owns the wheel (native scrollback/viewport scroll) even if `keyboard` direct mode is on; when the
  app HAS captured the mouse, the wheel is forwarded to the terminal → `MouseToBytes`.
  This fixes the wheel black-hole for alt-screen non-mouse apps (nano/less/pico): previously the
  aggregate gate suppressed wheel-to-scrollback while the terminal's native path dropped the event
  (`mouse_event_allowed(None, …) == false`).

### 7. Docs
- `README.md` (~60-77, 109-113) and `crates/term-wm-sys-ui-components/assets/help.md` (~35-41):
  document the default/captured mouse states, that native selection works for non-mouse-capturing
  apps (e.g. pico/nano), and the Shift (macOS: Option too) override.
- **Qualify the override in docs:** Shift/Option native-selection works on SGR mouse streams that
  reach term-wm. When term-wm is nested in a host terminal emulator, the host intercepts
  Shift+mouse first (host-level selection) and term-wm receives no bytes — so the override is a
  best-effort fallback, not an absolute guarantee.

  `mouse_selection_active_in_direct_mode_without_mouse_capture`; `AlwaysDirect` tracker now returns
  `DirectInputMode { keyboard: true, mouse: false, ..Default::default() }` (alt screen, no mouse —
  the pico/nano scenario). Press+Drag must be consumed and selection active.
- `terminal.rs::direct_mode_mouse_down_skips_selection` (2193): first half (1000h, `ctx.mouse_captured()` true via `.with_direct_mode(true)`) → `MouseToBytes`; second half uses a fresh pane (no mouse sequences) and a non-captured ctx → selection consumes the drag. Split into two focused tests.

Add:
- pty_state_tracker: `direct_input_mode()` mapping — `?1049h` → `keyboard: true`; `?1002h` →
  `mouse: true`;   `?1002h` + `?1005h` → `mouse: false` (unsupported encoding) with `utf8_mouse: true`;
  `?9h` → `mouse_tracking == X11Normal`; both → `access_label() == "Full"`; RIS reset.
- pty_state_tracker: **reset test** — after sending `?1000h` + `?1006h` + `?1005h` + `?1049h`
  (mouse/keyboard active), sending `\x1b[!p` (DECSTR) **and** separately `\x1bc` (RIS) must clear
  `DirectInputMode.mouse` and `DirectInputMode.keyboard` back to `false` (including
  `utf8_mouse`/`sgr_mouse`).
- terminal: captured ctx (`.with_direct_mode(true)` + 1000h parser) + **Shift** modifier →
  Press/Drag consumed by native selection (not `MouseToBytes`); same for **Alt** modifier **only**
  under `#[cfg(target_os = "macos")]` (assert the helper's cfg behavior via a small unit test on
  `force_native_selection`).
- runner / unified_event_source: a Keyboard→Full transition (aggregate unchanged) still yields a
  `DirectInputChanged` entry with the new mode (regression for SEV-1).
- component_context: `with_direct_input_mode` + `keyboard_direct()`/`mouse_captured()` getters.

  `.with_direct_input_mode(DirectInputMode { keyboard: true, mouse: false, .. })` (alt screen, no
  mouse) → `ScrollDown` produces a `ScrollView` action (native wheel scroll), NOT a pass-through;
  with `mouse: true` → wheel falls through to the child (forwarded to the app).

cargo clippy --workspace --all-targets --all-features -- -D warnings

Manual (macOS/Linux/Windows):
1. Run the WM; open `nano` (alt screen, no mouse) → mouse drag selects text, release copies to clipboard; **mouse wheel scrolls the WM viewport (no black-hole)**.
2. Open a mouse-capturing TUI (helix/micro/opencode-style) → clicks/drags/moves are routed to the app (cursor follows).
3. In the captured TUI, hold Shift (macOS: Option) and drag → native text selection works instead.
4. Start vim (toast "Direct Mode (Keyboard) enabled"); then enable its mouse (e.g. `:set mouse=a`) → toast updates to "Direct Mode (Full) enabled" — sub-mode transitions notify.
5. Open the debug log (command palette) → line like `[direct-mode] window=... mode=DirectInputMode { keyboard: true, mouse: false, ... }`.
