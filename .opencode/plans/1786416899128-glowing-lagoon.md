# Fix: pasting multi-line text into pico loses line breaks

## Symptom

Pasting a multi-line script into pico running inside term-wm loses the line
breaks (all lines run together). The same paste into pico in a normal terminal
(Terminal.app / iTerm2) preserves them.

## Root cause

term-wm's paste path sends the clipboard text **verbatim** when the child app has
not enabled bracketed paste (DECSET 2004). Clipboard text uses LF (`\n`) line
endings, so term-wm writes raw `\n` bytes to the PTY.

A normal terminal sends pasted newlines as **CR (`\r`)** in the non-bracketed
case — the same byte term-wm itself uses for the Enter key
(`crates/term-wm-pty-engine/src/input_encoding.rs:24` → `(KeyCode::Enter, _) =>
vec![b'\r']`). Pico (classic, no DECSET 2004) maps CR to "newline inserted" but
ignores a lone LF, so:
- normal terminal → `\r` → pico inserts newlines → breaks preserved;
- term-wm → raw `\n` → pico drops LFs → breaks lost.

The bracketed-paste gating itself is correct: the reader feeds all child output
into the same `shared_parser` the paste handler reads (`pty.rs:1143`,
`terminal.rs:188-192`), and `screen().bracketed_paste()` is set by the vt100 fork
when the child writes `\x1b[?2004h`.

## Fix (uses the `line-ending` crate)

Add the dependency (workspace convention, like `term-wm-vt100`):
- `Cargo.toml` `[workspace.dependencies]` (line 52 area, alphabetical):
  `line-ending = "1.5.1"`
- `crates/term-wm-ui-components/Cargo.toml` `[dependencies]` (alphabetical,
  between `indoc` and `linkify`): `line-ending = { workspace = true }`

In `crates/term-wm-ui-components/src/terminal.rs` add one helper and use it in
**both** paste paths (`Event::Paste`, lines 187-203, and
`TermWmAction::ClipboardPaste`, lines 233-256):

```rust
use line_ending::LineEnding;

/// Convert paste text to the bytes sent to the child PTY. When the app
/// enabled bracketed paste (DECSET 2004) the text is wrapped verbatim so the
/// app can insert it literally; otherwise line endings become CR — the byte
/// terminals send for Enter (see key_to_bytes). A lone LF is ignored by many
/// raw-mode apps (e.g. classic pico), so sending LF concatenates all lines.
/// LineEnding::CR.apply collapses LF / CRLF / CR all to a single CR.
fn paste_to_bytes(text: &str, bracketed_paste: bool) -> Vec<u8> {
    if bracketed_paste {
        let mut wrapped = b"\x1b[200~".to_vec();
        wrapped.extend_from_slice(text.as_bytes());
        wrapped.extend_from_slice(b"\x1b[201~");
        wrapped
    } else {
        LineEnding::CR.apply(text).into_bytes()
    }
}
```

Replace the duplicated wrapping/send blocks in `Event::Paste` and
`ClipboardPaste` with `paste_to_bytes(&text, bracketed_paste)`.

Single-line text (no newlines) is unchanged, so existing behavior for shells and
single-line pastes is preserved. Bracketed-paste apps (nano/vim/opencode) keep
verbatim LF inside the markers — no change. This replaces the hand-rolled
byte-scanning CRLF/LF/CR normalization from the earlier draft with the
purpose-built `line-ending` crate (no ad-hoc `\r`/`\n` logic of our own).

### Tests (extend the bracketed-paste test module, terminal.rs ~2541)

- `paste_sends_cr_for_lf_when_child_disabled`: non-bracketed `"a\nb"` →
  `b"a\rb"` (LF→CR), not `b"a\nb"`.
- `paste_collapses_crlf_when_child_disabled`: `"a\r\nb"` → `b"a\rb"` (single CR,
  no double CR).
- `paste_keeps_verbatim_when_child_enabled`: bracketed `"a\nb"` →
  `b"\x1b[200~a\nb\x1b[201~"` (LF preserved inside markers).
- Existing tests (`paste_sends_raw_when_child_disabled` asserting `b"hello"`,
  `paste_wraps_in_bracketed_when_child_enabled`, etc.) remain valid unchanged.

### Out of scope (note, no change)

- `crates/term-session-client/src/lib.rs:740-746` always wraps forwarded pastes
  in bracketed markers and forwards them into the shared session. That is
  correct for its role (it relays the host's already-bracketed paste), so it is
  left alone.
- The pty-engine's `key_to_bytes` already emits CR for Enter; no change.
