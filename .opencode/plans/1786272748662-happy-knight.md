# Plan: FAB auto-offset on bottom-row content + click-to-scroll tab into view

Two usability changes to the term-wm chrome. Independent of each other; both live in the
`term-wm-ui-components` / `term-wm-sys-ui-components` crates and need no config knob
(always-on behavior).

---

## Part 1 — Lift the monocle FAB when the app draws content on the bottom row

### Problem
In monocle mode the FAB renders at the absolute bottom-right of the screen
(`crates/term-wm-sys-ui-components/src/wm_fab.rs`). When the focused app draws a
full-width bottom row — a status line (opencode's bottom border, tmux, vim) — the FAB
overlaps it.

### Feasibility (confirmed by exploration)
Yes, reliably. The FAB renders **after** the window compositing loop into the **same
shared ratatui frame buffer**:

- `composite_window` blits each window's offscreen buffer into the main buffer
  (`crates/term-wm-console/src/draw_plan_renderer.rs:1095-1104`).
- FAB renders afterward (`src/lib.rs:255-271` → `WmFabComponent::render`, `wm_fab.rs:55-99`),
  so the main buffer already holds the app's final bottom-row pixels.
- In cramped monocle the window `dest` fills the full area (`show_borders: false`), so the
  app's last visible row == the screen's bottom row. Panels claim zero space in cramped
  monocle (`layout.rs:319`, `mod.rs:2376-2384`), so nothing else pollutes the bottom row
  before the FAB. The cursor overlay renders *after* the FAB, so the cursor can't cause
  false positives.
- Detection pattern already used in production: `!cell.symbol().starts_with(' ')`
  (`draw_plan_renderer.rs:645`, `:954`, `:1369-1376`).

### Reliability caveats (document in a code comment)
- Buffer is freshly re-created every frame (`Buffer::empty` in
  `console_render_target.rs:185-199`), so no stale FAB label pollutes detection.
- Symbol-only check matches repo convention; a status line rendered purely as
  background-colored spaces (no glyph) would not be detected — rare, acceptable.
- Wide-char continuations render as `' '`; the leading half has a real symbol on the same
  row, so whole-row detection still triggers.

### Changes (all in `crates/term-wm-sys-ui-components/src/wm_fab.rs`)
1. Add a named const:
   ```rust
   /// Rows to lift the FAB when the app draws content on the bottom row.
   const FAB_LIFT_OFFSET: i32 = 1;
   ```
2. Add a private detection helper that **strictly intersects with `buffer.area`** and uses
   the Option-returning `Buffer::cell()` (never `buffer[(x, y)]` indexing), so a clipped or
   partially-offscreen `area` can never panic:
   ```rust
   fn bottom_row_has_content(buffer: &ratatui::buffer::Buffer, area: LayoutRect, y: i32) -> bool {
       let buf = buffer.area;
       let buf_left = i32::from(buf.x);
       let buf_right = i32::from(buf.x).saturating_add(i32::from(buf.width));
       let buf_top = i32::from(buf.y);
       let buf_bottom = buf_top.saturating_add(i32::from(buf.height));
       if y < buf_top || y >= buf_bottom {
           return false;
       }
       let left = area.x.max(buf_left);
       let right = (area.x + i32::from(area.width)).min(buf_right);
       if left >= right {
           return false;
       }
       (left..right).any(|x| {
           buffer
               .cell((x as u16, y as u16))
               .is_some_and(|c| !c.symbol().starts_with(' '))
       })
   }
   ```
   (`y as u16` is safe because `y` is proven within the buffer height; `x` is proven within
   the buffer width by the clamped range, and `Buffer::cell` returns `None` outside its
   area anyway — indexing `buffer[(x, y)]` is never used.)
3. In `render` (currently wm_fab.rs:55-99), move `downcast_ratatui(backend)` earlier and,
   before setting `self.fab_rect`:
   ```rust
   let bottom_y = area.y + i32::from(area.height).saturating_sub(1);
   let content = bottom_row_has_content(&ratatui_backend.buffer, area, bottom_y);
   // Lift only when there is a row above the bottom to move into. `>=` (not `>`):
   // a 2-row area (`height == 2`) can still lift the FAB from row `area.y+1` up
   // to row `area.y`, which is inside the area; only a 1-row area has no room.
   let lift = if content && area.height >= 1 + FAB_LIFT_OFFSET as u16 {
       FAB_LIFT_OFFSET
   } else {
       0
   };
   self.fab_rect = LayoutRect {
       x: area.x + i32::from(area.width).saturating_sub(i32::from(width)),
       y: area.y + i32::from(area.height).saturating_sub(1 + lift),
       width,
       height: 1,
   };
   ```
   - `saturating_sub(1 + lift)` cannot underflow, and when `area.height == 1` the FAB
     renders at `area.y` (the only row) — same as today, no false offset claim.
   - Borrows are sequential: read cells into a `bool` first, then call `safe_set_string`.
   - Hitbox registration is unchanged — it uses the lifted `fab_rect`, so the tap target
     moves with the label.
4. Tests (in the existing `mod tests`; existing tests use an empty buffer and keep passing):
   - `fab_lifts_when_bottom_row_has_content`: pre-write a glyph at `(40, 23)` on an 80×24
     buffer, render, assert `fab_rect().y == 22` and the label is drawn on row 22.
   - `fab_stays_on_bottom_row_when_only_other_rows_have_content`: pre-write content on row 0
     only, assert `y == 23`.
   - `fab_lifts_on_two_row_area`: 2-row area with content on the bottom row, assert
     `fab_rect().y == area.y` (lifted one row into the top row, in bounds).
   - `fab_tiny_area_does_not_falsely_lift`: 1-row-tall area with content on it, assert
     `fab_rect().y == area.y` (no offset, no panic).
   - `fab_offscreen_area_does_not_panic`: `area` extending past the buffer edge (e.g.
     80×24 buffer with `area.x + area.width > buffer` width), assert render succeeds.

## Part 2 — Clicking a tabbar window title scrolls the tab fully into view

### Problem
Clicking a window title in the top-panel tabbar should bring that tab fully into view.
If the title is physically longer than the visible area, it should left-align (show the
leftmost part).

### Current behavior (explored)
The tabbar is `TabBarComponent<K>` in `crates/term-wm-ui-components/src/tab_bar.rs`. It
already has an auto-scroll-to-focused block in `render` (tab_bar.rs:282-301): when the
active key, viewport width, or focused tab bounds change, it scrolls the focused tab's left
edge into view (`flx < h` → `h_scroll = flx`) or right edge into view (`flx+fw > vp_end` →
`h_scroll = flx+fw-vp`), clamped to `max_scroll`. Click → focus flow:
`handle_press` (tab_bar.rs:551-562) → `TabBarEvent::Select` → `map_bar` →
`TermWmAction::FocusWindow` → `focus_window_key`.

Two gaps vs. the requested behavior:
1. **Deferred**: `handle_press` arms a `DragState` on any tab press (551-560), and the
   auto-scroll block is gated on `self.drag_state.is_none()` (285). So a clicked tab is not
   scrolled into view until after mouse release. Clicking the already-active tab never
   re-follows (guard `last_auto_focus != active_key` doesn't trip).
2. **Oversized tabs right-align instead of left-align**: when `fw > scroll_viewport_width`,
   the `flx+fw > vp_end` branch sets `h_scroll = flx+fw-vp > flx`, scrolling the title's
   left part off-screen and showing its tail. (Reachable: `MAX_ENTRY_LABEL = 40`, so a
   single tab can be ~44 cols wide in a very narrow viewport.)

### Changes (all in `crates/term-wm-ui-components/src/tab_bar.rs`)
1. Add a free helper next to the other module-level helpers (around line 26-42):
   ```rust
   /// Horizontal scroll that makes a tab at logical `lx` of `width` columns fully visible.
   /// Tabs wider than the viewport are left-aligned (show the leftmost columns).
   fn scroll_into_view_target(h: i32, lx: i32, width: i32, viewport_width: i32, max_scroll: i32) -> i32 {
       let target = if width > viewport_width {
           lx.max(0)                 // title longer than the area → left-align
       } else if lx < h {
           lx.max(0)                 // clipped on the left → reveal left edge
       } else if lx.saturating_add(width) > h.saturating_add(viewport_width) {
           (lx.saturating_add(width) - viewport_width).max(0)  // clipped right → reveal right edge
       } else {
           h                         // already fully visible
       };
       target.min(max_scroll).max(0)
   }
   ```
   This preserves the existing behavior for tabs that fit (the existing tests
   `manual_scroll_persists_until_active_changes` and
   `reorder_moves_active_off_screen_then_auto_scrolls_back` remain valid).
2. **Do NOT mutate `h_scroll` inside `handle_press`.** This is the review-mandated design:
   `entry_geometry` / `item_hits` are only refreshed during `render()`, so writing
   `h_scroll` mid-event would desync `DragState::grab_col` (derived from the prior frame's
   hit rects) from the scroll geometry if a `Drag` arrives before the next `render()`.
   Instead, record a pending click target that the next render pass consumes:
   - Add field `pending_scroll_to: Option<K>` to `TabBarComponent` (init `None` in `new()`).
   - In `handle_press`'s `hit_test_tab` branch (tab_bar.rs:551-562), before arming the drag
     state / returning `Select`, set `self.pending_scroll_to = Some(key)`. `h_scroll` is
     left untouched, so drag math (which uses the current `h_scroll` + logical
     `entry_geometry` positions) stays consistent until the next render.
   - In `render()`, immediately after the auto-scroll block (after line 301), consume it.
     **`drag_state` must be checked BEFORE `.take()`** — the `if let` scrutinee is evaluated
     first, so putting `take()` in the pattern would evict the pending target on the frame
     after a click (while the button is still held, `drag_state` is `Some` and the guard
     fails), silently breaking click-to-scroll:
     ```rust
     if self.drag_state.is_none()              // check BEFORE take() — `&&` short-circuits
         && let Some(key) = self.pending_scroll_to.take()
         && let Some((_, lx, width)) = self.entry_geometry.iter().find(|(k, ..)| *k == key)
     {
         self.h_scroll = scroll_into_view_target(
             i32::from(self.h_scroll),
             *lx,
             i32::from(*width),
             scroll_viewport_width,
             max_scroll,
         ) as u16;
     }
     ```
     When `drag_state.is_some()` (button still held), the `&&` short-circuits before `take()`
     runs, so the pending flag is retained and applies on the frame after release — a plain
     click therefore scrolls on the very next frame. The result is idempotent with the
     auto-scroll block, which re-follows the newly-focused tab anyway.
3. Fix the auto-scroll block (tab_bar.rs:285-298) to use the helper with the fresh local
   values, gaining the left-align fix for keyboard-focus / structural changes:
   ```rust
   if self.drag_state.is_none() && auto_scroll && let Some((flx, fw)) = focused_range {
       self.h_scroll = scroll_into_view_target(
           i32::from(self.h_scroll),
           flx,
           i32::from(fw),
           scroll_viewport_width,
           max_scroll,
       ) as u16;
   }
   ```
4. Tests:
   - `clicking_partially_visible_tab_scrolls_it_into_view`: many tabs in a 30-wide bar,
     scroll so a later tab is half-hidden at the right edge, press on its visible portion →
     assert `Select(key)` is returned AND that `h_scroll` is **unchanged** by the press
     itself; then `render_bar(...)` and assert `h_scroll` now places the tab's full logical
     range within `[h_scroll, h_scroll + scroll_viewport_width]`.
   - `clicking_oversized_tab_left_aligns`: one tab with a long label (≥ `MAX_ENTRY_LABEL`
     columns) in a ~20-wide bar; render, then press its partially-visible portion, render
     again, assert `h_scroll == lx` (left-aligned).
   - `clicking_active_tab_reeveals_it`: active tab half-hidden at the right edge, press it
     (no focus change → auto-scroll guard doesn't trip), render → it still scrolls into view
     via the pending path.
   - `drag_reorder_still_works_after_pending_scroll`: press a partially-visible tab (sets
     pending), issue a `Drag` (not a render), assert `h_scroll` is untouched and the drop
     target / reorder index are computed without coordinate drift; render, then release →
     reorder commits normally.
