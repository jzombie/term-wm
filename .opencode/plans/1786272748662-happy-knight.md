# Plan: Conditional FAB bottom-row reservation + click-to-scroll tab into view

Part 1 uses **previous-frame detection with relative-row inspection** (Option 1, confirmed
with the user): the FAB stays fixed on the bottom row; the application viewport is padded
up one row only while the app draws content on its bottom-most assigned row. Part 2
(tabbar click-to-scroll) is unchanged and implemented.

---

## Part 1 — Conditionally reserve the bottom row for the FAB (footprint-only collision)

### Design (confirmed: Option 1 + relative-row inspection, FAB-footprint only)
The layout pass (`register_managed_layout`) runs *before* any content is composited, so the
padding decision comes from the **previous frame**: `render_app` inspects only the FAB's
footprint (the ~9 rightmost columns) against the focused window's **current** bottom row in
the composited buffer, stores a bool on the `WindowManager`, and `register_managed_layout`
next frame reserves the bottom row when `is_monocle_cramped() && flag`.

**Why footprint-only:** instead of scanning the whole bottom row, only the columns directly
under the FAB label (`fab_rect.x .. fab_rect.x + fab_rect.width`) are checked. Apps with
left-aligned bottom content (shell prompt, vim mode indicator) keep their full height when
the bottom-right corner is empty.

**Padded-frame paradox (and how relative-row inspection resolves it):**
- Unpadded frame (window height H): app status line at row H-1 under the footprint →
  detected → flag true.
- Padded frame (window height H-1): app reflows via SIGWINCH → status line at row H-2 →
  the *physical* row H-1 is now blank, so a naive fixed-row check would clear the flag and
  oscillate. Instead the check targets the **window's current bottom row**
  (`window_area.y + window_area.height - 1`, which moves with the reservation), so it sees
  the status line at H-2 → flag stays true → latched padded.
- If the app clears its bottom-right corner, the footprint on the padded bottom row becomes
  blank → flag false → view safely expands back to full height next frame.

**Self-trigger avoidance:** detection runs after the window loop but **before the FAB
draws**, and the buffer is recreated each frame — the FAB label can never be detected.
1-frame lag (~16 ms) is imperceptible.

3. `crates/term-wm-console/src/draw_plan_renderer.rs`
   - Add a generic, strictly-clipped range helper (FAB-footprint detection uses it):
     ```rust
     /// True if any cell in `[x_start, x_end)` on row `y` has a non-space symbol.
     /// Coordinates are clipped to `buffer.area`. `y` is the window's current bottom
     /// row (it moves when the FAB row is reserved, which is what prevents oscillation).
     pub fn row_has_content_in_range(
         buffer: &ratatui::buffer::Buffer,
         x_start: i32,
         x_end: i32,
         y: i32,
     ) -> bool
     ```
     Implementation notes:
     - **Strict clipping first, direct slice scan second.** After clamping `y` into
       `[buf.y, buf.y+buf.height)` and `[x_start, x_end)` into `[buf.x, buf.x+buf.width)`
       (returning `false` on out-of-bounds `y` or an empty/negative range), index into
       Ratatui's contiguous `buffer.content` array directly instead of calling
       `Buffer::cell()` per cell:
       ```rust
       let buf_w = usize::from(buffer.area.width);
       let row_offset = (y as usize - buffer.area.y as usize) * buf_w;
       let start_idx = row_offset + (left as usize - buffer.area.x as usize);
       let end_idx = row_offset + (right as usize - buffer.area.x as usize);
       buffer.content[start_idx..end_idx]
           .iter()
           .any(|c| !c.symbol().starts_with(' '))
       ```
     - Eliminates `Buffer::cell()`'s per-iteration `area.contains()` bounds check (done
       once up front by the clamping) and scans a contiguous `&[Cell]`, letting LLVM
       auto-vectorize the ASCII-space symbol check in `--release`. Semantics are identical
       to the `cell()` version (all indices are proven in-bounds by the clamp).
   - This is a strict superset of the reviewed bounds safety: the pre-clamped indices are
     exactly what `Buffer::cell` would validate, so no out-of-bounds indexing is possible.
4. `src/lib.rs` (`render_app`)
   - After the window loop (line 200) and before the FAB block (line 255) — the buffer has
     the app's content only (panels claim nothing in cramped monocle; the FAB has not yet
     drawn) — check the FAB's footprint against the window's current bottom row and store it.
     The flag is set **in both branches** so it is cleared when leaving cramped monocle
     (otherwise a stale `true` would falsely pad the first frame after re-entering):
      ```rust
      if wm.is_monocle_cramped() {
          // The FAB's label is the shared menu icon; its DISPLAY width (not char count)
          // is the footprint the app must not collide with. Wide glyphs (Nerd Font,
          // emoji) span 2 terminal columns but a single char, so `.chars().count()`
          // would under-size the footprint and miss collisions under the label's left
          // edge. Matches the FAB component's own width (also display-based).
          let fab_width = {
              let ctx = wm.component_context(true);
              let icon = term_wm_ui_components::helpers::menu_icon(ctx.app_name());
              unicode_width::UnicodeWidthStr::width(icon.as_str()) as u16
          };
          let has = if fab_width == 0 {
              false
          } else {
              let wa = wm.managed_area();
              let bottom_y = wa.y + i32::from(wa.height).saturating_sub(1);
              // Recompute the footprint from the CURRENT frame's geometry: the FAB is
              // right-aligned to the screen, so x = right_edge - fab_width. Trusting a
              // stored x would desync after a resize (x can exceed the new width,
              // clamping the range to empty and dropping valid content).
              let x_start = wa.x + i32::from(wa.width).saturating_sub(i32::from(fab_width));
              let x_end = wa.x + i32::from(wa.width);
              if let Some(rb) = backend.as_any_mut().downcast_mut::<RatatuiBackend>() {
                  row_has_content_in_range(&rb.buffer, x_start, x_end, bottom_y)
              } else {
                  false
              }
          };
          wm.set_bottom_content_flag(has);
      } else {
          wm.set_bottom_content_flag(false); // clear stale flag when leaving cramped monocle
      }
      ```
      Notes: `fab.fab_rect()` is NOT used — it is a `WmFabComponent`-only method and
      `get_semantic_component` returns the generic `L: WmComponent`. The `backend` is
      downcast locally (matching the empty-state block) so no `&mut` borrow of `backend` is
      held across `render_panels` / the FAB render below. Requires adding
      `unicode-width = { workspace = true }` to the root `term-wm` crate's `[dependencies]`.
      `wm.managed_area()` returns `LayoutRect` (`crate::Rect`, i32 x/y, u16 width/height) —
      NOT `ratatui::layout::Rect` — so `wa.y + i32::from(wa.height).saturating_sub(1)` and
      `wa.x + i32::from(wa.width).saturating_sub(...)` are `i32 + i32` and need no casts.
5. `crates/term-wm-sys-ui-components/src/wm_fab.rs`: FAB stays at `y = area.y + area.height - 1`
   (fixed on the bottom row). Change the width computation from `label.chars().count()`
   to `unicode_width::UnicodeWidthStr::width(label.as_str())` so the FAB's rendered
   footprint and hitbox match its true display columns (wide-glyph safe) and stay in lockstep
   with the detection footprint in `src/lib.rs`.

## Part 2 — Clicking a tabbar title scrolls it fully into view (unchanged)

Implemented in `crates/term-wm-ui-components/src/tab_bar.rs`:
- `scroll_into_view_target(h, lx, width, viewport_width, max_scroll)` fully reveals a tab,
  **left-aligning tabs wider than the viewport** (clippy-clean merged branch).
- `pending_scroll_to: Option<K>` set in `handle_press` (no `h_scroll` mutation mid-event);
  consumed in `render()` only when `drag_state.is_none()` (checked before `.take()`), so a
  held button preserves the pending target. Auto-scroll block uses the shared helper.
- Test helper `render_bar` now calls `bar.begin_frame()` (matches production
  `WmTopPanelComponent` at wm_top_panel/mod.rs:87).
- Tests (all passing): click-scroll fully in view, oversized left-align, already-active
  reveal, drag-reorder-no-desync.
