# Plan: Reserve a bottom chrome row for the FAB + click-to-scroll tab into view

Two usability changes. Part 1 was redesigned: **the FAB stays fixed on the bottom row;
the application viewport is padded up by reserving a bottom chrome row in the layout
engine.** Part 2 (tabbar click-to-scroll) is unchanged and already implemented in the
working tree.

---

## Part 1 — Reserve the bottom row for the FAB (viewport padding, FAB stays put)

### Problem (revised)
Lifting the FAB only relocates occlusion from row 23 to row 22. Instead, the FAB always
stays at the absolute bottom-right, and the focused application window is given one fewer
row in cramped monocle so the bottom row is dedicated chrome space.

### Design
In cramped monocle (`is_monocle_cramped()`), shrink `managed_area.height` by 1 in
`register_managed_layout`. This propagates automatically:
`managed_area` → `layout.regions(managed_area)` (layout.rs:435) → `full_region_for_key` →
`region.bounds` (engine.rs:80) → `apply_monocle_culling(focused, screen = managed_area)`
(engine.rs:56, draw_plan.rs:137) → `surface.dest` (src/lib.rs:105-110) →
`composite_window` → `content_rect` → `ScrollViewComponent` → `TerminalComponent` area →
`Pane::resize` → `Pty::resize` → `TIOCSWINSZ`/SIGWINCH (terminal.rs:236-246, pty.rs:406-451).

So the PTY is resized to one fewer row each frame, the app receives SIGWINCH and
reformats its status line one row up natively, and the reserved bottom row is never
overlapped. Scrollback survives (vt100 grid is reflowed in place, not recreated).

The FAB component is **reverted to its original code**: it renders at
`y = area.y + area.height - 1` with the full-screen `area` passed at src/lib.rs:261 —
exactly the reserved row.

### Why static, not content-detected
Content-based padding is unstable: once the PTY is resized, the app redraws shorter, the
bottom row empties, detection flips back, and the layout oscillates between two sizes.
A permanent reservation removes runtime buffer scanning entirely and is deterministic.

### Changes
1. `crates/term-wm-core/src/window/window_manager/layout.rs`
   - Add const `FAB_RESERVED_ROWS: u16 = 1`.
   - Add free helper:
     ```rust
     /// Shrink `area` by the FAB's reserved bottom row when the FAB is shown in
     /// cramped monocle. `height` is never shrunk below 1.
     fn reserve_fab_row(area: Rect, cramped_monocle: bool) -> Rect {
         if cramped_monocle && area.height > 1 {
             let mut a = area;
             a.height = a.height.saturating_sub(FAB_RESERVED_ROWS);
             a
         } else {
             area
         }
     }
     ```
   - In `register_managed_layout`, immediately after `self.bottom_claimed = bottom_rect;`
     (line 385) and before `let prev_managed = self.managed_area;` (line 386):
     ```rust
     // Cramped monocle: the FAB occupies the bottom-right of the screen. Reserve
     // the bottom row for it so the focused window never renders beneath it; the
     // PTY resizes to the shorter area and apps format status lines above the row
     // natively (no buffer scanning, no oscillation).
     self.managed_area = reserve_fab_row(managed_area, self.is_monocle_cramped());
     ```
     (Replace the current `self.managed_area = managed_area;` line.)
2. Revert `crates/term-wm-sys-ui-components/src/wm_fab.rs` to HEAD
   (`git checkout -- crates/term-wm-sys-ui-components/src/wm_fab.rs`). This removes
   `FAB_LIFT_OFFSET`, `bottom_row_has_content`, the render() lift logic, and the 5
   added tests from the earlier abandoned approach. The FAB stays at the bottom-right.

### Command-menu interaction (verified, no conflict)
The monocle bottom-panel hints overlay already renders at
`full_area.y + full_area.height - 1` (draw_plan_renderer.rs:847-852) — the same row the
FAB uses when the menu is closed. When the command menu opens the FAB hides and the hints
occupy the reserved row; when it closes the FAB reappears. No resize churn.

### Tests (in the `mod.rs` tests module, alongside `handle_mouse_focus_click_skipped_in_monocle`)

## Part 2 — Clicking a tabbar title scrolls it fully into view (unchanged)

Already implemented in `crates/term-wm-ui-components/src/tab_bar.rs`:
- Free helper `scroll_into_view_target(h, lx, width, viewport_width, max_scroll)` that
  fully reveals a tab, **left-aligning tabs wider than the viewport**.
- New field `pending_scroll_to: Option<K>` set in `handle_press`'s tab branch — `h_scroll`
  is NOT mutated mid-event (keeps `DragState::grab_col` consistent with the last render).
- In `render()`, the pending target is consumed **only when `drag_state.is_none()`**
  (checked before `.take()`, so the pending target survives a held button), and the
  auto-scroll block now uses the shared helper (gains the left-align fix for keyboard/
  structural focus changes).

### Remaining fix (test helper)
The 4 new tests fail because the test helper `render_bar` does not replicate the
production lifecycle: `WmTopPanelComponent` calls `self.bar.begin_frame()` before render
(wm_top_panel/mod.rs:87), which clears `item_hits`; `render()` does NOT clear them itself.
Without it, `item_hits` accumulate across renders and stale hits shadow the new ones.

Fix: add `bar.begin_frame();` as the first line of `render_bar` in `tab_bar.rs`'s tests
module. This is safe for existing tests (they render once or assert only `h_scroll`).

### Tests (already written, should pass after the helper fix)
- `clicking_partially_visible_tab_scrolls_it_into_view`: press (h_scroll unchanged, pending
  set), render → tab fully within viewport (h_scroll 40 → 44).
- `clicking_oversized_tab_left_aligns`: single ≥40-col tab in a 20-wide bar, scrolled to
  max → click → render → h_scroll back to `lx` (0).
- `clicking_active_tab_reeveals_it`: already-active half-hidden tab → click → render →
  revealed via the pending path (auto-scroll guard doesn't trip).
- `drag_reorder_still_works_after_pending_scroll`: press (pending set), drag (h_scroll
  untouched, drop index correct, no drift), render while held (pending retained), release
  → `Reorder { key, target_index }` commits, next render applies the scroll.

Manual:
- Run term-wm in a narrow terminal (cramped monocle) with opencode: the window is one row
  shorter, opencode's bottom border sits on the second-to-last row, and the FAB floats in
  the reserved bottom row. In a plain shell, typing in the last visible row never collides
  with the FAB.
- Tabbar: open enough windows to overflow the tab strip; click a half-hidden tab → it
  scrolls fully into view immediately; a very long title in a narrow terminal left-aligns.
