# Plan: Fix terminal scrollbar losing "stuck to bottom" on resize (esp. monocle)

## Problem
Resizing the physical terminal window while **in monocle mode** (and, more mildly, resizing
into/out of monocle) makes the terminal's scrollback "stuck to bottom" state break: the
scrollbar jumps partway up and the view shows duplicate prompts spaced about a screen-height
apart. Plain window resizes outside monocle are barely affected.

## Root cause
`TerminalComponent::render_screen` (crates/term-wm-ui-components/src/terminal.rs:512-530)
decides follow-tail vs. scroll-into-history in the `current_sb == 0` branch:

```rust
if current_sb == 0 {
    if view_offset < self.last_max_scrollback.get().saturating_sub(1) {
        let target_sb = used.saturating_sub(view_offset);
        pane.set_scrollback(target_sb);        // scroll into history ← BUG path
    } else {
        handle.scroll_vertical_to(usize::MAX); // follow tail
    }
}
```

On a resize both inputs are **stale**:
- `view_offset` comes from `ctx.viewport().offset_y`. The `ScrollView` clamps it
  (scroll_view.rs:451-462) against the **old** `content_height` and the **new** viewport
  height *before* the terminal's `set_content_size` (terminal.rs:505) updates the content —
  so a height grow pushes `offset_y` down (e.g. 100 → 75), and a height shrink with stale
  content can strand it too.
- `last_max_scrollback` holds the previous frame's `used`, updated only *after* the decision
  (terminal.rs:531).

When `view_offset < last_max_scrollback - 1`, the sync mistakes this resize artifact for a
genuine user scroll and calls `pane.set_scrollback(target_sb)`, dragging the pane into the
scrollback — the view shows history ("halfway up") and the live shell prompt is duplicated
against an old scrollback copy a screen apart.

**Why monocle is worse:** in monocle the window fills the screen, so resizing the physical
window reflows the PTY repeatedly (window resize + the FAB content-dodging reservation
toggling `managed_area` by ±1 row), firing several resize/reflow frames in a row — each
re-entering the buggy branch. `current_sb == 0` means the pane is genuinely at the tail (a
real user scroll sets `current_sb > 0` on the next frame), so on a content change following
the tail is always correct.

## Fix
Use an **explicit resize flag** (not a `used`-change heuristic — that would misclassify
normal output bursts such as `tail -f` as resizes and snap the user back to the tail while
they're trying to scroll up).

1. `TerminalComponent::render` (terminal.rs:236-246): capture the resize before updating
   `last_size`, and pass it to `render_screen`:
   ```rust
   let size = (area.width, area.height);
   let resized = size != self.last_size.get();
   if resized {
       // ... existing pane.resize + last_size.set(size) ...
   }
   // ...
   self.render_screen(backend, area, ctx, resized);
   ```
2. `render_screen` signature gains `resized: bool`.
3. In the `current_sb == 0` branch (terminal.rs:514-520), use `resized` instead of a
   `used`-mismatch heuristic:
   ```rust
   if current_sb == 0 {
       if resized {
           // Resize artifact: view_offset is stale (the ScrollView clamped it
           // against old geometry before set_content_size ran). Stay at the tail
           // so the prompt doesn't duplicate / jump partway up.
           handle.scroll_vertical_to(usize::MAX);
       } else if view_offset < self.last_max_scrollback.get().saturating_sub(1) {
           // No resize: a moved view_offset is a genuine user scroll.
           let target_sb = used.saturating_sub(view_offset);
           pane.set_scrollback(target_sb);
       } else {
           handle.scroll_vertical_to(usize::MAX);
       }
   }
   ```
   `handle.scroll_vertical_to(usize::MAX)` re-pins the scrollbar thumb to the new bottom
   (applied next frame by the ScrollView) while the pane stays at `scrollback 0`, so the
   rendered content is the tail — no duplicate prompts. Streaming-output scroll-up is
   unaffected because `resized` is false on those frames.

## Tests (crates/term-wm-ui-components/src/terminal.rs, scroll-sync module)
- Add a test-only helper `set_last_size(&mut self, w, h)` (mirrors `set_last_scrollback` /
  `set_last_max_scrollback` at terminal.rs:459-465) so tests can force `resized`.
- Update `scroll_sync_current_sb_zero_view_offset_below_last_max_syncs_scrollback` → rename
  to `scroll_sync_current_sb_zero_resize_follows_tail`: prime `last_size` to a non-matching
  value (e.g. `(79, 24)`) so render sees `resized == true`, `view_offset` below the stale
  max → expect follow-tail (`scrollback` stays 0, `scroll_vertical_to(max)` pending).
- Add `scroll_sync_current_sb_zero_genuine_scroll_syncs_scrollback`: `last_size` matches the
  render area (`resized == false`), `used == last_max_scrollback`, `view_offset == 50` →
  `set_scrollback(used - 50)` — a real scroll is still honored.
- Existing `...view_offset_at_last_max_follows_tail` / `...view_offset_greater_than_last_max_follows_tail`
  (resized false, at-tail) still pass unchanged.
