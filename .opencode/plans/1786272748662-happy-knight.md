# Plan: Drain-Synchronized PTY resize — perf pass (hoist master fd) + verification

## Status
The drain-sync refactor is implemented (shared plumbing, Unix self-pipe wake, reader-owned
`apply_resize` at the pipe-drain boundary, `Pty::resize` → request-only). This amendment
addresses the review points:

1. **`Pty::resize` is already gutted** (verified, pty.rs:519-535): it only records
   `pending_resize` and signals the wake — no parser lock, no `set_size`, no `ioctl` on the
   UI thread. (The plan's original Phase 3 was done; the field is now the shared `size` Arc,
   not a `pty_size`.) No change needed.
2. **Hot-path Mutex contention in the reader** (actionable): `master_fd` is re-fetched under
   `master.lock()` on EVERY inner-drain iteration (pty.rs:929 outer poll, :961 inner
   zero-poll). During a fast stream this locks the same Mutex the UI thread holds for
   `process_group_leader` and the reader holds in `apply_resize`, thousands of times/sec.

## Change: hoist `master_fd` out of the reader loop
In `parser_read_loop` (pty.rs:~900), fetch the fd **once** after setup, before the loop:

```rust
// The pty master fd never changes — fetch it once to avoid a Mutex lock on every
// drain iteration.
#[cfg(unix)]
let master_fd = master
    .lock()
    .unwrap_or_else(|err| err.into_inner())
    .as_raw_fd()
    .unwrap_or(-1);
```

Then use the hoisted `master_fd` in both the outer `poll([master_fd, wake_read_fd], -1)` and
the inner drain `poll(&mut pfd { fd: master_fd }, 0)` — **no `master.lock()` in the loop
body**. This cuts the reader's per-iteration Mutex traffic to zero in the steady-state drain.

## Follow-up: reader startup blocked on `Clipboard::new()`
The reader's one-time setup (`clipboard.unwrap_or_else(Clipboard::new)`, pty.rs:922) runs
BEFORE the loop and can block on the arboard pasteboard handshake for a second or more,
delaying the first drain/apply (which is why a new drain-sync resize test must poll up to 5s).
Consider deferring clipboard init to the first OSC 52 sequence (lazy `OnceLock`) so reader
startup — and the first drain-synchronized resize — is not gated on the clipboard.

## Tests
- Keep the three drain-sync tests; make the "idle" wake-path test robust to the clipboard
  startup delay (already polls up to 5s). After the lazy-clipboard change they should pass
  without the long poll.
- Add a stress check that a pending resize applies during a fast stream at the 64 KB drain
