# Plan: Drain-Synchronized PTY resize (reader applies resize when the pipe is empty)

## Problem
Drag-resizing fires `Pty::resize` ~60×/sec from the UI thread, reflowing the vt100 grid and
issuing `ioctl(TIOCSWINSZ)` (SIGWINCH) mid-shell-draw. Zsh writes `administra`, the grid
re-wraps under it, Zsh finishes `tor@…` on the new line, and its `\x1b[J` clears only the
bottom fragment — leaving torn, duplicated prompt text. A timer/debounce is a bandage; the
correct fix is **event-driven**: never resize (reflow OR ioctl) while the shell is mid-write.

## Architecture: the reader thread owns resize, applied at the pipe-empty drain
- The **UI thread** only records a pending size (`pending_resize`) and wakes the reader. It
  never touches the grid or the OS for resizing.
- The **reader thread** reads/parses bytes (unchanged). The instant it detects the pipe is
  empty (`EAGAIN` / WouldBlock after a non-blocking drain, or the wake is signalled and a
  drain probe finds no data), it applies the pending resize: vt100 `set_size` reflow
  (reusing the fork's pull-down / bottom-anchor logic), the shrink `ESC[S` cursor push, the
  tracker resize, and `master.resize` (SIGWINCH) — all while holding the parser lock, so the
  grid width never changes mid-shell-write and the shell gets SIGWINCH only when idle.

## Phase 1 — Shared plumbing (`crates/term-wm-pty-engine/src/pty.rs`)
1. Wrap `master: Box<dyn MasterPty + Send>` in `Arc<Mutex<Box<dyn MasterPty + Send>>>`
   (Pty keeps a clone; the reader gets one). Route the main thread's `process_group_leader`
   / `as_raw_fd` / `take_writer` through the lock. `writer` is unchanged (separate handle).
2. Add `pending_resize: Arc<Mutex<Option<PtySize>>>` (set by the UI, consumed by the reader).
3. Add a wake primitive shared with the reader:
   - Unix: `eventfd` (or a `pipe` self-pipe). The UI writes a byte to wake a blocked reader.
   - Windows: a manual-reset `Event` handle. **Dependency:** portable-pty's `MasterPty` does
     not expose the ConPTY read handle, so add a small `as_raw_handle()` accessor (or a
     `resize_wake` handle obtained from it) to the workspace's portable-pty dependency —
     either a fork or a feature-gated patch. This is the one upstream touch required.
4. New const `PTY_DRAIN_RESIZE` note: no timer anywhere; all pacing comes from pipe state.

## Phase 2 — Reader loop restructure (`parser_read_loop`, pty.rs:782+)
Make the reader detect the drain and apply pending resizes:
1. Set the reader fd non-blocking (Unix: `fcntl(O_NONBLOCK)` on the fd from
   `master.as_raw_fd()`; Windows: after exposing the handle, use `PeekNamedPipe`/overlapped
   peek rather than non-blocking). `ParserReadLoopArgs` gains `pending_resize`,
   `master: Arc<Mutex<Box<dyn MasterPty + Send>>>`, and the wake fd/handle.
2. Restructure the loop:
   ```
   const MAX_DRAIN_BYTES: usize = 64 * 1024;   // starvation bound (see below)
   loop {
       poll([reader_fd, wake_fd], -1)          // block for data OR a resize wake
       if wake readable: clear it; then drain-probe the reader (non-blocking)
       drain: let mut drain_bytes = 0; loop { match nonblock_read() {
           Ok(n)  => process chunk (existing parse/status/osc52 path),
                    drain_bytes += n;
                    if drain_bytes >= MAX_DRAIN_BYTES { break; }   // anti-starvation
           WouldBlock => break,                 // pipe empty → shell idle
           Err(..) => break,
       } }
       // ── DRAIN BOUNDARY ── apply any pending resize here:
       if let Some(size) = pending_resize.take() {
           apply_resize(size);                  // see Phase 3
       }
   }
   ```
   Because resize only fires at the drain boundary (pipe empty) — or after the 64 KB
   starvation bound — the grid is never reflowed mid-write and SIGWINCH never interrupts a
   shell draw. A resize request while the reader is blocked is delivered via the wake.
   **Anti-starvation:** discrete shell actions (`ls`, typing, prompt redraws) are ≪ 64 KB and
   always hit `WouldBlock` first → flawless tear-free resizing. A continuous flood (`yes`,
   busy log, compilation) that never returns `WouldBlock` now applies the pending resize
   every 64 KB (mid-stream tearing is invisible during a 60fps flood, and SIGWINCH still
   reaches the app), keeping the grid attached to the physical window bounds.
   - Windows: replace `poll` with `WaitForMultipleObjects` on the ConPTY handle + wake event,
     then `PeekNamedPipe` (to probe available bytes) + an overlapped/blocking read to drain;
     the drain boundary + `MAX_DRAIN_BYTES` logic is identical. Use `PeekNamedPipe`, not
     `O_NONBLOCK`, for the Windows availability check.
3. `apply_resize(size)` (private, runs on the reader thread): replicate the current
   `Pty::resize` emulator steps — lock the parser, shrink `ESC[S` push-up (using the current
   parser rows), `screen_mut().set_size(...)`, unlock; `tracker.resize(size.rows)`;
   `master.lock().resize(size)` (ioctl/SIGWINCH); set `self.pty_size` (via a shared
   `Arc<Mutex<PtySize>>` or a callback, since the reader owns it now).

## Phase 3 — `Pty::resize` becomes a request (pty.rs:406-451)
`Pty::resize` (same signature, still `Pane::resize` → UI entry) becomes:
```rust
pub fn resize(&mut self, size: PtySize) -> PtyResult<()> {
    if size.rows < 2 || size.cols < 2 { return Ok(()); }
    *self.pending_resize.lock().unwrap_or_else(|e| e.into_inner()) = Some(size);
    self.wake_reader();               // eventfd / event signal
    Ok(())
}
```
No reflow, no ioctl, no parser mutation on the UI thread. The parser stays at the last
drain-applied size until the reader applies the request at the next drain boundary (≈
immediate for an idle shell — the pipe is already empty).

## Phase 4 — Tests (`crates/term-wm-pty-engine/src/pty.rs` test module, real Pty)
- `resize_is_deferred_until_pipe_drained`: spawn a Pty; request `resize(B)` while the child is
  idle (pipe empty) → after a short wait, the parser is at size B (reader applied at the
  drain) and the OS child sees the new size.
- `resize_does_not_interrupt_mid_write`: feed a large output burst; request `resize` mid-burst;
  assert the grid was not reflowed until the burst fully drained (no width change mid-stream).
- `rapid_resizes_coalesce_to_final`: request `resize(B)`, `resize(C)`, `resize(D)` rapidly;
  after drain, the parser + OS are at D only.
- Existing reader/reflow tests must still pass (they use the parser/reader paths directly).

## Verification
```bash
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test -p term-wm-pty-engine
cargo test   # full suite
```
Manual (Unix primary): `term-wm`, run a long-prompt command (`administrator@…`), drag-resize
rapidly in monocle — existing text re-wraps only between shell writes, prompt draws once
cleanly at the final width, no horizontal tearing or duplicate fragments. Also verify with a
busy stream (`yes`, a long `make`) that resizing still tracks the window (applied at each
64 KB drain bound, mid-stream tearing invisible during a flood).

## Risks / notes
- **Windows**: requires the portable-pty handle exposure (Phase 1) and can only be verified on
  a Windows host/CI — flag for a Windows run.
- This is a significant concurrency change to the PTY engine; the parser lock already
  serializes reader-apply vs UI-render, and the existing `Arc<Mutex<Parser>>` is reused.
- No timers added anywhere; all pacing is pipe-state driven, per the design.
