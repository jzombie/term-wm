# Fix #258: Tiled windows with void space above/below have no resize handle

## Problem (from issue #258)

"Tiled drag resize regions should always be present."

- **Scenario 1**: Two windows open; tile one into the bottom-right/left quadrant. There is no **top** resize handle on that window.
- **Scenario 2**: One window open; snap it to the top half. It fills half the vertical space but cannot be resized vertically.

In both cases the window sits next to empty `Void` space, and no split-handle (resize region) is exposed along the boundary with that empty space.

## Root cause

When a window is tiled into a quadrant / snapped against an edge while other space is empty, the tiling tree is a **resizable `Split` whose sibling is a `LayoutNode::Void`**, e.g.:

```
Scenario 2 (snap-to-top):        Scenario 1 (bottom-left quadrant):
Split(Vertical, resizable)       Split(Horizontal, resizable)
├── Leaf(window)                 ├── Split(Vertical, resizable)
└── Void                         │   ├── Void            ← space above
                                 │   └── Leaf(window)
                                 └── Leaf(other window)
```

The layout engine *does* generate a `SplitGap` for these leaf↔void boundaries (`layout_recursive` in `crates/term-wm-layout-engine/src/tiling.rs` only requires `resizable && children.len() > 1`), so `layout.handles()` returns them.

They are then dropped by the **split-handle filter** in
`crates/term-wm-core/src/window/window_manager/layout.rs:487-502`
(inside `update_layout`, called from `register_managed_layout`):

```rust
let filtered_handles: Vec<SplitHandle> = handles
    .into_iter()
    .filter(|handle| {
        let Some(LayoutNode::Split { children, .. }) =
            layout.root().node_at_path(&handle.path)
        else { return false; };
        let left = children.get(handle.index);
        let right = children.get(handle.index + 1);
        left.is_some_and(|node| node.subtree_any(|key| !self.is_window_floating(key)))
            && right.is_some_and(|node| node.subtree_any(|key| !self.is_window_floating(key)))
    })
    .collect();
```

`LayoutNode::Void` has **no leaves**, so `subtree_any(...)` returns `false` for the void side, and the handle is discarded. Result: no resize region against the void space.

The drag machinery already supports void siblings: `apply_drag` (`crates/term-wm-layout-engine/src/tiling.rs:274`) treats a `Void` child as a weighted split participant, so dragging a leaf↔void boundary correctly changes the window's size (the void grows/shrinks). Rendering/masking (`render_handles_masked` in `src/lib.rs`) and hover occlusion already handle void-adjacent handles correctly, because void space is not a window region. **The only blocker is the filter.**

## Fix (one surgical change)

`crates/term-wm-core/src/window/window_manager/layout.rs` — relax the filter so a handle is kept when a boundary separates **real tiled space from either another tiled window or empty `Void` space**, while never exposing handles between two empty regions:

- Side is empty `Void` space (no leaves at all) → eligible.
- Side contains at least one tiled (non-floating) window → eligible.
- Side contains leaves but only floating windows → **not eligible** (floating windows are resized by their own chrome; this preserves the pre-existing "don't show tiling handles against floating-only subtrees" behavior, incl. the tiled→maximized case where the window becomes floating).
- **Invariant**: at least one side must contain a tiled window. Otherwise a `[Void, Void]` split would pass the side eligibility on both sides and expose a phantom handle between two empty regions.

Concretely, replace the closure body with:

```rust
let side_ok = |node: &LayoutNode<WindowKey>| {
    // Eligible: empty Void space (no leaves) OR a subtree containing a tiled
    // window. Sides whose only windows are floating are resized via floating
    // chrome, not tiling split handles.
    !node.subtree_any(|_| true) || node.subtree_any(|key| !self.is_window_floating(key))
};
let has_tiled = |node: &LayoutNode<WindowKey>| {
    node.subtree_any(|key| !self.is_window_floating(key))
};

// in the filter closure, after resolving `left`/`right`:
left.is_some_and(side_ok)
    && right.is_some_and(side_ok)
    && (left.is_some_and(has_tiled) || right.is_some_and(has_tiled))
```

(`subtree_any` is the existing helper on `LayoutNode`; for `Void(_)` it returns `false`, so `!subtree_any(|_| true)` is `true` only for leaf-free/empty subtrees. The `has_tiled` conjunct guarantees every retained handle has at least one real tiled window on one side, so a degenerate `[Void, Void]` split can never produce a phantom handle.)

No layout-engine or render changes are needed.

## Tests

Add regression tests that reproduce both scenarios through `tiling_handles()` and exercise the drag.

### 1. Unit tests — `crates/term-wm-core/src/window/window_manager/mod.rs` (test module, next to the existing `setup_tiling_with_gap` / `layout_handle_*` tests)

- **`split_handle_present_next_to_void`** (Scenario 2):
  Build `LayoutNode::Split { direction: Vertical, children: [Leaf(k0), Void(id)], weights: [1,1], resizable: true }` over an 80×24 `managed_area`, `set_managed_layout` + `register_managed_layout`. Assert `wm.tiling_handles()` is non-empty and the handle's gap rect sits at the vertical boundary (row ≈ 12).
- **`split_handle_drag_resizes_window_against_void`**:
  Same tree; register handle hitboxes (mirror `setup_tiling_with_gap`), dispatch Press on the gap, Drag up a few rows, Release, re-`register_managed_layout`, and assert the window's `height` grew and the void side shrank.
- **`split_handle_present_for_bottom_quadrant`** (Scenario 1):
  Build `Split(H)[ Split(V)[Void, Leaf(k0)], Leaf(k1) ]`, register, assert handles include the vertical gap *between the Void and k0* (the "top resize handle" of the bottom-left window — `direction == Vertical` and the gap rect spans the left half at row ≈ 12).
- **`split_handle_suppressed_between_dual_voids`**:
  Build `Split { children: [Void(1), Void(2)], resizable: true }` (regression for the `has_tiled` guard), register, and assert `wm.tiling_handles()` is **empty** — no phantom handle between two empty regions.

### 2. Integration test — `tests/integration_tiling.rs`

- **`tiled_window_with_void_above_below_has_resize_handles`**:
  Use the existing `setup_with_resizable`-style harness (`render_app` + `advance_frame`), build a `[Leaf, Void]` vertical resizable split via `set_managed_layout`/`register_managed_layout`, `advance_frame`, then assert `wm.tiling_handles()` is non-empty and a Press/Drag on the handle is `Consumed` and changes the window's height after the next frame.

Existing tests that rely on the filter are all leaf↔leaf splits (`wm_with_two_windows`, `setup_tiling_with_gap`, `close_all_windows_then_tile_new_does_not_phantom` which only asserts regions) — none assert void-adjacent handles are *absent*, so no existing test should break.
