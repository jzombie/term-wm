# Fix: `term-session` new channels spawn in daemon's cwd, not the caller's

## Root cause

`term-session` is a client that talks to a long-lived detached gateway daemon over muxio IPC. When a NEW channel is created, the PTY child is spawned **inside the daemon process**, and its working directory is set to `std::env::current_dir()` evaluated in the daemon — which is frozen at daemon startup (inherited from whoever first auto-spawned it). The caller's cwd is **never transmitted**: the `Spawn` RPC payload (`crates/term-session-muxio-service-definitions/src/methods.rs:69-74`) carries only `cmd`, `cols`, `rows`.

Chain:
1. `crates/term-session-client/src/lib.rs:405-413` — client sends `(cmd, cols, rows)`; never reads its own cwd.
2. `crates/term-session-server/src/session_server.rs:627` decodes 3-tuple; line 699 calls `Session::spawn(...)`.
3. `crates/term-session-server/src/session.rs:21-22,49-50` — `builder.cwd(std::env::current_dir())` = **daemon's** cwd.
4. `crates/term-session/src/auto_spawn.rs:127-154` — daemon inherits the first launcher's cwd and keeps it forever.

Per user decision: respawn behavior doesn't matter (live sessions are joined, cwd is irrelevant); always use the spawning client's cwd for any new spawn.

## Next step (build): enforce a LOSSLESS cwd round-trip

The review follow-up (comments at `to_string_lossy` + `resolve_cwd`/`Session::spawn`
unit tests) was implemented and is in the working tree (uncommitted). The user now
wants the lossy `to_string_lossy` on the wire to be **replaced by a guaranteed
byte-for-byte lossless round-trip**. This section supersedes the lossy parts of
the previous step (the client/mock comments that justified lossiness get removed;
the unit tests are upgraded to assert raw-byte fidelity).

### Constraint: codec types
- Wire codec is **bitcode 0.6.9** (`Encode`/`Decode` derive; serde feature off).
  It natively supports `Vec<u8>` / `Vec<u16>` but **not** `PathBuf`/`OsString`.
- Client and daemon always run on the same host (local IPC), so a
  **platform-native byte encoding** is safe and lossless on every scoped target:
  - Unix: `OsStrExt::as_bytes()` / `OsStr::from_bytes()` (arbitrary bytes).
  - Windows: `encode_wide()` → u16 LE byte pairs / `OsString::from_wide()` (WTF-16).
  - other: best-effort UTF-8 fallback (unreachable in scope; documented).

## Next step (build): inherent `encode`/`decode` + concrete `From` for `PathWire`

User request: make `PathWire` self-contained with inherent `encode`/`decode`
methods (plus `to_path_buf` alias) **and** concrete `From` conversions (the
generic `P: AsRef<Path>` form is rejected — inference ambiguity E0283 and
coherence fragility vs the reflexive `From<T> for T`). All changes are confined
to `crates/term-session-muxio-service-definitions/src/path_wire.rs` plus one
line in `crates/term-session-server/src/session.rs`; purely additive.

Verified no shadowing: the only `.encode(`/`.decode(` method-syntax calls in the
tree are unrelated `base64` encodes; `PathWire`'s `bitcode::{Encode, Decode}` are
used via derive only, so inherent methods can't collide with trait method-syntax

### Design note — API shape
- `encode_path` / `decode_path` remain the canonical, pub, module-level core
  (they carry the platform-cfg logic and are doc-referenced + tested).
- Inherent `PathWire::encode` / `decode` / `to_path_buf` are thin delegates

- `PathWire::from(x)` now means *either* thing depending on source type:
  - `From<Vec<u8>>` (existing): wrap **already-encoded wire bytes**.
  - `From<&Path>` / `From<PathBuf>` / `From<&str>` / `From<String>` (new):
    **encode a path**.
  Document the split on the struct so callers can't misread it.

## Next step (docs): explicitly document the same-host / no-cross-platform sharing

User feedback: the existing docs mention "same host" only in passing and never
state the **negative** — that `PathWire` bytes are NOT portable between Windows
and Unix, and that mixing hosts silently garbles the path rather than erroring.
This is a documentation-only change (no behavior / wire-format change).

### Facts to document (per user's architectural analysis)
- `PathWire` is designed for **same-host local IPC**: client and gateway daemon
  run on the same OS (Unix↔Unix raw `OsStr` bytes; Windows↔Windows UTF-16 LE
  `u16` pairs). Paths are host-native and only meaningful on the producing host
  (`C:\...` is invalid as a Unix cwd and vice versa).
- **Not supported:** cross-platform path sharing or heterogeneous daemon-state
  migration (serialize a Windows daemon's state, restore on Linux).
- **Supported via SSH:** remote sessions work because the daemon runs on the
  remote host, so `cwd` is resolved in the remote OS's context.
- **Wire format is not self-describing:** `PathWire` is packed as a raw byte
  array with no platform tag. Forwarding Unix bytes to a Windows daemon would be
  parsed as misaligned UTF-16 pairs → silent garble, not a structured error.
- Cross-host translation would require a canonical encoding (e.g. WTF-8) — out
  of scope for the current same-host design.

### 1. `crates/term-session-muxio-service-definitions/src/path_wire.rs` module doc (lines 1-9)
Append an explicit paragraph after the current "same host ... losslessly" text:
- Same-host only; cross-platform sharing NOT supported.
- Bytes are opaque to the other platform and must never be forwarded
  host-to-host; wire format carries no platform tag, so a cross-host decode
  garbles silently instead of erroring.
- SSH remote sessions are unaffected (daemon resolves `cwd` on the remote host).
- Canonical encoding (e.g. WTF-8) would be required for cross-host migration;
  deliberately not chosen.
