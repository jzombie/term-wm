## Remaining (this session)

### Problem: Intermittent black screen after resize

`has_new_data` is computed before `Event::Resize` runs. When a resize event arrives (not PTY data), `has_new_data` is false, and the render gate skips `render_frame()`. The resized-but-blank parser is never drawn.

### Existing fix (already correct): `force_render` in `Event::Resize`

```rust
Event::Resize(w, h) => {
    let size = PtySize { rows: h, cols: w, .. };
    if let Err(err) = pane.resize(size) {
        tracing::warn!(error = %err, "resize failed");
    }
    force_render = true;   // <-- forces render gate open
}
```

This is correct and must be kept. The render gate `if has_new_data || force_render` already handles the black screen.

### Problem: DECAWM auto-scroll row duplication on Client B

When Client A resizes, the server broadcasts `OnPtyResized` and the PTY process writes redraw bytes. Client B often receives PTY redraw bytes (via `push_rx`) **before** the `OnPtyResized` RPC. The PTY bytes are formatted for the new larger grid, but Client B's VTE parser still has the old smaller grid. Writing to the bottom-right cell triggers ANSI auto-wrap (`DECAWM`), scrolling the terminal up and duplicating the last row.

### Existing fix (already correct): `apply_pending_resize` at two sites

The `apply_pending_resize` closure checks `resize_pending` at Site 1 (top of loop) and Site 2 (inside `push_rx` arm, before `parser.process`). This resizes the parser before PTY bytes are processed, preventing the DECAWM scroll.

### FATAL BUG: `\x1b[2J` in `apply_pending_resize`

The current `apply_pending_resize` issues `out.write_all(b"\x1b[0m\x1b[2J\x1b[H")` which clears the **host terminal** but leaves the **VTE parser** intact. On the next `render_frame()` call, the parser's stale grid is dumped onto the freshly-cleared screen → permanent corruption.

Furthermore, writing `\x1b[2J` interrupts the PTY output stream: the PTY process may emit redraw bytes that arrive milliseconds after the clear, but if no more data comes, the screen stays black (the original echo-loop problem from Root Cause A).

**Directive:** Remove ALL manual `\x1b[2J` injections. Host screen state must be updated exclusively through `render_frame()`.

## Fixes

### Fix 1: Disable DECAWM + post-cell margin sanitation

Wrap `render_frame` output with `\x1b[?7l` (disable auto-wrap) before writing cells, and `\x1b[?7h` (restore) after. This prevents writing to `(cols-1, rows-1)` from triggering an implicit line feed on the physical terminal.

Sanitize margins **after** drawing each row's cells. Reset SGR to default (`\x1b[0m`) immediately before `\x1b[K` to prevent color bleed (the original post-line bug was the missing SGR reset, not the position). Removing `\x1b[J` entirely avoids the stroboscopic filmstrip artifact from pre-line erasure and the unsafe cursor-clamping risk during drag-resize — transient bottom-margin garbage resolves naturally when PTY geometry catches up.

```rust
pub fn render_frame(out: &mut dyn Write, screen: &Screen, rows: u16, cols: u16) -> io::Result<()> {
    let mut buf = Vec::with_capacity(...);
    let mut active_style = CellStyle::default();

    buf.extend_from_slice(b"\x1b[0m");
    buf.extend_from_slice(b"\x1b[?7l");       // disable DECAWM

    for row in 0..rows {
        write!(buf, "\x1b[{};1H", row + 1)?;

        // ... cell-writing loop (apply_sgr, contents, unicode_width) ...

        // Post-cell right-margin sanitation: reset SGR then clear to end of line
        buf.extend_from_slice(b"\x1b[0m\x1b[K");
        // Synchronize tracker with the physical \x1b[0m reset
        active_style = CellStyle::default();
    }

    buf.extend_from_slice(b"\x1b[?7h");       // re-enable DECAWM
    // ... cursor position, cursor visibility ...
    out.write_all(&buf)?;
    out.flush()
}
```

### Fix 2: Make `apply_pending_resize` a pure function returning `bool`

Remove `stdout` parameter, the clear-code injection, and the mutable capture of `force_render`. Return `true` when geometry was actually updated, letting call sites aggregate the flag via `|=`:

```rust
let apply_pending_resize = |shared_parser: &Arc<Mutex<Parser>>| -> bool {
    if resize_pending.swap(false, Ordering::Relaxed) {
        let cols = server_cols.load(Ordering::Relaxed);
        let rows = server_rows.load(Ordering::Relaxed);
        if cols > 0 && rows > 0 {
            let mut parser_lk = shared_parser.lock().unwrap();
            let (cur_rows, cur_cols) = parser_lk.screen().size();
            if cur_cols != cols || cur_rows != rows {
                parser_lk.screen_mut().set_size(rows, cols);
                return true;
            }
        }
    }
    false
};
```

Site 1: `force_render |= apply_pending_resize(&pane.shared_parser());`
Site 2: `force_render |= apply_pending_resize(&pane.shared_parser());`

### Fix 3: Remove `\x1b[2J` from `Event::Resize` (already clean)

Current `Event::Resize` handler is already correct — no `\x1b[2J`, just `pane.resize()` + `force_render = true`. Keep as-is.

### Fix 4: Re-enable server broadcast to all clients (already reverted)

Leave `session_server.rs` unchanged — `guard.clients.values().cloned().collect()` broadcasts to all clients including the originator. The `\x1b[2J` removal makes the echo loop benign: `OnPtyResized` still fires, `apply_pending_resize` runs, but if dimensions already match, it's a no-op (no clear, no corruption).

### Fix 5: Keep unconditional server_cols store in `Event::Resize` (already correct)

Current code does `pane.resize()` which internally calls `ResizePty::call(...)` → server responds with constrained `(actual_cols, actual_rows)` → parser is resized to those actual dimensions. The `OnPtyResized` that arrives later will set `resize_pending`, but `apply_pending_resize` checks parser dims and sees they match → no-op. This works correctly without the pre-emptive atomics update.
